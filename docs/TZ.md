### 0.2 Из PDF «CX Pulse Control — карточка проекта»

- Бизнес-цель: быстрее находить и маршрутизировать проблемные обращения, раньше замечать повторные жалобы и риск ухода клиента.
- Контур решения: 01 Обращение (текст/расшифровка) → 02 Поиск контекста (история клиента) → 03 Решение агента (риск и приоритет) → 04 Вызов инструмента (создание инцидента) → 05 Контроль (статус и аналитика).
- Scope MVP: поток синтетических текстовых обращений из нескольких каналов; агент анализирует, запрашивает историю, определяет приоритет, создаёт инцидент; панель оператора и руководителя: очередь, карточка инцидента, статусы, показатели.
- Демо на защите (3–5 мин): саркастичная жалоба о повторном списании комиссии → агент находит историю и распознаёт риск ухода → выбирает приоритет, вызывает инструмент, создаёт инцидент → инцидент в очереди, аналитика обновляется → жюри вводит своё сообщение (проверка вне заготовки).
- Что доказываем и измеряем: точность классификации и маршрутизации; полнота обнаружения критичных обращений; время от обращения до создания инцидента.

### 0.4 Из калькулятора «Потери от сбоев (dCLTV)» (скриншоты HTML)

- Методология: сбой превращает довольного клиента в детрактора, который приносит банку меньше прибыли; потеря одного такого клиента оценена для каждого продукта/канала ставкой dCLTV (₽). Формула — как в справочнике NPS-инициатив, но «наоборот».
- Формула: Потеря (₽) = Пострадавшие × % ставших детракторами × % невозврата × Ставка dCLTV.
- Значения по умолчанию в калькуляторе: пострадавших 100 000, детракторов 10 %, невозврата 50 %.

## 1. Цель и границы MVP

### 1.1 Цель
Показать работающего ИИ-агента команды CX крупного банка, который в реальном времени принимает клиентские сигналы со всех поверхностей, связывает их с техническими событиями подсистем, самостоятельно создаёт и маршрутизирует инциденты, информирует клиента, контролирует исполнение командами и закрывает петлю (клиент получил услугу → извинительный подарок), а в спорных случаях передаёт решение человеку (human-in-the-loop). При этом «под капотом» видны рассуждения агента, граф выполнения и изменения в БД, а эффективность разных LLM измерима. **[BRD]** Дополнительно демо-стенд показывает два контура реального времени для C-level: автономное закрытие клиентского негатива с внешней площадки (отзыв → идентификация → проверка транзакций → возврат комиссии в Mock-АБС → публичный ответ за ≤ 10 с) и пресечение комплаенс-риска в отделении (речь сотрудника → потоковая транскрибация → детекция мисселлинга → алерт руководителю при третьем нарушении).

### 1.2 Входит в MVP (must have)
1. Эмулятор рабочего дня банка с генерацией псевдослучайных событий (операции клиентов, сбои подсистем, ошибки клиентов, жалобы по каналам, действия команд).
2. ИИ-агент CX на базе GigaChat-3-Ultra со сменным провайдером LLM.
3. Рабочее место сотрудника CX: лента сигналов, тепловая карта РФ, очередь HITL, доска инцидентов, карточка инцидента с историей клиента/инцидентов/статусов, центр уведомлений, задачи на подарки.
4. Экран «Под капотом»: трассировка шагов и рассуждений агента, визуализация графа агента и графа сущностей, активность БД, шина событий.
5. Лендинг неидентифицированного клиента + публичная страница трекинга обращения с уведомлениями.
6. Мастер первичной настройки и меню настроек.
7. БД с синтетическими данными без ПДн, сгенерированная ИИ-инструментами.
8. Бенчмарки и метрики для сравнения LLM-провайдеров (GigaChat-3-Ultra/Lightning/Pro, OpenRouter-free, mock).
9. Установка одним скриптом из репозитория, без внешних сервисов (кроме API выбранной LLM и, опционально, Telegram Bot API).
10. Расчёт экономического эффекта по методике dCLTV бизнес-команды (раздел 14.4).
11. Интерфейс ru/en, визуальный стиль «в духе Сбера» без явного брендирования.
12. Telegram-бот для сценария потенциального клиента на финале (опциональный сервис).
13. Модель поведения клиентов (психотипы, реакция на инциденты и на заботу, уход) — чтобы экономика и метрики удержания считались по эмулированным исходам, а не по константам (4.5, 14.5).
14. **[BRD]** Контур «Внешние площадки и автономный возврат»: эмулятор ленты отзовика/Telegram-канала, приём отзывов по API, матчинг клиента по косвенным данным, Mock-АБС со счетами и проводками, детерминированные бизнес-правила, инструмент возврата комиссии, публичный ответ под постом, «быстрый путь» агента (раздел 21).
15. **[BRD]** Контур «Аудиомониторинг отделения и мисселлинг»: потоковый STT из микрофона браузера (офлайн Vosk в контейнере, сменный провайдер), разделение спикеров, гибридный детектор мисселлинга, счётчик нарушений на сессию, алерт руководителю (WebSocket, опционально Telegram), экран мониторинга и эмулятор устройства руководителя (раздел 22).
16. **[BRD]** Режим подстраховки для показа без сети: кассеты записанных ответов реальных моделей (`replay`-провайдер), предзаписанные аудиофайлы, скрытая кнопка запуска (5.4, 12.7).
17. **[BRD]** Панель «Log/Debug» на демо-экранах: проценты уверенности, извлечённые JSON-сущности, сработавшие правила — в одном окне с бизнес-результатом (12.6).
18. **[BRD]** Голосовой ввод жалобы «Надиктовать»: кнопка микрофона в режиме показа и на лендинге, тот же `STTProvider`, текст уходит агенту обычным сигналом канала `voice_input` (3.6, 11, 12.2).
19. **[ДТЗ]** Приёмный слой `ingest`: единая схема сообщения и нормализатор, приём транскриптов диалогов файлами/REST, адаптеры источников REST/polling (3.7).
20. **[ДТЗ]** NLP-дополнения: тональность трёх классов (≥ 80 % на `sentiment_v1`), детектор скрытого негатива few-shot, саммари `problem_summary` (7).
21. **[ДТЗ]** Роутер-инструменты агента `route_to_department` / `notify_customer` / `escalate_to_manager` / `request_clarification`, поле `router_action`, эскалации руководителю CX, тикетница `v_tickets` и экспорт цепочки решений (9.2, 9.7).
22. **[ДТЗ]** «Красные фразы» сотрудника по готовому транскрипту (пакетный режим) с рекомендацией руководителю; трёхцветные зоны карты и живой тикер эффекта (12.2, 22.8–22.9).

### 1.3 Не входит (out of scope)
Реальные интеграции с банковскими системами и каналами банка (единственный реальный внешний канал — собственный Telegram-бот для финала, раздел 11.3); аутентификация/авторизация (оставлена на будущее развитие); реальные ПДн; реальный биллинг и платёжные системы (возвраты комиссий выполняются только в Mock-АБС, 21.4); мобильные приложения; синтез речи (TTS) и голосовые звонки в каналах контакт-центра (транскрипты приходят текстом — решение №13; голос клиента в MVP есть только как «надиктовать жалобу» на стенде, 3.6); диаризация по голосовому отпечатку (pyannote и аналоги — требуют GPU и закрытых моделей, 22.3); парсинг реальных площадок (Банки.ру, Telegram) — заменён эмулятором и API (21.2); запуск локальных LLM внутри приложения; высоконагруженная архитектура; интеграция с существующими агентами банка (решение команды). **[BRD]** Потоковое распознавание речи (STT) из состава исключений выведено частично: оно входит в MVP только для контура аудиомониторинга отделения (раздел 22).

### 1.4 Принципы
- Демо важнее глубины: каждая сущность имеет ровно столько полей, сколько нужно показать на экране.
- Детерминированность: все генераторы принимают seed; демо-сценарии воспроизводимы.
- Всё эмулируемое помечено как эмуляция (бейдж «эмуляция» в UI), чтобы жюри понимало границы.
- LLM-независимость: агент работает через единый интерфейс провайдера; при недоступности LLM есть rule-based fallback, чтобы демо не сорвалось.
- Open source only: лицензии MIT/Apache-2.0/BSD/PostgreSQL/OFL, бесплатные для коммерческого использования.
- **[BRD]** Деньги — только по правилам: любое движение средств (возврат комиссии) инициируется агентом, но подтверждается детерминированным бизнес-правилом и лимитом автономии (9.3, 9.6); LLM объясняет и общается, правило — разрешает списание/возврат. Это одновременно защита от галлюцинаций и наглядный аргумент для комплаенса.
- **[BRD]** Реальное время не зависит от симуляционного: контуры «внешние площадки» и «аудиомониторинг» управляются человеком у стенда и работают с задержкой реального мира даже при паузе симулятора (4.7).
- **[ДТЗ]** Имена наружу — из ТЗ заказчика, механика — внутренняя: инструменты, поля JSON и шкалы, названные в дополнительном ТЗ, реализуются с точными именами как внешний контракт показа (`route_to_department`, `problem_summary.severity`, `sentiment`), а внутренние механизмы v1.3 (политики, правила, HITL, экономика) остаются под ними; двойного хранения данных не допускается (одна БД — PostgreSQL).
- **[BRD]** Демо не может сорваться: для каждого демо-сценария есть офлайн-путь (mock или кассета `replay`) и предзаписанные входы, запускаемые скрытой кнопкой (5.4, 12.7).

## 3. Модель банка (предметная область)

### 3.1 Сегменты клиентов
`mass` Массовый · `salary` Зарплатный · `premium` Премиум · `vip` VIP · `ultra_vip` Ultra VIP (Private) · `social` Льготный/социальный (пенсионеры, льготные категории) · `youth` Молодёжный.

### 3.2 География
Справочник всех субъектов РФ (области, республики, края, автономные округа/область, города федерального значения) с федеральным округом, кодом региона, численностью населения и центроидом для карты; справочник городов (≥ 1 100 городов РФ или минимум топ-300 по населению + все региональные центры) с координатами. Клиенты распределяются по субъектам и городам пропорционально населению с настраиваемыми «горячими точками» для демо. Карта — SVG субъектов РФ (данные из открытых источников: Natural Earth / OSM-производные с лицензией, допускающей коммерческое использование; файл кладётся в репозиторий, без CDN).

### 3.3 Продукты

### 3.4 Системы банка (эмулируемые)
Фронтовые: `mobile_app` Мобильное приложение · `web_bank` Сайт/интернет-банк · `contact_center` Платформа контакт-центра (звонки, чаты, письма) · `social_listening` Мониторинг соцсетей.
Промежуточные: `processing` Процессинг карт · `notification_gw` Шлюз уведомлений (push/SMS/e-mail) · `promo_engine` Движок акций и тарифов · `antifraud` Антифрод.
Продуктовые подсистемы: `sub_deposits` Вклады · `sub_lending` Кредиты и кредитные карты · `sub_debit` Дебетовые карты. Ядро: `core_abs` АБС (учёт).
Каждая система пишет лог событий (уровень, код ошибки, компонент, затронутые клиенты/операции). Пример путей операции: «Открыть вклад» = mobile_app → promo_engine → sub_deposits → core_abs → notification_gw.
**[BRD]** `core_abs` и `processing` в v1.3 становятся *stateful*-моками (Mock-АБС): у каждого клиента есть счета с балансом (`accounts`), каждая операция порождает проводки (`ledger_entries`) с отдельной строкой комиссии (`fee`), а возврат (`refund`) — обратную проводку; баланс и проводки видны в UI на виджете «АБС (эмуляция)». Новый код ошибки `PROC-QR-FEE-CHARGED` — комиссия списана за оплату по QR (СБП), которая по тарифу для физлиц бесплатна; это событие-триггер сценария 8. Дополнительно эмулируются `review_portal` (внешняя площадка отзывов/Telegram-канал, 21.2) и `branch_audio` (аудиоканал отделения, 22) — как источники сигналов, а не как банковские системы.

### 3.5 Команды (эмулируемые исполнители инцидентов)
`team_cx` CX · `team_deposits` · `team_lending` · `team_debit` · `team_front` (приложение/сайт) · `team_processing` · `team_notifications` · `team_contact_center` · `team_promo` · `team_antifraud` · **[BRD]** `team_compliance` (комплаенс: разбор мисселлинга, регуляторные сигналы) · `team_branch_network` (сеть отделений: руководители ВСП, получатели алертов). Для каждой: зона ответственности (системы), «скорость» (распределение времени реакции и фикса), вероятность запроса уточнений, вероятность нарушения SLA (для демонстрации эскалаций).

|---|---|---|---|
| Соцсети | VK, Одноклассники, Telegram-комментарии, отзовики (банковские порталы) | часто нет (ник), иногда по номеру карты/телефона в ЛС | короткий эмоциональный текст |

### 3.7 Приёмный слой `ingest`: единая схема сообщения, транскрипты, адаптеры источников [ДТЗ]
**Единая схема сообщения** (`contracts/events/ingest/unified_message.schema.json`, FR-1.3): `channel` (из перечисления каналов), `channel_subtype`, `external_id` (идемпотентность), `client` — либо `client_id`, либо `contact_hints` {phone, email, nickname, card_last4, name}, `text`, `timestamp` (момент возникновения у источника; `received_at` ставит сервер), `geo` {region_code, city_id, lat, lon, source ∈ client_profile | message | contact | ip_mock | none}, `attachments[]` (ссылки на транскрипт/пост), `origin`, `meta`. Нормализатор `app/ingest/normalizer.py` приводит к этой схеме все входы: события симулятора, `POST /api/signals`, лендинг, бот, посты площадки, голосовой ввод, транскрипты и сообщения адаптеров — и только потом создаёт `signals` (с `geo`). Каскад гео: город клиента → регион контакта → гео сообщения → имитация по IP (только для demo-профиля, помечается) → `none` (сигнал не попадает на карту и учитывается счётчиком «без гео»).

**Транскрипты диалогов** (FR-1.1, FR-4.1). Форматы: JSON по схеме `ingest/transcript.schema.json` (метаданные: `kind` ∈ branch_retail | contact_center_call | contact_center_chat, отделение/сотрудник/стол, `client_id` или контакты, продукт сделки, `started_at`, `geo`; реплики `turns[]` с `speaker` ∈ employee | client, `text`, `t0_ms`/`t1_ms` опционально) и TXT построчно: `[чч:мм:сс] Сотрудник: …` / `Клиент: …` (таймкод опционален; роли распознаются по словарю синонимов «Оператор/Менеджер/Сотрудник», «Клиент/Абонент»). Входы: `POST /api/ingest/transcripts` (JSON-тело или multipart с несколькими файлами), пакетный импорт каталога `data/import/transcripts/` при сиде и кнопкой в настройках, drag-and-drop на вкладке «Транскрипты» экрана `/compliance`. Каждый транскрипт сохраняется в `transcripts` и получает до двух анализов по флагам `analyses`: `client_signal` — реплики клиента собираются в текст обращения, создаётся сигнал канала `call`/`chat`/`branch` с `origin = transcript`, далее обычный граф агента (ответ клиенту, маршрутизация, эскалация); `employee_quality` — пакетный анализ речи сотрудника на «красные фразы» (22.8) с отчётом руководителю. По умолчанию для `branch_retail` включены оба анализа, для контакт-центра — `client_signal` (второй включается флагом).

**Адаптеры источников** (FR-1.2). Таблица `ingest_sources` (code, kind ∈ rest | polling | file, channel, config JSONB, enabled, interval_s, last_polled_at, cursor). `rest` — приём `POST /api/ingest/messages` (одно сообщение или массив); `polling` — фоновый воркер каждые `interval_s` (по умолчанию 10 с) запрашивает URL из `config.url`, ожидает массив сообщений единой схемы, дедуплицирует по `external_id`, сохраняет `cursor`; `file` — читает JSONL из каталога. В demo-профиле заведён источник `mock_social_polling`, который опрашивает собственную mock-ленту backend `GET /api/public/mock-social-feed` (синтетические сообщения из корпуса соцсетей по расписанию симулятора) — так требование «имитация через REST или polling» выполняется обоими способами без внешних сервисов. Внешние URL для polling допускаются только при явной настройке и помечаются как «внешний источник».

## 4. Эмулятор рабочего дня банка

### 4.1 Симуляционное время
- Рабочий день 09:00–21:00 симуляционного времени; множитель скорости настраивается (по умолчанию 1 сим-час = 1 реальная минута → день за 12 минут; есть пресеты «демо 5 минут», «реалтайм»). Кнопки: Старт/Пауза/Стоп/Возобновить/Шаг/Сброс дня, выбор текущего запуска и история запусков (раздел 4.6); «циркадная» тема UI привязывается к симуляционному времени, а не к системному (наследие прототипа, но информативнее).
- Рабочие дни для SLA считаются в симуляционных днях; календарь выходных упрощён (сб/вс).

### 4.2 Генератор событий (Event Engine)
Детерминированный PRNG (seed в настройках). Типы событий и целевые интенсивности по умолчанию (на сим-час, настраиваются):

| Событие | Интенсивность | Описание |
|---|---|---|
| `op.*` операции клиентов | 300–600 | открытие вклада, пополнение, перевод, оплата картой, платёж по кредиту, выпуск карты, запрос лимита |
| `fault.*` сбои подсистем | 0.5–2 | таймаут/ошибка в системе; затрагивает N операций за окно времени; имеет код (DEP-TIMEOUT-503, PROMO-RATE-MISMATCH, PROC-DOUBLE-DEBIT, NOTIF-DELAY, APP-LOGIN-FAIL …) |
| `client_error.*` ошибки клиента | 20–40 | неверные реквизиты, ожидание промо-ставки после окончания акции, непонимание комиссии, просрочка по невниманию |
| `signal.*` обращения клиентов | 15–40 | генерируются из операций/сбоев/ошибок с задержкой (минуты–часы), выбором канала и тональности; часть «шумовых» (благодарности, вопросы, предложения) |
| `team.*` действия команд | по инцидентам | взятие в работу, запрос уточнений, RCA, решение о фиксе, релиз, закрытие |
| `fault.regression` регрессия после фикса | 10–15 % релизов | «починили одно — сломали рядом»: новый сбой в смежной системе/продукте в течение 1–4 сим-часов после `team.release`, с ссылкой на исходный инцидент (`faults.caused_by_incident_id`) |
| `client.*` поведение клиентов | по модели 4.5 | реакция на ответ агента (`satisfied`, `asks_again`, `escalates`, `silent`), `churn_intent`, снижение активности, `account_closure` (закрытие обслуживания) |
| `sla.tick` | каждые 15 сим-мин | пересчёт остатков SLA, эскалации |
| `review.*` **[BRD]** | по действию пользователя у стенда + 0–2 фоновых в сим-час | `review.posted` (пост на эмуляторе площадки или по API), `review.replied` (публичный ответ агента), `review.escalated_to_dm` (перевод в личный канал) |
| `abs.*` **[BRD]** | по операциям | `abs.fee_charged`, `abs.refund_posted`, `abs.balance_changed` — проводки Mock-АБС; видны на виджете баланса |
| `compliance.*` **[BRD]** | по аудиосессиям | `compliance.session_started`, `compliance.utterance` (финальная реплика с ролью), `compliance.trigger` (нарушение с категорией и уверенностью), `compliance.alert` (порог достигнут), `compliance.session_closed` |

Каузальность: сбой → затронутые операции → у части клиентов жалобы (вероятность зависит от психотипа, сегмента и суммы) → повторные жалобы при отсутствии реакции → рост риска ухода → при превышении терпения уход (закрытие продуктов). Параметры вероятностей и задержек берутся из психотипа клиента (раздел 4.5). Это даёт агенту возможность связывать жалобы между собой и с логами, а экономике — считать удержание по фактическим исходам.

### 4.3 Сценарный слой
Поверх случайного потока — скриптовые сценарии (YAML в `scenarios/`), запускаемые кнопкой из UI: гарантируют воспроизводимость демо (раздел 18). Сценарий задаёт клиента, последовательность событий с относительным временем, ожидаемые действия агента (для автопроверки).

### 4.4 Масштаб данных и профили

Решение заказчика: глубина истории — 14 календарных дней (покрывает самые долгие инциденты в 10 рабочих дней), приоритет — разнообразие ситуаций, а не объём.

| Профиль | Клиентов | История | Сигналов в истории | Инцидентов в истории | Когда использовать |
|---|---|---|---|---|---|
| `demo` (по умолчанию) | 5 000 | 14 дней | ~2 500 | ~400 | ВМ/ноутбук 16–32 ГБ, демо и защита |
| `lite` | 1 000 | 14 дней | ~800 | ~150 | слабое железо, быстрые пересоздания, автотесты |
| `stress` (опционально) | 20 000 | 14 дней | ~10 000 | ~1 500 | проверка производительности UI |

Требование к разнообразию («матрица покрытия»): генератор обязан обеспечить наличие в истории каждой комбинации {тип сигнала} × {продукт} × {канал} хотя бы один раз и каждой ячейки матрицы SLA (сложность × критичность) не менее 5 инцидентов, включая закрытые в срок, просроченные и находящиеся в промежуточных статусах; обязательно присутствие всех сегментов и всех федеральных округов. Матрица покрытия проверяется тестом после генерации и отображается в мастере.

### 4.5 Модель поведения клиентов: психотипы и «цифровые двойники»

Назначение (решение заказчика, v1.1): клиенты в симуляции должны вести себя как «средний клиент банка» и по-разному реагировать на сбои и на заботу о себе, чтобы коэффициенты удержания в экономике были результатом эмуляции, а не константами. Модель двухуровневая: параметрическая для всех клиентов (дёшево, детерминированно) и LLM-двойники для «подсвеченных» клиентов (дорого, но даёт живые тексты и реакции).

Схема психотипов (предложение архитектора; 8 типов, доли настраиваются по сегментам):

| Код | Психотип | Как проявляется | p(жалоба при сбое) | Задержка жалобы | Терпение до ухода | Чувствительность к заботе | Предпочтения каналов |
|---|---|---|---|---|---|---|---|
| `loyal_pragmatic` | Лояльный прагматик | терпит мелкие сбои, пишет по делу, благодарит | 0,25 | часы–день | 7–10 раб. дней | средняя (ценит факт решения) | приложение, чат |
| `anxious` | Тревожный | пишет сразу, часто в несколько каналов, успокаивается после информирования | 0,70 | минуты | 5–7 дней | высокая (достаточно «мы видим проблему») | звонок, чат, повтор в соцсети |
| `demanding_rational` | Требовательный рационалист | хочет сроки, причины и компенсацию; фиксирует нарушения SLA | 0,60 | часы | 3–5 дней, при срыве SLA — уход | высокая к срокам, низкая к подаркам без решения | e-mail, чат |
| `public_emotional` | Эмоциональный публичный | сарказм/агрессия в соцсетях, вирусность; смягчается при публичном ответе и личном канале | 0,55 | минуты–часы | 3–5 дней | высокая к скорости и тону, средняя к подаркам | соцсети, затем чат |
| `silent_churner` | Молчаливый уходящий | не жалуется, снижает активность и уходит; виден только по операциям | 0,10 | — | 5–10 дней | высокая к проактивному уведомлению (единственный рычаг) | push |
| `bonus_hunter` | Охотник за бонусами | жалуется ради компенсации, повторяется; удержание зависит от подарка | 0,65 | часы | 10+ дней | низкая к словам, высокая к баллам | чат, соцсети |
| `novice` | Новичок / низкая финансовая грамотность | ошибки клиента, путает комиссию и сбой; нужен понятный ответ | 0,45 | часы–день | 5–7 дней | высокая к объяснению и обучающему контенту | звонок, отделение |
| `status_oriented` | Статусный | ожидает персонального сервиса и скорости; привилегии партнёров значимы; typical для premium/vip/ultra_vip | 0,50 | минуты–часы | 2–4 дня | высокая к персональному менеджеру и привилегиям | звонок менеджеру, чат |

Доли психотипов по сегментам (значения по умолчанию, редактируются): mass — loyal 30 / anxious 20 / demanding 10 / public 10 / silent 15 / bonus 5 / novice 10 / status 0; salary — loyal 35 / anxious 15 / demanding 15 / public 5 / silent 20 / bonus 5 / novice 5; social — loyal 25 / anxious 30 / novice 25 / silent 15 / public 5; youth — public 25 / bonus 20 / novice 20 / anxious 15 / loyal 10 / silent 10; premium — demanding 30 / status 25 / loyal 25 / silent 15 / public 5; vip — status 45 / demanding 30 / loyal 20 / silent 5; ultra_vip — status 70 / demanding 30. Психотип хранится в `clients.psychotype` и не показывается клиенту; сотруднику CX он виден как подсказка «стиль коммуникации» в карточке Клиент 360 (на реальных данных это был бы ML-признак; в MVP — метка генератора).

Состояния клиента (машина состояний, таблица `client_states`): `calm` → `affected` (операция попала в сбой) → `complaining` (создан сигнал) → `waiting` (ждёт ответа/решения) → `satisfied` | `asks_again` | `escalates` (повторный сигнал, другой канал, резче тон) | `churn_intent` (флаг в тексте или по снижению активности) → `retained` | `churned`. Переходы задаются параметрами психотипа и фактами обслуживания: время первого ответа, выполнение SLA, промежуточные отчёты, проактивное уведомление до жалобы, подарок и его соответствие психотипу, нарушение тона (запрещённые формулировки снижают удержание). Формула склонности к уходу (параметрическая, настраивается): `hazard = base(psychotype) × seg_mult × (1 + 0.5·repeat) × (1 + 0.8·sla_breach) × (1 − care_sensitivity·care_score)`, где `care_score ∈ [0,1]` агрегирует проактивность, скорость, соблюдение сроков и уместность подарка. Каждый `sla.tick` клиенты в `waiting`/`churn_intent` разыгрывают переход.

Уход как инцидент: событие `client.account_closure` создаёт сигнал типа `churn` и внутренний инцидент `account_closure` (команда `team_cx`, сложность `medium`, критичность по сегменту; для vip/ultra_vip — `high` и обязательный HITL) с обязательными полями «причина ухода», «связанные инциденты», «что было предложено», «можно ли вернуть». Такие инциденты не требуют ответа клиенту, но входят в экономику как реализованная потеря (14.4) и в разбор «почему не удержали» на дашборде.

LLM-двойники («подсвеченные» клиенты): для клиентов из сценариев 18, из очереди HITL, для сегментов vip/ultra_vip и для случайной выборки (по умолчанию ≤ 20 клиентов на сим-день, лимит в настройках) тексты жалоб, уточнений и реакций генерирует лёгкая модель (`GigaChat-3-Lightning` по умолчанию; в офлайне — mock на шаблонах по психотипу). Промпт двойника получает: психотип, сегмент, продукт, историю операций и обращений, последнее сообщение банка, фактическое состояние проблемы — и возвращает структурированный ответ `{reaction, tone, text, churn_intent, satisfaction 0–1}`. Двойник не знает внутренних данных инцидента, кроме того, что ему сообщили, — так проверяется качество коммуникации агента. Расход токенов двойников учитывается отдельно (`agent_runs.kind = 'client_twin'`) и ограничен бюджетом; остальные клиенты обслуживаются параметрической моделью без LLM.

Что это даёт демо: на экране «Под капотом» виден диалог агент ↔ двойник; на дашборде — удержание по психотипам и по «уровню заботы»; в калькуляторе (14.5) — фактические исходы вместо допущений; в сценариях — «молчаливый уход», который агент ловит по снижению активности и проактивному уведомлению.

### 4.6 Запуски эмуляции: история, изоляция, прерывание и возобновление

Требование заказчика (v1.2): итоги каждого запуска эмуляции сохраняются; повторный запуск сценария не должен «загрязняться» предыдущими; эмуляцию можно прервать и возобновить.

Понятия:
- **Базовое состояние (baseline)** — результат генерации синтетических данных (клиенты, продукты, 14 дней предыстории, справочники, настройки). Создаётся мастером/`install.sh`; сразу после генерации сохраняется снимок (`pg_dump -Fc` → `data/baseline/<profile>.dump` и контрольная сумма). Предыстория помечена `run_id` базового запуска (`sim_runs.kind = 'baseline'`).
- **Запуск (run)** — отрезок работы симулятора от «Старт» (или запуска сценария) до «Стоп»/завершения сценария. Запись в `sim_runs`: идентификатор, метка, вид (`free` — свободная эмуляция, `scenario` — демо-сценарий, `baseline`), сценарий, сид, профиль LLM, снимок настроек, `started_sim`/`finished_sim`, реальное время, статус (`running` | `paused` | `interrupted` | `completed` | `stopped` | `archived`), итоговые метрики (`summary` JSONB: все показатели раздела 14.1 и экономика 14.4 за запуск, расход токенов по профилям, число запусков агента, HITL, SLA, удержание, ушедшие).
- **Привязка данных.** Все строки, порождённые во время запуска, несут `run_id`: события, операции, сбои, логи, сигналы, инциденты, действия команд, артефакты, задачи, уведомления, состояния и реакции клиентов, уходы, запуски агента, решения людей, отложенные пробуждения, расчёты экономики. Справочники, клиенты и бенчмарки вне запусков (`run_id` отсутствует).

Поведение:
- **Текущий запуск** хранится в `sim_state.current_run_id`. Дашборд, лента, карта, доска инцидентов, калькулятор «Факт» и метрики по умолчанию показывают текущий запуск; переключатель «Запуск» позволяет выбрать любой прошлый запуск или «все» (для сравнения). Данные базового состояния видны в режиме «baseline + текущий» (по умолчанию для лент и карточек, чтобы история клиента и инцидентов не исчезала) и исключаются из счётчиков запуска.
- **Стоп / прерывание.** «Пауза» замораживает время без завершения запуска. «Стоп» завершает запуск: фиксируется `finished_sim`, рассчитывается `summary`, статус `stopped`; открытые инциденты и ожидающие HITL остаются в данных запуска как «незавершённые» и учитываются в метриках как `open`. Прерывание извне (остановка контейнера, падение процесса, закрытие ноутбука) переводит запуск в `interrupted` при следующем старте приложения.
- **Возобновление.** Запуск в статусах `paused`/`interrupted` возобновляется с того же `sim_time`: генераторы продолжают по сохранённому сиду и счётчикам RNG (`sim_state.rng_state`), прерванные запуски агента восстанавливаются из чекпоинтов LangGraph (шаг с незавершённым LLM-вызовом помечается `retry` и выполняется заново), отложенные пробуждения (`followups`) и таймеры поведения клиентов пересчитываются от `sim_time`. Возобновлять можно только последний незавершённый запуск; завершённые (`completed`/`stopped`) не возобновляются — создаётся новый.
- **Повторный запуск сценария.** Кнопка «Запустить сценарий» предлагает режим сброса: `counters` — новый `run_id` с чистыми счётчиками и метриками поверх текущего состояния данных (быстро, прошлые запуски остаются в истории, но не влияют на показатели); `baseline` — полный откат к базовому состоянию из снимка (`pg_restore` в транзакции обслуживания, ≤ 60 с для `demo`), после чего стартует новый запуск; для сценариев с «именованными» клиентами (сценарии 1, 4, 7) режим `baseline` обязателен, иначе клиент уже находится в изменённом состоянии. Все прошлые запуски сохраняются в `sim_runs` с метриками; при `baseline`-сбросе их строки данных удаляются вместе с восстановлением, а `summary` и экспорт запуска (JSON) остаются — таблица `sim_runs` и каталог `runs/` не входят в снимок и восстанавливаются после `pg_restore`.
- **История запусков.** Экран «Запуски» (вкладка панели управления): список с метками, сценарием, длительностью, статусом, ключевыми метриками; сравнение двух запусков рядом (например, один и тот же сценарий на GigaChat-3-Ultra и на mock); экспорт запуска в JSON/CSV; архивирование (удаление строк данных с сохранением `summary`); удаление.
- **Детерминизм.** Повторный запуск сценария в режиме `baseline` с тем же сидом и mock-провайдером даёт идентичные события и метрики — это проверяемый критерий (19).
- **Install/CLI.** `install.sh --reset` восстанавливает baseline из снимка (если он есть) вместо повторной генерации; `scripts/run.sh stop|resume|status|reset-baseline` — те же действия из консоли.

### 4.7 Реальное время против симуляционного: «живые» контуры [BRD]

Контуры «внешние площадки» (раздел 21) и «аудиомониторинг» (раздел 22) управляются человеком у стенда и обязаны реагировать с задержкой реального мира (секунды), независимо от скорости и состояния симулятора:
- Если симулятор на паузе или остановлен, событие `review.posted` или `compliance.*` всё равно обрабатывается немедленно; агент и детектор работают в реальном времени всегда, симуляционное время нужно им только как метка (`*_sim`) для SLA и отчётов.
- Если текущего запуска нет (`sim_state.current_run_id IS NULL`), система автоматически создаёт запуск вида `live` (`sim_runs.kind = 'live'`), чтобы соблюсти правило изоляции по `run_id` (4.6); такие запуски видны в истории с меткой «живой показ».
- Все задержки живых контуров измеряются в реальном времени и пишутся в `agent_steps.latency_ms` / `utterances.latency_ms`; целевые бюджеты — 16.4.
- Фоновая генерация отзывов (0–2 в сим-час) и фоновые аудиосессии (предзаписанные, по расписанию) включаются в настройках, чтобы лента `/feed` и статистика мисселлинга не были пустыми до прихода демонстратора.

Один `docker compose up`: сервисы `db`, `backend`, `frontend` (nginx со статикой), опционально `mailpit` (эмулятор почты, MIT) и `tgbot` (Telegram-бот для финала, раздел 11.3). **[BRD]** Потоковый STT (Vosk) живёт внутри `backend` как отдельный asyncio-воркер с собственным пулом процессов (модель загружается один раз при старте; ~0,3 ГБ ОЗУ для small-модели), а не отдельным сервисом — чтобы не усложнять `install.sh`; при `--no-stt` воркер не запускается. Аудио с микрофона захватывается браузером (`getUserMedia` + `AudioWorklet`), пакуется в PCM16 16 кГц и передаётся по WebSocket `/ws/audio/<session_id>` — для этого фронтенд должен открываться по HTTPS или с `localhost` (16.1). Внешние зависимости — только исходящий HTTPS к API выбранной LLM и, при включённом боте, к Telegram Bot API; для офлайн-демо есть провайдер `mock`. Запуск локальных моделей в состав приложения не входит (решение заказчика), но любой внешний OpenAI-совместимый endpoint (в том числе локальная модель на другой машине) подключается через адаптер `openai_compatible`.

Целевая среда: любая Linux-машина с Docker — ВМ заказчика за VPN/Caddy или ноутбук; 4–8 ядер (8–16 потоков), 16–32 ГБ ОЗУ. Интернет на защите гарантирован организаторами.

### 5.2 Абстракция LLM-провайдера
Интерфейс `LLMProvider`: `chat(messages, tools, response_schema, temperature) → {content, tool_calls, usage, latency_ms, raw}`; `embed(texts)` (опционально); `health()`.
Реализации:
- `gigachat` — нативный клиент (langchain-gigachat / REST `POST /v1|v2/chat/completions`), авторизация по Authorization key (freemium), access-токен живёт 30 минут и обновляется автоматически. Модель по умолчанию `GigaChat-3-Ultra`; быстрая модель для дешёвых шагов `GigaChat-3-Lightning`; для бенчмарков также `GigaChat-3-Pro`. Параллельные вызовы функций доступны в API v2 только у Ultra. Документация: https://developers.sber.ru/docs/ru/gigachat/models/gigachat-3-ultra , https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/post-chat , https://developers.sber.ru/docs/ru/gigachat/guides/functions/function-calling-modes
  - Пул ключей: у заказчика два freemium-ключа (физлицо и сотрудник), лимит 50 млн токенов на ключ (вход + выход суммарно). Провайдер хранит несколько ключей, ведёт счётчик израсходованных токенов по каждому (из поля `usage` ответа), показывает остаток в настройках и на экране бенчмарков, переключается на следующий ключ при исчерпании или ошибке квоты. Бенчмарк заранее оценивает расход (кейсов × средних токенов) и предупреждает, если прогон выйдет за заданный бюджет.
- `openai_compatible` — любой сервер с `/v1/chat/completions`: OpenRouter (основной «другой ИИ» для сравнения), gpt2giga-прокси, локальная модель на внешней машине (Ollama/vLLM/LM Studio) по URL. GigaChat также доступен через частично совместимый OpenAI-эндпоинт `https://api.giga.chat/v1` (https://developers.sber.ru/docs/ru/gigachat/guides/compatible-openai).
  - OpenRouter, профиль бесплатных моделей (id с суффиксом `:free`): платформенные лимиты 20 запросов/мин и 50 запросов/сутки (1 000/сутки, если на аккаунте когда-либо куплено ≥ $10 кредитов); неудачные запросы тоже расходуют суточный лимит (https://openrouter.ai/docs/api_reference/limits). Следствия: встроенный rate-limiter (≤ 18 RPM на провайдер), очередь запросов, чтение `GET /api/v1/key` для отображения остатка суточного лимита, «лёгкий» бенчмарк-набор на 30–40 кейсов для бесплатных моделей и запрет использовать OpenRouter-free как основную модель живого симулятора (только бенчмарки и ручные прогоны). Решение заказчика (v1.1): аккаунт OpenRouter уже существует, баланс $47 — порог $10 пройден, действует лимит 1 000 запросов/сутки на бесплатные модели; это позволяет прогонять полный золотой набор. Модели по умолчанию в профилях сравнения: `nvidia/nemotron-3-ultra-550b-a55b:free`, `openrouter/owl-alpha`, `openai/gpt-oss-120b:free`. Платные модели OpenRouter допускаются как резерв с бюджетным лимитом (по умолчанию $10 на весь хакатон, настраивается; расход читается из `GET /api/v1/key`). Примечание: `openrouter/owl-alpha` — stealth-модель без суффикса `:free`, она может быть переименована или снята с бесплатной раздачи в любой момент; мастер при первом запуске проверяет доступность каждого id через `GET /api/v1/models` и предлагает замену (`nvidia/nemotron-3-super-120b-a12b:free` или текущий топ коллекции бесплатных моделей).
- `mock` — детерминированный rule-based классификатор на ключевых словах и справочниках; гарантирует работу демо без сети (офлайн-сценарий на синтетических данных — требование заказчика) и служит бейзлайном в бенчмарках и «контрастом» для доказательства работы ИИ (раздел 12.5).
- `replay` **[BRD]** — провайдер-«кассета» (5.4): отдаёт заранее записанные ответы реальной модели по хешу нормализованного запроса (системный промпт + сообщения + схема + модель), эмулируя потоковую выдачу с исходной скоростью; при промахе кэша — делегирует следующему провайдеру в цепочке (`gigachat` → `mock`). Используется в режиме подстраховки, в автотестах сценариев (стабильные ответы без сети и без расхода токенов) и для повторяемости бенчмарков.
Политика «двух моделей»: тяжёлые шаги (решение, ответ клиенту) — основная модель; дешёвые (нормализация, извлечение сущностей) — быстрая. Профили моделей сохраняются в таблице `llm_profiles`, переключаются в настройках без перезапуска. Structured output: JSON-схемы Pydantic с валидацией и ретраем (до 2 попыток), при провале — fallback на mock и пометка в трассировке. Потоковая генерация (streaming) обязательна для основной модели — она используется на экране «Под капотом» для показа рассуждений в реальном времени.

### 5.3 Абстракция STT-провайдера [BRD]

Интерфейс `STTProvider`: `start_stream(session_id, sample_rate, channels) → stream`; `feed(stream, pcm_chunk)`; события `partial(text, channel)` / `final(text, channel, words[], t0, t1, confidence)`; `health()`; `capabilities()` → {streaming, channels, offline}. Реализации:
- `vosk` (по умолчанию) — офлайн, в контейнере `backend`; `KaldiRecognizer` на сессию, `SetWords(True)` для таймкодов; модель `vosk-model-small-ru-0.22` лежит в репозитории (`data/models/stt/`), более точная `vosk-model-ru-0.42` подключается через `install.sh --stt-model large` (скачивание с контрольной суммой, вне правила «без внешних зависимостей» как явная опция). Для стерео-входа создаются два распознавателя (канал 1 — сотрудник, канал 2 — клиент). Пользовательский словарь (названия продуктов, «страховка», «вклад», «ПДС», «ИСЖ», «НСЖ») передаётся грамматикой для повышения точности ключевых слов.
- `browser` — Web Speech API (`SpeechRecognition`, ru-RU, `interimResults`) на стороне клиента; результаты уходят на сервер как уже готовые реплики. Внешний сервис распознавания (данные уходят вендору браузера), поэтому выключен по умолчанию и помечен бейджем «внешний STT».
- `salutespeech` — потоковое двухканальное распознавание gRPC v2 (до 2 каналов в реальном времени); доступно только при наличии доступа юридического лица — подключение физлиц и тариф Freemium прекращены с 15 июля 2026 года; профиль присутствует в настройках как опция для корпоративного контура.
- `openai_compatible_audio` — любой сервер с `/v1/audio/transcriptions` (faster-whisper, whisper.cpp-server и т. п.) в режиме псевдо-потока (чанки по 2–3 с); для демо не рекомендуется из-за задержки.
Один и тот же провайдер и клиентский компонент захвата (`<VoiceInput>`: кнопка микрофона, индикатор уровня, частичный текст серым, финальный — в поле) используются и для аудиомониторинга (22), и для «надиктовать жалобу» (12.2 экран 7, лендинг 11): во втором случае это одноканальная сессия без ролей и детектора, результат — просто текст в поле формы. Выбор провайдера — в мастере (шаг 4) и в `/settings → Аудио`; все метрики (задержка partial/final, доля финалов, WER на предзаписанных файлах с эталонным текстом) пишутся в `stt_metrics` и показываются на экране бенчмарков.

### 5.4 Режим подстраховки: кассеты `replay` и предзаписанные входы [BRD]

Назначение: показ должен состояться при отсутствии интернета в зале, падении API GigaChat/OpenRouter или проблемах с микрофоном (NFR BRD). Три слоя:
1. **Кассеты LLM** (`data/cassettes/<scenario>.jsonl`): во время репетиции при включённом флаге `LLM_RECORD=1` каждый вызов LLM (включая потоковые чанки с таймингами, tool calls, usage, `model`) записывается с ключом `sha256(provider, model, normalized_messages, schema)`. Провайдер `replay` (5.2) воспроизводит ответ с исходной скоростью токенов; в трассировке шаг помечен `source = replay`, а в футере экранов — тихий бейдж «офлайн-кассета от <дата>», чтобы не вводить зрителя в заблуждение (принцип 1.4 «всё эмулируемое помечено»). Кассеты — это ответы реальных моделей, поэтому экран «Под капотом» остаётся честным.
2. **Предзаписанные аудио** (`data/audio/<scenario>/*.wav`, 16 кГц): проигрываются в тот же STT-конвейер, что и микрофон (сервер читает файл чанками в реальном темпе), так что распознавание — настоящее и офлайн (Vosk); для каждого файла хранится эталонный транскрипт с ролями и таймкодами (`*.ref.json`) — он используется, если STT недоступен, и для расчёта WER.
3. **Скрытая кнопка**: горячая клавиша `Ctrl+Shift+R` (и длинное нажатие на логотип в шапке) открывает меню демонстратора: «Опубликовать отзыв сценария 8», «Проиграть диалог сценария 9 (аудио / транскрипт)», «Переключить LLM → replay», «Переключить STT → файл», «Вернуть всё в онлайн». Меню не видно в обычном режиме и не попадает в скриншоты README.
Правила: кассеты и аудио коммитятся в репозиторий (размер контролируется, ≤ 50 МБ суммарно); `install.sh --offline` автоматически выбирает `replay → mock` для LLM и `vosk` для STT; автотесты сценариев 8–9 прогоняются на кассетах.

## 6. Поток обработки сигнала (end-to-end)

1. Приём: событие канала → `signals` (сырой текст, канал, время, метаданные; для идентифицированных — `client_id`, для неидентифицированных — контакт/ник).
2. Нормализация (быстрая модель): язык, краткое содержание, извлечение сущностей (продукт, сумма, дата операции, упоминание ухода/суда/регулятора/мошенничества).
3. Идентификация клиента: по `client_id`, иначе попытка матчинга по контактам (телефон/e-mail из профиля) — только синтетика; **[BRD]** для внешних площадок — по косвенным данным: ник автора (`clients.social_handles`), маскированный номер карты `**** 4512` (`client_products.card_last4`), маскированный телефон `+7 9** *** 12-34`, город/продукт из текста как уточняющие признаки; результат — список кандидатов с уверенностью (точное совпадение ника или ник + last4 → ≥ 0,9; только last4 → неоднозначно); при одном кандидате ≥ 0,8 клиент считается идентифицированным, при нескольких — агент задаёт уточняющий вопрос в личном канале или отправляет в HITL; при неудаче — статус «неидентифицированный».
4. Сбор контекста (инструменты): профиль и сегмент, продукты, операции за окно (по умолчанию 72 сим-часа), логи систем за окно по пути операции, прошлые сигналы/инциденты (90 дней), открытые инциденты с тем же кодом ошибки/продуктом/регионом (для связывания), риск ухода.
5. Классификация (основная модель, JSON): тип сигнала, продукт, система-источник, гипотеза причины (`tech_fault` / `client_error` / `tariff_terms` / `service_quality` / `fraud_suspicion` / `info_request` / `gratitude` / `suggestion` / `legal_regulatory`), тональность и признаки сарказма/агрессии, риск ухода 0–100, уверенность 0–1, обоснование (2–4 предложения на русском).
6. Решение: сложность, критичность, SLA (матрица раздела 8), приоритет очереди, маршрут (команды), действие по клиенту (ответ/шаблон/канал), необходимость HITL (раздел 10), связать с существующим инцидентом или создать новый.
7. Исполнение инструментами: `create_incident` / `link_signal_to_incident` / `notify_client` / `notify_team` / `create_task(gift|callback|manual_review)` / `request_human_decision` / `schedule_followup` / **[BRD]** `check_business_rules` / `refund_fee` / `publish_public_reply` / `find_affected_clients`.
7a. **[BRD]** Быстрый путь (fast path, 21.4): если на шаге 4 найдена операция-триггер и `check_business_rules` вернул подтверждённое нарушение с готовым действием (например, `RULE-QR-FEE-001 → refund`), а политики 9.3 разрешают автономию, то шаги 5–8 схлопываются в один вызов основной модели (классификация + решение + текст ответа в одном structured output) и немедленное исполнение: `refund_fee` → `create_incident(type='fee_refund', status='resolved')` → `publish_public_reply` + `notify_client` → `verify_service_delivered` (баланс восстановлен) → `close_incident` → `gift` по справочнику. Параллельно агент проверяет массовость (`find_affected_clients` по тому же коду ошибки за окно) и при ≥ N пострадавших открывает отдельный инцидент `tech_fault` в `team_processing` с предложением массового возврата — массовый возврат всегда через HITL.
8. Контроль: подписка на события команды → при «фикс внедрён» агент запускает `verify_service_delivered` (эмуляция: повторная операция клиента проходит успешно) → закрытие инцидента → уведомление клиента → задача на подарок (сумма по сегменту и критичности) → обновление метрик.
9. Проактивная ветка: `fault.*` без жалобы → агент определяет затронутых клиентов → превентивное уведомление («видим проблему, устраняем») → инцидент в команду подсистемы и в CX → после фикса — приглашение продолжить оформление.

## 7. Классификатор сигналов

| Код | Тип | Базовая критичность | Примеры |
|---|---|---|---|
| `tech_fault` | Технический сбой | средняя→высокая при массовости | ошибка при открытии вклада, зависший платёж, двойное списание |
| `client_error` | Ошибка/непонимание клиента | низкая | ожидал промо-ставку после окончания акции, неверные реквизиты |
| `tariff_terms` | Претензия к тарифам/условиям | средняя | комиссия «необоснованная», ставка не та |
| `service_quality` | Качество обслуживания | средняя | грубость оператора, очередь в ВСП |
| `fraud_suspicion` | Подозрение на мошенничество | высокая | звонок «из службы безопасности», неизвестное списание |
| `legal_regulatory` | Судебный/налоговый/регуляторный сигнал | высокая, HITL | иск, арест счёта, жалоба в ЦБ |
| `churn_intent` (флаг) | Намерение уйти | повышает приоритет | «закрою все счета», «ухожу в другой банк» |
| `info_request` | Запрос информации | низкая | график платежей, тарифы |
| `gratitude` | Благодарность | — | спасибо сотруднику |
| `suggestion` | Предложение | — | добавить лимиты в приложении |
| `repeat` (флаг) | Повторное обращение | повышает критичность на ступень | второй сигнал по той же причине за 14 дней |

Флаги `churn_intent`, `repeat`, `sarcasm`, `aggression`, `mass_impact` (связано ≥ N клиентов) модифицируют решение.

**[ДТЗ] Трёхклассная тональность (FR-2.1).** В `normalization` и `classification` добавлено поле `sentiment` ∈ {positive, neutral, negative}: модель выводит его напрямую, а сервис сверяет с порогами `negativity` (≤ 33 → positive, 34–66 → neutral, ≥ 67 → negative); расхождение логируется и считается метрикой согласованности. Поле `tone` (6 значений) сохраняется как более тонкая характеристика для выбора шаблона ответа; `sentiment` — внешняя метка для карты, ленты и бенчмарка. Целевая точность ≥ 80 % на наборе `sentiment_v1` (300 текстов всех каналов, 100/100/100 по классам, с сарказмом и сленгом в 20 % примеров) для основного провайдера; mock-провайдер оценивается тем же набором без требования порога.

**[ДТЗ] Скрытый негатив (FR-2.2).** Объект `hidden_negativity` в `normalization`: `sarcasm`, `passive_aggression`, `churn_threat` — каждый с `present`, `confidence`, `evidence_ru` (дословная подстрока). Детектор — few-shot промпт `prompts/v1/hidden_negativity.md` с ≥ 12 размеченными примерами на класс («спасибо, что списали комиссию, очень удобно», «ну да, конечно, разберётесь, как всегда», «подскажите, как закрыть все счета») и контрпримерами; вызывается в узле `normalize` той же быстрой моделью одним запросом с нормализацией. Результат поднимает флаги `sarcasm`, `passive_aggression` (новый), `churn_intent`, корректирует `negativity` (сарказм при формально позитивном тексте → не ниже 60) и участвует в политике эскалации (9.3). Набор `hidden_negativity_v1` (120 примеров) — метрики precision/recall по классам.

**[ДТЗ] Саммари проблемы (FR-2.3).** Объект `problem_summary` в `classification` с полями ровно по ДТЗ: `problem` (≤ 2 предложения, ≤ 300 символов, без ПДн), `severity` ∈ {low, medium, high, critical}, `suggested_team` (код команды). Отображение на внутреннюю модель: `low/medium/high` = `criticality`; `critical` = `criticality = high` плюс один из признаков — `regulator_threat`, `fraud_suspicion` с суммой > 50 000 ₽, `mass_impact`, `churn_threat` для vip/ultra_vip — и всегда влечёт `needs_human`. `suggested_team` сверяется с маршрутом решения: расхождение показывается на панели «ИИ против правил». Валидация числа предложений — в коде (разбиение по `.!?`), при нарушении — повторный запрос с указанием ошибки (не более одного ретрая), затем усечение.

**[BRD] Шкала негатива и сущности нормализации.** Схема `normalization` дополняется полями: `negativity` 0–100 (уровень негатива; 0 — благодарность, 50 — нейтральная претензия, ≥ 80 — агрессия/угроза ухода), `intents[]` (`churn_threat`, `refund_request`, `complaint`, `question`, `public_shaming`, `regulator_threat`), `entities` {`amount_rub`, `product`, `operation_hint` (QR-оплата, перевод, снятие), `date_hint`, `error_text`}, `contacts_hint` {`nickname`, `masked_phone`, `masked_card_last4`, `city`}. Существующие `tone`/`churn_risk` сохраняются: `negativity` — про текст, `churn_risk` — про клиента с учётом контекста; оба показываются на панели Log в процентах. Для mock-провайдера `negativity` считается по словарю с весами, для LLM — полем structured output; расхождение > 30 пунктов между ними подсвечивается на панели «ИИ против правил».

## 8. Модель инцидента

### 8.1 Классы и шкалы
- Сложность: `easy` лёгкий (конфигурация, ответ клиенту, перезапуск), `medium` средний (фикс в одной подсистеме), `hard` сложный (несколько систем/команд, миграция данных).
- Критичность: `low` / `medium` / `high`. Повышается при флагах `repeat`, `mass_impact`, `churn_intent`, сегментах vip/ultra_vip, `legal_regulatory`, `fraud_suspicion`.
- Тип `account_closure` (закрытие обслуживания): внутренний инцидент для разбора ухода клиента, создаётся моделью поведения (4.5), не требует ответа клиенту, участвует в экономике как реализованная потеря.
- **[BRD]** Сложность `instant` (мгновенный): нарушение подтверждено бизнес-правилом и устраняется инструментом агента без участия команды (возврат комиссии, корректировка уведомления). Жизненный цикл проходится за один запуск агента: `new → classified → resolved → verifying → closed`; SLA измеряется в секундах реального времени (цель ≤ 10 с), команда-владелец системы получает инцидент *постфактум* как уведомление о дефекте.
- **[BRD]** Тип `fee_refund` (возврат ошибочной комиссии): всегда `instant`, несёт ссылки на операцию, проводку возврата и правило; сумма, превышающая лимит автономии, переводит инцидент в `awaiting_human`.
- **[BRD]** Тип `misselling` (нарушение практик продаж в отделении): создаётся контуром аудиомониторинга при достижении порога (22.5); команда `team_compliance`, сложность `medium`, критичность `high` (сегмент клиента и сумма сделки могут повышать до обязательного HITL); обязательные поля: сотрудник, отделение/стол, сессия, список триггеров с цитатами и уверенностью, рекомендация (стоп-продажа, переобучение, отмена договора); ответ клиенту формируется только после решения человека (руководителя отделения).
- Приоритет очереди P1–P4 = f(критичность, риск ухода, множитель сегмента, повторность) — влияет на порядок в ленте и время первого ответа, но не на срок фикса.

### 8.2 Матрица SLA (рабочие дни на устранение)
| Сложность \ Критичность | Высокая | Средняя | Низкая |
|---|---|---|---|
| Мгновенный **[BRD]** | ≤ 10 с реального времени (p50), ≤ 15 с (p95) — не рабочие дни | — | — |
| Лёгкий | 1 | 2 | 3 |
| Средний | 3 | 4 | 5 |
| Сложный | 5 | 5 (+ обязательный промежуточный отчёт на 3-й день) | до 10 (+ обязательные промежуточные отчёты на 3-й, 6-й и 9-й день) |

Решение заказчика: для сложных некритичных инцидентов окно до 10 рабочих дней с обязательными промежуточными отчётами. Промежуточный отчёт — артефакт `progress_report` (раздел 8.4), который команда-исполнитель обязана опубликовать к контрольной дате; отсутствие отчёта к сроку автоматически порождает событие `sla.report_missing`, предупреждение в ленте CX и напоминание команде от агента; второе пропущенное напоминание — эскалация руководителю CX. Матрица редактируется в настройках (таблица `sla_matrix`), контрольные дни отчётов задаются списком.

Отдельно: SLA первого ответа клиенту — по сегменту (раздел 3.1); SLA «взято в работу командой» — 2 сим-часа для high, 4 для medium, 8 для low. Контрольные точки: предупреждение при 25 % остатка, эскалация при 0 % (руководитель CX + бейдж «SLA истёк»). Для инцидентов длительностью свыше 5 дней клиент получает промежуточное уведомление о ходе работ одновременно с каждым отчётом команды (шаблон `progress_update`).

### 8.3 Жизненный цикл
`new` → `classified` → `routed` (направлен в команду) → `in_progress` (у команды) → `fix_proposed` (есть RCA и решение о внедрении) → `fix_deployed` → `verifying` (проверка услуги клиенту) → `resolved` → `closed`.
Боковые состояния: `awaiting_human` (HITL), `awaiting_client` (нужны данные от клиента), `escalated`, `duplicate`, `rejected`. Любая смена статуса пишется в `incident_status_history` с актором (агент / человек / команда) и причиной.

### 8.4 Цифровой след команды (эмуляция)
Артефакты инцидента, создаваемые командой-исполнителем: `rca` (анализ первопричины), `fix_decision` («Решение о внедрении фикса №…», с рисками и планом), `progress_report` (промежуточный отчёт для длинных инцидентов: сделано / осталось / риски / новый прогноз), `release_note` (релиз/хотфикс, версия, время), `verification_report`. Генерируются LLM по шаблону или из заготовок (для mock-режима), хранятся в `incident_artifacts` и показываются во вкладке «Документы» карточки инцидента.

### 8.5 Извинительный подарок (справочник от бизнеса)
После `resolved` агент создаёт `tasks(kind='gift')` с предложением из справочника `gift_catalog`; задача попадает в список «Подарки» CX для подтверждения (HITL для VIP/Ultra VIP и при выборе привилегий партнёров).

| Код | Подарок | Кому доступен | Правило выбора |
|---|---|---|---|
| `bonus_points` | Бонусные баллы программы лояльности, 300–1 000 баллов | все сегменты | базовый подарок; размер = 300 (низкая критичность) / 600 (средняя) / 1 000 (высокая); +200 при повторном обращении, потолок 1 000 |
| `lounge_pass` | Дополнительное бесплатное посещение бизнес-зала аэропорта | vip, ultra_vip | при критичности средняя/высокая |
| `restaurant_special` | Особое обслуживание в элитном ресторане-партнёре | vip, ultra_vip | при высокой критичности или `churn_intent` |
| `business_class_discount` | Скидка на бизнес-класс в самолёте от партнёра | vip, ultra_vip | при высокой критичности и `churn_intent`; для ultra_vip — только после подтверждения человеком |
| `personal_call` | Персональный звонок сотрудника CX/менеджера | social, vip, ultra_vip | дополнение к любому подарку |

Для VIP и Ultra VIP агент предлагает бонусы плюс одну привилегию; сотрудник CX может заменить привилегию в карточке задачи. Все названия партнёров в данных — вымышленные.

## 9. ИИ-агент CX: граф и инструменты

### 9.1 Граф (LangGraph)
`ingest → normalize → identify_client → gather_context → check_rules → [fast_path? → act_instant → verify → close → gift] | classify → decide → [needs_human? → wait_human] → act → followup_monitor → verify → close → gift`.
**[BRD]** Узел `check_rules` (9.6) и ветка `act_instant` добавлены для быстрого пути: условное ребро после `gather_context` выбирает ветку по результату правил и политик (21.4); обе ветки пишут одинаковые шаги в `agent_steps`, поэтому «Под капотом» показывает их на одном графе с подсветкой выбранного маршрута. Контур аудиомониторинга (22) не использует этот граф: детектор мисселлинга — отдельный потоковый конвейер `compliance/`, который при достижении порога создаёт инцидент `misselling` и уже он попадает в стандартный граф на узел `decide` (маршрут, HITL руководителя, уведомления).
Каждый узел пишет шаг в `agent_steps` (вход, выход, промпт, ответ модели, tool calls, токены, латентность). Чекпоинт состояния — в PostgreSQL (LangGraph checkpointer), чтобы отложенные обращения и HITL переживали перезапуск.

### 9.2 Инструменты (function calling)
`get_client_profile`, `get_client_products`, `get_recent_operations`, `get_system_logs`, `find_related_incidents`, `search_similar_signals`, `create_incident`, `link_signal_to_incident`, `update_incident`, `notify_client(channel, template, vars)`, `notify_team`, `create_task`, `request_human_decision(options, recommendation)`, `schedule_followup(when)`, `verify_service_delivered`, `close_incident`; **[BRD]** `match_client_by_hints(contacts_hint) → candidates[]`, `check_business_rules(operations[], context) → violations[]`, `refund_fee(operation_id, amount_rub, rule_id, reason) → ledger_entry` (идемпотентен по `correlation_id`, проверяет лимит автономии и наличие проводки комиссии, пишет `abs.refund_posted`), `publish_public_reply(post_id, text, link_to_dm)` (публикует ответ под постом эмулятора площадки и помечает пост «отвечено»), `find_affected_clients(error_code, window)` (для оценки массовости и предложения массового возврата), `get_account_balance(client_id)`.
Каждый инструмент валидируется схемой и логируется; побочные эффекты только через инструменты (никаких «скрытых» записей).

**[ДТЗ] Роутер-инструменты (FR-3.1–3.4).** Поверх внутренних инструментов агент получает четыре инструмента с именами и сигнатурами из дополнительного ТЗ — именно их модель видит первыми в списке функций, они же показываются зрителю на панели Log:
- `route_to_department(department, priority, summary)` — создаёт тикет в тикетнице: фасад над `create_incident` + маршрутизацией; `department` — код команды (`teams.code`, синонимы из ДТЗ «департамент» разрешаются по справочнику), `priority` 1–4, `summary` → `incidents.summary` и `problem_summary`; возвращает `ticket_id` (= `incidents.public_id`). При уже существующем инциденте по дедупликации — линкует и возвращает его `ticket_id` (поле `linked = true`).
- `notify_customer(channel, message)` — отправляет клиенту подтверждение «инцидент взят в работу» или иной текст: фасад над `notify_client` без шаблона; текст проходит те же проверки (ПДн, запрещённые обещания); доставка эмулируется (запись в `notifications`, строка в логе, бейдж «эмуляция»; для Telegram-бота — реальная отправка).
- `escalate_to_manager(reason, severity)` — создаёт запись `escalations` (руководитель CX или руководитель отделения — по контексту), ставит элемент в очередь руководителя (HITL с типом `escalation`), шлёт уведомление в топик `hitl` и опционально в Telegram; возвращает `escalation_id`. Обязателен по политике 9.3 при критическом негативе и повторном обращении.
- `request_clarification(question, channel)` — задаёт клиенту уточняющий вопрос и переводит сигнал в `awaiting_client` с `followup`; фасад над `client_action.kind = request_data` + `schedule_followup`.
Внутренние инструменты (`create_incident`, `notify_client`, `request_human_decision`, …) остаются доступны модели для остальных действий; в трассировке фасад и вложенный вызов показываются как один шаг с раскрытием. Решение агента дополнено полем `router_action` ∈ {route, escalate, request_clarification, none} — обязательный «ответ в терминах ДТЗ», который должен быть согласован с фактическими вызовами (проверка в `policy_checks`).

### 9.3 Политики принятия решений (конфигурируемые)
- Порог уверенности для автономного действия: 0.75 (ниже — HITL).
- Обязательный HITL: ultra_vip; `legal_regulatory`; `fraud_suspicion` с суммой > 50 000 ₽; подарок с привилегией партнёра (бизнес-зал, ресторан, бизнес-класс) и любой подарок для ultra_vip; повторная жалоба 3+; конфликт классификаций между моделью и rule-based.
- Дедупликация: один инцидент на (код ошибки, система, окно 4 сим-часа); новые сигналы линкуются и повышают `mass_impact`.
- Тон ответа клиенту: по сегменту и каналу; запрещённые формулировки (нет обвинений клиента, нет обещаний сроков, не предусмотренных SLA).
- **[BRD]** Автономный возврат (`refund_fee`): разрешён, если одновременно (а) бизнес-правило подтвердило нарушение (9.6), (б) сумма ≤ `policies.refund_autonomy_limit_rub` (по умолчанию 5 000 ₽; для vip/premium — 15 000 ₽, для ultra_vip — всегда HITL), (в) уверенность идентификации клиента ≥ 0,8 и классификации ≥ 0,75, (г) по этой операции ещё не было возврата (идемпотентность), (д) клиент не в списке «подозрение на злоупотребление» (≥ 3 возвратов за 30 дней → HITL). Иначе — `request_human_decision` с готовым предложением; массовый возврат (≥ `mass_refund_threshold`, по умолчанию 10 клиентов) — всегда HITL.
- **[BRD]** Публичный ответ (`publish_public_reply`): без персональных данных и номеров карт/счетов, можно упоминать сумму и факт возврата, если их назвал сам автор; обязательны извинение, факт/сроки возврата, приглашение в личный канал; запрещены обещания вне SLA и обвинения. Для `negativity ≥ 80` и сегментов premium+ — ответ дополнительно отправляется в личный канал.
- **[ДТЗ]** Обязательная эскалация (`escalate_to_manager`): `hidden_negativity.churn_threat.present` или `intents ∋ churn_threat` при `negativity ≥ 80`; флаг `repeat` (второй сигнал по той же причине за 14 дней) при `sentiment = negative`; `problem_summary.severity = critical`; три и более обращения любого содержания за 7 дней. Эскалация не отменяет маршрутизацию: тикет создаётся всегда, эскалация добавляется сверху. Руководитель видит очередь эскалаций на вкладке HITL с фильтром «Эскалации».
- **[ДТЗ]** Уточнение (`request_clarification`): при уверенности классификации < 0,6 или отсутствии обязательных сущностей (сумма/продукт для `tariff_terms`, `tech_fault`) агент задаёт один вопрос; второй подряд вопрос запрещён — далее маршрутизация с пометкой «данных недостаточно».
- **[BRD]** Мисселлинг: порог алерта `compliance.alert_threshold` (по умолчанию 3 за сессию), категории и их веса настраиваются (22.4); алерт создаётся немедленно (без HITL), а инцидент `misselling` требует подтверждения руководителя отделения перед любыми действиями по клиенту; при уверенности детектора < 0,6 триггер помечается «предварительно» и не входит в счётчик, пока LLM не подтвердит.

### 9.4 Промпты
Системный промпт агента (роль, политика банка, формат JSON), промпты классификации, ответа клиенту, эмуляции команд — в `prompts/*.md` с версионированием; версия промпта фиксируется в трассировке для бенчмарков.

### 9.5 Отложенные обращения (второй базовый сценарий команды)
Очередь `deferred`: сигналы, по которым агент ждёт данных (от клиента, от команды) или наступления времени (например, окончания акции). Планировщик будит граф по `schedule_followup`. UI показывает «спящие» обращения с причиной ожидания и датой пробуждения.

### 9.7 Тикетница, эскалации и цепочка решений [ДТЗ]
**Тикетница (FR-3.2).** Дополнительное ТЗ допускает in-memory/SQLite; в проекте тикеты — это инциденты в PostgreSQL (одно хранилище, изоляция по `run_id`, экономика, SLA). Для внешнего контракта заведено представление `v_tickets` (ticket_id, department, priority, summary, status ∈ open | in_progress | resolved | closed | rejected — отображение статусов инцидента, channel, client_segment, region_code, created_at, escalated, agent_run_id) и `GET /api/tickets` с фильтрами; на рабочем месте — вкладка «Тикеты» (та же доска инцидентов в терминах ДТЗ, переключатель «Инциденты / Тикеты»).

**Эскалации (FR-3.4).** Таблица `escalations` (incident_id, signal_id, reason, severity, to_role ∈ cx_lead | branch_manager, status ∈ open | acknowledged | resolved | dismissed, created_by agent | human, acknowledged_by, resolution_ru); события `escalation.created/acknowledged/resolved`; метрика «доля эскалаций и их обоснованность» на дашборде.

**Цепочка решений (FR-3.5).** `GET /api/agent/runs/{id}/decision-chain` возвращает компактную последовательность шагов: `{step, node, tool, args (с маскировкой), result_brief, why_ru}` — `why_ru` берётся из `rationale_ru` соответствующего узла и `human_recommendation`; формат JSON и Markdown (`?format=md`) для копирования в отчёт жюри. Та же цепочка — панель Log (12.6) и экран «Под капотом» (12.5); в карточке тикета — кнопка «Почему так решили».

### 9.6 Детерминированные бизнес-правила (Rules Engine) [BRD]

Назначение: требование BRD FR 1.4 («если оборот выполнен по QR-коду, но комиссия списана → ошибка системы → инициировать возврат») — это детерминированная проверка, которую нельзя доверять только LLM. Поэтому между сбором контекста и решением добавлен узел `check_rules`: чистые функции над операциями/проводками/тарифами, объявленные в таблице `business_rules` (код, название, условие в декларативном DSL на JSON-логике или Python-предикате в `app/rules/`, действие, лимиты, владелец-команда, активность).

| Код | Условие | Действие агента | Владелец дефекта |
|---|---|---|---|
| `RULE-QR-FEE-001` | `operation.kind = 'payment' AND operation.method = 'qr_sbp' AND ledger.fee_amount > 0 AND tariff.qr_fee = 0` | `refund_fee(fee_amount)` + ответ клиенту; дефект `PROC-QR-FEE-CHARGED` в `team_processing` | processing |
| `RULE-DOUBLE-DEBIT-001` | две проводки `debit` с равной суммой и мерчантом в окне 120 с | `refund_fee(duplicate)`; дефект `PROC-DOUBLE-DEBIT` | processing |
| `RULE-PROMO-RATE-001` | вклад открыт в окне действия акции, ставка в договоре ≠ промо | предложение сохранить промо-ставку — только через HITL (как в сценарии 1) | promo |
| `RULE-NOTIF-DUP-001` | ≥ 3 одинаковых уведомлений за 10 мин | извинение + подавление дублей; дефект `NOTIF-DELAY` | notifications |

Правила возвращают `violations[] = {rule_id, evidence (ids операций/проводок), proposed_action, amount, confidence = 1.0}`. LLM получает их как факт в контексте и обязан сослаться на правило в обосновании; если LLM предлагает возврат без подтверждённого правила — это конфликт классификаций (9.3) и HITL. На панели «ИИ против правил» (12.5) правила показываются как третья колонка: что увидели правила, что увидела модель, что сделал агент. Правила редактируются в `/settings → Правила` и версионируются (хеш в трассировке).

## 10. Human-in-the-loop

Очередь «Требует решения» в рабочем месте CX. Карточка HITL содержит: сигнал, контекст, предложение агента (классификация, маршрут, текст ответа клиенту), варианты действий (Принять / Изменить / Отклонить / Передать коллеге), поле причины. Решение человека записывается в `human_decisions`, возвращается в граф и используется как few-shot пример для похожих сигналов (поиск по эмбеддингам или по ключам тип+продукт+система). Метрика: доля HITL, среднее время решения человека, доля изменённых предложений агента.

## 11. Лендинг и трекинг для неидентифицированного клиента

- `/claim` — публичная страница в едином стиле: форма (имя/как обращаться, телефон или e-mail, регион/город — выбор из справочника, продукт — выбор, текст обращения, согласие на обработку), простая антибот-проверка (арифметика). Без ПДн в демо: подсказка «используйте вымышленные данные».
- **[BRD]** Рядом с полем текста — кнопка «Надиктовать»: голос с микрофона транскрибируется потоково (5.3), текст появляется в поле и редактируется до отправки; подпись «распознано офлайн-движком, проверьте текст»; при недоступности микрофона (http без localhost) кнопка скрыта с подсказкой. Сигнал получает `origin = 'voice_input'` и сохраняет исходный транскрипт.
- После отправки: номер обращения, ссылка `/track/<token>` (token — случайная строка 24+ символов), QR-код для показа на демо.
- `/track/<token>` — таймлайн: получено → взято в работу агентом → классификация (понятным языком) → инцидент создан и направлен в команду X → ответ/решение → закрыто; кнопка «Дополнить обращение». Уведомления дублируются в центр уведомлений и (если включён Mailpit) письмом.
- Агент самостоятельно формирует инциденты по таким обращениям, собирает решения и информирует клиента на странице трекинга.

### 11.3 Telegram-бот для финала (реальный канал)
Решение заказчика: на демо уведомления эмулируются; для финала даётся QR-код на собственного Telegram-бота команды, через который жюри проходит сценарий потенциального/неидентифицированного клиента.
- Реализация: сервис `tgbot` (Python, aiogram — MIT) в long-polling режиме, чтобы не требовать входящих портов за VPN/Caddy; бот создан техлидом и принадлежит ему: `@CXPulseControlBot` (https://t.me/CXPulseControlBot), токен хранится только в `.env` (`TELEGRAM_BOT_TOKEN`) и вводится в мастере/настройках; при пустом токене или в режиме `--offline` сервис не запускается, остальное приложение не зависит от него.
- Сценарий бота: `/start` → приветствие и выбор «Я клиент банка / Я ещё не клиент» → свободный текст проблемы → уточнение контакта и региона (кнопки-подсказки) → создание сигнала канала `telegram_bot` → ответ с номером обращения и ссылкой `/track/<token>`. Далее агент может задать уточняющий вопрос через бота (`awaiting_client`), а все смены статуса инцидента и финальный ответ приходят сообщениями в чат. Диалог сохраняется в `signals`/`notifications` и виден в карточке инцидента.
- QR-код на бота генерируется приложением (`qrcode`, BSD) и показывается на экране «Жюри-режим» и в README.
- Ограничения: Telegram Bot API — внешний опциональный сервис, явно вынесенный за правило «без внешних зависимостей»; никаких ПДн не сохраняется, кроме того, что пользователь сам ввёл для демонстрации, с предупреждением «используйте вымышленные данные».

### 12.3 Реальное время
WebSocket `/ws/stream` с темами `signals`, `agent`, `agent_tokens` (потоковые токены рассуждений), `incidents`, `notifications`, `sim`, `db`, `runs`, **[BRD]** `feed` (посты и публичные ответы), `abs` (проводки и балансы), `compliance` (реплики, триггеры, алерты, состояние сессии), `stt` (частичные результаты распознавания). ### 12.4 Локализация
Русский — основной язык интерфейса, английский — дополнительный, переключатель в шапке (react-i18next, MIT; словари `frontend/src/locales/{ru,en}.json`). ### 12.5 Как доказать жюри, что работает ИИ, а не каскад if/elif (рекомендация архитектора)
Цель экрана «Под капотом» — сделать невозможным объяснение поведения системы детерминированными правилами. Показываем граф, его выполнение, рассуждения и ответы модели, изменения в БД (как и задумывал заказчик) и добавляем пять приёмов, каждый из которых по отдельности правила воспроизвести не могут:
1. Потоковые рассуждения в реальном времени. Токены ответа модели появляются в карточке шага по мере генерации (streaming из API), с пометкой модели и провайдера из поля `model` ответа; рядом — счётчики prompt/completion-токенов и латентность, которые совпадают с данными в личном кабинете провайдера. Правила не «печатают» ответ по токенам и не имеют токенов.
2. Реальные вызовы инструментов, сгенерированные моделью. Блок `tool_calls` показывает JSON-аргументы, которые модель составила сама (например, `create_incident` с заголовком и обоснованием, написанными моделью), а затем — результат исполнения и записи, появившиеся в БД (вкладка «Данные в БД» подсвечивает те же строки по id). Связь «текст модели → побочный эффект в таблице» видна на одном экране.
3. «ИИ против правил» на одном сообщении (панель (g)). Жюри вводит произвольный текст, и приложение одновременно прогоняет его через LLM и через mock-классификатор, показывая оба результата рядом: правила спотыкаются о сарказм, иронию, опечатки, косвенные формулировки («ну спасибо, что опять списали дважды, пойду в другой банк»), смешанные темы и неявные намерения; модель объясняет, почему она так решила. Это самый наглядный контраст — сохранять прогоны как «кейсы для защиты».
4. Диалог с агентом об инциденте. В карточке инцидента есть чат «Спросить агента»: «почему критичность высокая?», «что изменится, если клиент — массовый сегмент?», «перепиши ответ клиенту мягче». Агент отвечает в контексте инцидента и может применить изменение через инструмент (с записью в историю статусов). Контрфактические вопросы правила не поддерживают.
5. Переключатель модели «на лету» и бенчмарки. Жюри переключает профиль (GigaChat-3-Ultra → Lightning → OpenRouter-free → mock) и повторяет то же сообщение: формулировки обоснования, уверенность и иногда решение меняются, а на экране бенчмарков видно, что метрики различаются по моделям. Детерминированный код давал бы один и тот же ответ.
Политика раскрытия промптов: системные промпты и сырые ответы модели показываются полностью (режим «эксперт», включён по умолчанию для защиты); в настройках есть тумблер «скрывать системные промпты», оставляющий только структурированные шаги — на случай публичной демонстрации. Риск утечки промпт-инжиниринга для хакатона считаем приемлемым: открытость — часть доказательства.
Дополнительно: пометка «эмуляция» на действиях команд и систем, чтобы жюри различало, где работает ИИ-агент CX, а где — симулятор банка; версия промпта и хеш конфигурации печатаются в футере трассировки для воспроизводимости.

**[ДТЗ]** Экспорт цепочки решений: на экране «Под капотом» и в карточке тикета — кнопка «Цепочка решений» (`GET /api/agent/runs/{id}/decision-chain`), показывающая последовательность «инструмент → аргументы → почему» в терминах ДТЗ (route_to_department, notify_customer, escalate_to_manager, request_clarification) с раскрытием внутренних вызовов.

### 12.6 Панель «Log/Debug» на демо-экранах [BRD]

Требование BRD: зрители должны видеть, как «думает» ИИ, не уходя с демо-экрана. На `/feed`, `/compliance`, `/manager` и в карточке инцидента внизу есть сворачиваемая панель Log (по умолчанию развёрнута в режиме показа): хронологическая лента шагов текущей обработки с реальными метками времени и задержкой каждого шага (мс), для каждого шага — модель/провайдер, уверенность в процентах, извлечённые сущности в виде компактного JSON с подсветкой синтаксиса, сработавшие бизнес-правила с доказательствами (ссылки на операции/проводки), вызовы инструментов и их результат, ссылки «открыть в "Под капотом"». Панель — это тот же поток `agent`/`compliance` из WebSocket, что и экран `/engine`, только в компактном виде; тумблер «скрывать системные промпты» (12.5) действует и здесь. Для C-level рядом с техническими полями выводится «бизнес-строка»: что произошло для клиента и банка («возвращено 450 ₽, риск оттока снижен с 78 % до 21 %, предотвращённая потеря 1 823 ₽»).

### 12.7 Меню демонстратора и режим подстраховки [BRD]

Скрытое меню (`Ctrl+Shift+R` или длинное нажатие на логотип, 5.4): статус сети и провайдеров (LLM, STT, Telegram) с цветными индикаторами; переключатели «LLM: онлайн / replay / mock», «STT: микрофон / файл / транскрипт»; кнопки запуска предзаписанных входов для сценариев 8 и 9; «Сбросить сценарий к baseline» (4.6); «Открыть `/manager` на телефоне» (QR). Все переключения логируются в `sim_events` (`demo.failover`), а в футере появляется тихий бейдж текущего режима — зритель видит честную пометку, но без «кричащих» уведомлений. Автоматический failover: при ошибке/таймауте LLM > 8 с на быстром пути агент сам переключается на `replay → mock` и продолжает цепочку (16.4).

Локальные модели не запускаются, но любой внешний OpenAI-совместимый URL можно добавить как профиль. Раннер прогоняет набор с одинаковыми промптами и температурой 0 (где поддерживается), соблюдает rate-limit профиля, ведёт учёт токенов по ключам GigaChat (бюджет 50 млн на ключ) и показывает прогноз расхода до старта; результаты — таблица и графики на экране «Бенчмарки», экспорт CSV/JSON, фиксация версии промпта, seed и id модели. Критерии защиты из PDF отображаются первыми. Повторяемость: каждый кейс можно прогнать 3 раза для оценки стабильности (по умолчанию выключено из-за лимитов).

### 14.4 Экономический эффект (методика калькулятора dCLTV)
Используется формула и ставки из калькулятора бизнеса (раздел 0.4), чтобы цифры на дашборде совпадали с расчётами Елены:

Потенциальная потеря инцидента (₽) = Пострадавшие × Доля детракторов × Доля невозврата × Ставка dCLTV

- Пострадавшие — число клиентов, затронутых сбоем/инцидентом (из `faults.impact_count` или число связанных сигналов для нетехнических инцидентов, минимум 1).
- Доля детракторов — по умолчанию 10 %, Доля невозврата — по умолчанию 50 % (значения калькулятора); редактируются в настройках `economics_settings`.
- Ставка dCLTV выбирается по правилу приоритета: продукт инцидента → система-источник → канал → «Средняя ставка по банку» (4 050 ₽). Маппинг на наши сущности: `deposit` → «Вклады / накопительный счёт» 961; `debit_card` → «Дебетовая карта» 458,46 (для сегмента salary — «Зарплатная карта» 232,875; для youth при детских продуктах — 38,475); `credit_card` → «Кредитные карты» 305; `credit` → «Потребительский кредит» 92,745 (подтипы: автокредит 15,795, ипотека 48,195 — вне MVP, оставлены в справочнике); `mobile_app`/`web_bank` → «Мобильное приложение» 1 323; `processing` при переводах → 373,005, при платежах → 292,005; `contact_center` звонок → 204,93, чат → 206,955; `branch` → 115; `notification_gw`, `promo_engine`, `antifraud`, `core_abs` и любые другие системы вне таблицы → «Средняя ставка по банку» 4 050 ₽ (решение заказчика, v1.1); сегменты premium/vip/ultra_vip добавляют слагаемое «Премиальное обслуживание» 91,53.
- Предотвращённая потеря (₽) = Потенциальная потеря × Коэффициент удержания. Коэффициенты настраиваемые (решение заказчика, v1.1), хранятся в `economics_settings.retention_factors` по классам исхода: `closed_in_sla_with_gift` 1,0; `closed_in_sla` 0,9; `closed_late` 0,5; `closed_with_regression` 0,3; `open` 0; `rejected` 0; `churned` 0 (реализованная потеря). Режим `calibration_mode = simulated` заменяет ручные коэффициенты фактическими долями удержания из модели поведения (4.5): для каждого класса исхода берётся доля клиентов `retained` среди `affected` за окно истории; рядом показываются оба варианта, чтобы Елена могла сверить допущения калькулятора с эмуляцией. Так дашборд показывает «Потенциальные потери за день», «Предотвращённые потери», «Потери под риском (открытые инциденты)», с разбивкой по продуктам, регионам и сегментам.
- **[BRD]** Инциденты `fee_refund`: к потенциальной потере по dCLTV добавляется прямая стоимость — сумма возвращённой комиссии (`ledger_entries.amount`), экономический эффект считается как предотвращённая потеря минус возврат; на `/feed` рядом с ответом показывается «вернули 450 ₽, сохранили ≈ N ₽ ценности клиента». Инциденты `misselling`: в `economics_settings` вводится настраиваемая величина `misselling_case_cost_rub` (ожидаемые потери от одного случая: отмена договора, возврат премии, регуляторный/репутационный риск); значение по умолчанию равно средней ставке по банку 4 050 ₽ × коэффициент 1,0 и помечено «требует согласования с бизнесом» (20.3); предотвращённой считается стоимость случаев, по которым руководитель отреагировал («Иду») до завершения сделки.
- На карточке инцидента отображается расчёт в развёрнутом виде (все множители), чтобы его можно было сверить с калькулятором вручную. Таблица ставок `dcltv_rates` редактируется в настройках и экспортируется; в UI есть встроенная копия калькулятора («Сколько денег теряет банк из-за сбоев») для демонстрации бизнес-блока.

### 14.5 Калькулятор потерь: вкладка «Факт по симуляции»
Встроенный калькулятор (копия «Сколько денег теряет банк из-за сбоев») дополняется вкладкой, которая наполняется из данных симуляции, а не из допущений (требование заказчика, v1.1):
- Таблица сбоев по продуктам × дням × часам (тепловая матрица 14 дней × 24 часа с фильтром по продукту/системе/региону): число сбоев, затронутых операций и клиентов, поступивших сигналов.
- Исходы инцидентов по классам: закрыты в срок (всё исправлено, клиент уведомлён, подарок выдан), закрыты с нарушением срока, закрыты с регрессией («починили одно — сломали рядом», связь через `faults.caused_by_incident_id`), открыты, отклонены; по каждому классу — потенциальная и предотвращённая потеря.
- Ушедшие клиенты: кто ушёл спустя время после инцидента (из `churn_events`), через сколько дней, какой психотип и сегмент, что было предложено, сумма реализованной потери (ставка dCLTV без коэффициента удержания); каждая строка ведёт на инцидент `account_closure`.
- Сравнение «допущения vs факт»: доля детракторов и невозврата из калькулятора против фактических долей из симуляции, коэффициенты удержания ручные против калиброванных.
- Экспорт в CSV/XLSX и кнопка «Подставить факт в калькулятор» (переключает `calibration_mode`).

## 16. Установка, запуск, репозиторий

### 16.1 Требования к хосту
Любая Linux-машина (целевые: ВМ заказчика за VPN/Caddy или ноутбук с локальным Docker; Ubuntu 21.04+/Debian/CachyOS), 4–8 ядер, 16–32 ГБ ОЗУ (минимум для профиля `lite` — 2 ядра/4 ГБ), 5 ГБ диска; Docker 24+ и Docker Compose v2 (скрипт проверяет и предлагает установить на Ubuntu/Debian); исходящий интернет к API LLM (на защите гарантирован) либо режим `--offline` с mock. macOS и Windows (WSL2) — поддерживаются как побочный эффект Docker, но не тестируются целенаправленно. За Caddy приложение работает по одному префиксу/поддомену (frontend проксирует `/api` и `/ws`), секреты не попадают в клиентский бандл. **[BRD]** Для аудиомониторинга браузер отдаёт микрофон только в безопасном контексте — по HTTPS либо с `http://localhost` / `127.0.0.1`; открытие по `http://<IP ВМ>` микрофон не получит (ограничение браузеров), поэтому на демо используется либо ноутбук с локальным Docker (localhost), либо ВМ за Caddy с TLS; `install.sh` печатает предупреждение, если UI доступен только по http с нешаблонного хоста. STT добавляет ~1 ядро CPU и 0,3 ГБ ОЗУ на активную сессию (small-модель), 6 ГБ ОЗУ — при большой модели; одновременных сессий на демо — 1–2.

### 16.2 `install.sh`
1. Проверка Docker/Compose, портов (по умолчанию 8080 UI, 8000 API, 5432 БД, 8025 Mailpit), создание `.env` из `.env.example`, генерация секретов.
2. `docker compose build && docker compose up -d`.
3. Миграции Alembic, загрузка справочников, быстрая генерация базовых данных (профиль `demo`: 5 000 клиентов, 14 дней истории) — идемпотентно.
4. Снимок базового состояния после сида (`data/baseline/<profile>.dump`), health-check, вывод адреса мастера настройки и QR-кода. Флаги: `--offline` (LLM `replay → mock`, STT `vosk`, без сети, бот выключен), `--reset` (откат к снимку baseline или повторная генерация, если снимка нет), `--profile lite|demo|stress`, `--seed N`, `--no-mailpit`, `--with-tgbot` (требует `TELEGRAM_BOT_TOKEN` в `.env`), **[BRD]** `--no-stt` (не запускать STT-воркер), `--stt-model small|large` (large скачивает `vosk-model-ru-0.42` с проверкой контрольной суммы — единственная необязательная внешняя загрузка), `--record-cassettes` (включить запись ответов LLM на репетиции). Снимок baseline включает счета и проводки Mock-АБС. Отдельно `scripts/run.sh stop|resume|status|reset-baseline` для управления запусками из консоли.
Дополнительно: `make demo` (запуск сценария защиты), `make bench`, `make test`, `uninstall.sh`.

### 16.4 Нефункциональные требования
**[ДТЗ]** Пакетный анализ транскрипта до 60 реплик ≤ 10 с (p50) с рекомендациями; импорт файла транскрипта → появление сигнала клиента ≤ 3 с; polling-адаптер — интервал ≥ 5 с, идемпотентность по `external_id`; пересчёт зон карты ≤ 1 с после события; тикер экономики обновляется ≤ 2 с после пересчёта.
Старт системы ≤ 90 с на холодном кэше образов; обработка одного сигнала агентом по полному графу ≤ 15 с с GigaChat-3-Ultra (UI показывает прогресс по шагам); **[BRD]** быстрый путь (21.4): первое видимое действие агента на экране ≤ 2 с после публикации поста, полная цепочка «пост → возврат в АБС → ответ под постом» p50 ≤ 10 с, p95 ≤ 15 с (бюджет: нормализация на Lightning ≤ 1,5 с, БД + правила ≤ 0,3 с, один вызов Ultra «классификация+решение+ответ» со streaming ≤ 5 с, инструменты ≤ 0,5 с), при превышении 8 с на любом LLM-шаге — автоматический failover на `replay → mock` без остановки цепочки; аудиомониторинг (22.7): частичный транскрипт ≤ 0,5 с от речи, предварительная отметка правилом ≤ 0,3 с после финала реплики, подтверждение LLM ≤ 2 с, итоговая реакция счётчика ≤ 3 с, алерт на `/manager` ≤ 1 с после порога; голосовой ввод жалобы: частичный текст ≤ 0,5 с, финализация ≤ 1,5 с после паузы, далее — обычный бюджет сигнала; UI отзывчив при 5 000 клиентах и 10 000 сигналов; логирование структурное (JSON); все секреты только в `.env`; никакого исходящего трафика, кроме LLM API, Telegram Bot API (если включён бот) и опционально обновления образов. Все LLM-вызовы проходят через rate-limiter и учёт токенов; при недоступности LLM агент деградирует до mock без остановки симуляции.

## 19. Критерии приёмки MVP

1. `git clone … && ./install.sh` на чистой Ubuntu ВМ с Docker приводит к рабочему мастеру настройки без ручных шагов.
2. Мастер проверяет подключение к GigaChat-3-Ultra и позволяет выбрать другой провайдер; параметры редактируются в настройках.
3. Симулятор генерирует события всех типов; тепловая карта и лента обновляются в реальном времени; есть Старт/Пауза/Скорость.
4. Агент по сценариям 1–7 выполняет ожидаемые действия (автотесты зелёные), все действия видны в трассировке.
5. HITL-очередь работает: решение человека меняет ход обработки и записывается.
6. Карточка инцидента показывает историю клиента, историю инцидентов, историю статусов, документы команды, коммуникации.
7. Лендинг создаёт обращение, страница трекинга отражает прогресс и уведомления; при заданном токене Telegram-бот проводит тот же сценарий и присылает статусы в чат.
8. Экран бенчмарков показывает сравнение GigaChat-3-Ultra, Lightning, Pro, минимум одной бесплатной модели OpenRouter и mock по метрикам раздела 14, с учётом токенов по ключам и лимитов OpenRouter.
9. В данных нет реальных ПДн (проверка скриптом по паттернам), нет внешних CDN (тест), все зависимости — разрешённые лицензии (отчёт `pip-licenses`/`license-checker`).
10. Инциденты класса «сложный/низкая критичность» живут до 10 рабочих дней, промежуточные отчёты создаются и контролируются, пропуск отчёта порождает предупреждение и эскалацию.
11. На карточке инцидента и дашборде отображается расчёт потерь по методике dCLTV с теми же ставками и формулой, что в калькуляторе бизнеса.
12. Интерфейс переключается ru/en без перезагрузки; явного брендирования нет, палитра соответствует разделу 12.1.
13. Экран «Под капотом» демонстрирует все пять приёмов раздела 12.5, включая панель «ИИ против правил».
14. Клиенты имеют психотипы и состояния; реакция на ответ агента и уход разыгрываются по модели 4.5; «подсвеченные» клиенты отвечают текстом через лёгкую модель (в офлайне — mock); уход создаёт инцидент `account_closure`; вкладка калькулятора «Факт по симуляции» заполняется и калибрует коэффициенты удержания.
15. Бенчмарк с тремя моделями OpenRouter из 5.2 проходит на полном золотом наборе в пределах суточного лимита 1 000 запросов, с отображением остатка лимита и расхода баланса.
16. Каждый запуск эмуляции сохраняется в истории с итоговыми метриками; повторный запуск сценария в режиме `baseline` с тем же сидом на mock даёт идентичные события и метрики; в режиме `counters` показатели нового запуска не содержат данных предыдущих.

18. **[BRD]** Публикация отзыва на `/feed` (или `POST /api/public/reviews`) запускает цепочку агента, видимую на панели Log в течение ≤ 2 с; для сценария 8 баланс клиента в виджете АБС меняется на сумму возврата и под постом появляется релевантный ответ агента за ≤ 10 с (p50 по 10 прогонам на GigaChat-3-Ultra), ≤ 15 с (p95); возврат подтверждён правилом `RULE-QR-FEE-001` в трассировке; повторная публикация того же отзыва не создаёт второй возврат.

21. **[BRD]** Детектор мисселлинга на наборе `misselling_v1` даёт F1 ≥ 0,8 для выбранной модели и показывает precision/recall по категориям на экране бенчмарков; «чистые» продающие фразы не вызывают алерт.
22. **[BRD]** Режим подстраховки: при отключённой сети (`install.sh --offline` или имитация отказа API) сценарии 8 и 9 проходят целиком на кассетах `replay`, Vosk и предзаписанных WAV по скрытой кнопке; в футере виден бейдж режима; автоматический failover срабатывает при таймауте LLM без прерывания цепочки.
24. **[BRD]** На демо-экранах `/feed`, `/compliance`, `/manager` присутствует панель Log с процентами уверенности, JSON-сущностями, сработавшими правилами и бизнес-строкой эффекта; системные промпты скрываются тумблером.
25. **[BRD]** Кнопка «Надиктовать» в режиме показа и на лендинге превращает речь в текст в поле формы (частичный текст ≤ 0,5 с), текст редактируется до отправки, сигнал помечен `origin = 'voice_input'` и обрабатывается агентом как обычный текст; в трассировке виден шаг STT с провайдером и уверенностью; без микрофона/HTTPS кнопка скрыта, текстовый ввод работает.
26. **[ДТЗ]** Транскрипт в JSON и в TXT, загруженный файлом и через `POST /api/ingest/transcripts`, сохраняется в `transcripts`, порождает сигнал клиента ≤ 3 с и отчёт о «красных фразах» ≤ 10 с (p50, до 60 реплик); сообщение через `POST /api/ingest/messages` и через polling-адаптер mock-ленты проходит нормализацию в единую схему (канал, клиент, текст, timestamp, гео) и создаёт сигнал; повтор по `external_id` отклоняется как дубль.
27. **[ДТЗ]** Точность `sentiment` на `sentiment_v1` ≥ 80 % для основного провайдера (отчёт бенчмарка в репозитории); расхождение `sentiment` с порогами `negativity` ≤ 10 % примеров.
28. **[ДТЗ]** На `hidden_negativity_v1` recall по `sarcasm`, `passive_aggression`, `churn_threat` ≥ 0,75 при precision ≥ 0,7; саркастичный текст с позитивной лексикой получает `sentiment = negative` и флаг `sarcasm` (сценарий 11).
29. **[ДТЗ]** `problem_summary` присутствует у каждого классифицированного сигнала, `problem` ≤ 2 предложений в ≥ 95 % случаев, `severity` и `suggested_team` на `summary_v1` совпадают с эталоном в ≥ 80 % (severity — с допуском ±1 уровень); несогласованность `suggested_team` с маршрутом видна на панели «ИИ против правил».
30. **[ДТЗ]** Агент использует инструменты `route_to_department`, `notify_customer`, `escalate_to_manager`, `request_clarification` с точными сигнатурами; `router_action` согласован с вызовами (`policy_checks`); тикет виден в `GET /api/tickets` и на вкладке «Тикеты»; подтверждение клиенту записано в `notifications` и в лог; эскалация обязательна при угрозе ухода с `negativity ≥ 80` и при повторном негативном обращении (сценарий 11) и попадает в очередь руководителя CX.
31. **[ДТЗ]** `GET /api/agent/runs/{id}/decision-chain` возвращает цепочку «инструмент → аргументы → почему» для любого запуска в JSON и Markdown; та же цепочка видна на панели Log и «Под капотом».
32. **[ДТЗ]** На `red_phrases_v1` F1 по семейству `conduct` ≥ 0,75, для `misinformation` указан верный факт из БД; алерт `immediate` руководителю содержит цитату и рекомендацию и появляется на `/manager` и в логе ≤ 2 с после завершения анализа (сценарий 10); для `script_violation` алерт не создаётся, находки попадают в отчёт.
33. **[ДТЗ]** Слой «Зоны» раскрашивает субъекты в 🟢/🟡/🔴 по `v_map_zones` с учётом негатива сигналов и сработок copilot, пересчитывается ≤ 1 с после события и имеет текстовую легенду; элементы ленты инцидентов содержат саммари, статус маршрутизации и канал; тикер финансового эффекта обновляется ≤ 2 с после пересчёта экономики.

## 21. Контур «Внешние площадки и автономный возврат» [BRD, сценарий 1]

### 21.1 Назначение и границы
Показать C-level, как агент сам находит негатив на внешней площадке, узнаёт клиента по косвенным данным, находит ошибку банка в транзакциях, устраняет её деньгами и публично отвечает — за секунды. Реальные Банки.ру и Telegram не парсятся (вне MVP): их заменяют эмулятор ленты `/feed` и публичный API, что также исключает юридические риски и зависимость от сети. Вся логика агента (нормализация, матчинг, правила, решение, текст) — настоящая; банковские системы — Mock-АБС из раздела 3.4.

### 21.2 Слушатель (FR 1.1)
- `POST /api/public/reviews {platform, author_nick, text, mentions?: {card_last4?, phone_masked?}, posted_at?}` → `external_posts` + событие `review.posted` → сигнал канала `review_portal` → граф агента. Ответ API возвращает `post_id` и ссылку на пост в `/feed`.
- Эмулятор `/feed` (экран 8 в 12.2): лента постов с формой публикации; обновляется по WebSocket (`feed`); у каждого поста — статус (новый / обрабатывается / отвечено / переведён в личный канал) и время реакции агента.
- Фоновые посты (0–2 в сим-час, из корпуса `SA-Reviews`) — чтобы лента жила; доля из них «шумовые» (вопросы, благодарности), доля — повод для сценария 2 и 8.
- Тот же приёмник используется Telegram-ботом (11.3) для сообщений из канала/чата, если команда решит подключить реальный канал на финале.

### 21.3 NLP и идентификация (FR 1.2–1.3)
Нормализация на быстрой модели (GigaChat-3-Lightning) возвращает structured output из раздела 7: `negativity` 0–100, `intents[]`, `entities`, `contacts_hint`. Узел `identify_client` вызывает `match_client_by_hints`: поиск по `clients.social_handles` (точное совпадение ника → 0,9), по `client_products.card_last4` (0,5, если один клиент; делится на число совпадений), по маскированному телефону (0,6), по городу и продукту как уточнению (+0,1 каждый, только при наличии другого признака); итоговая уверенность — вероятностная комбинация; порог автономии 0,8. Все кандидаты и их очки показываются на панели Log («Mock CRM: 1 кандидат, 0,93»). Если автор — не клиент, агент публично приглашает в личный канал и создаёт сигнал «неидентифицированный» (как с лендинга, раздел 11).

### 21.4 Decision Engine и быстрый путь (FR 1.4)
1. `get_recent_operations` + `get_account_balance` за окно 72 сим-часа, фильтр по сумме/продукту из `entities` (450 ₽, дебетовая карта) → операция-кандидат и её проводки (`ledger_entries`: `debit 3 200`, `fee 450`).
2. `check_business_rules` (9.6) → `RULE-QR-FEE-001` matched с доказательствами (ids проводок, тариф «QR/СБП для физлиц — 0 ₽»).
3. Политики 9.3 (лимит, уверенность, идемпотентность, антизлоупотребление) → `fast_path = true`.
4. Один вызов основной модели (GigaChat-3-Ultra, streaming, structured output `instant_decision`): классификация (`tech_fault` + `tariff_terms`, флаги `churn_intent`, `public`), обоснование со ссылкой на правило, текст публичного ответа, текст личного уведомления, рекомендация подарка. Параллельные вызовы функций API v2 позволяют Ultra одним ответом запросить `refund_fee`, `create_incident`, `publish_public_reply`, `notify_client`.
5. `act_instant` исполняет инструменты в порядке «деньги → инцидент → публичный ответ → личное уведомление»; `refund_fee` создаёт проводку `refund` с `refund_of_entry_id` и `rule_id`, обновляет баланс и шлёт `abs.refund_posted`; `verify_service_delivered` проверяет баланс; `close_incident`; `gift` по справочнику (300 баллов при `churn_intent`).
6. Массовость: `find_affected_clients(PROC-QR-FEE-CHARGED, 24 сим-часа)` → при ≥ `mass_refund_threshold` создаётся инцидент `tech_fault` в `team_processing` (`mass_impact`), предложение массового возврата — в HITL; после подтверждения агент выполняет `refund_fee` пакетно с прогрессом на экране и проактивно уведомляет пострадавших (ветка 9 раздела 6).
Если правило не подтверждено (например, комиссия законна по тарифу), агент идёт по обычному графу: объясняет клиенту тариф (`client_error`/`tariff_terms`), без возврата, с предложением обратиться в личный канал.

### 21.5 Публичный ответ (FR 1.5)
Инструмент `publish_public_reply` публикует текст под постом с бейджем «Ответ банка · ИИ-агент CX» и временем реакции; текст генерирует основная модель по промпту `public_reply.md` с правилами 9.3 (извинение, факт и срок возврата, приглашение в личный канал, без ПДн, тон по сегменту и площадке — короче и человечнее, чем в e-mail); `promise_check` отклоняет обещания вне SLA; при `negativity ≥ 80` агент дополнительно переводит диалог в личный канал (`review.escalated_to_dm`). Двойник клиента (4.5) реагирует на публичный ответ (`satisfied`/`asks_again`) — реакция отображается как ответный комментарий под постом с пометкой «эмуляция клиента».

### 21.6 Критерии показа
См. 19 п. 18–19 и бюджет задержек 16.4. На экране `/feed` зритель одновременно видит: пост → строки панели Log с задержками и процентами → проводку возврата и новый баланс на виджете АБС → ответ под постом → строку эффекта («возвращено 450 ₽, предотвращённая потеря ≈ N ₽»).

## 22. Контур «Аудиомониторинг отделения и пресечение мисселлинга» [BRD, сценарий 2]

### 22.1 Назначение и границы
Агент в режиме, близком к реальному времени, слушает диалог менеджера и клиента в отделении, транскрибирует его, выявляет паттерны мисселлинга в речи сотрудника, ведёт счётчик нарушений в рамках сессии и при достижении порога немедленно уведомляет руководителя отделения, одновременно открывая инцидент `misselling` для комплаенса. Вне MVP: голосовая диаризация, запись и хранение аудио клиентов, интеграция с реальными системами аудиозаписи отделений, TTS.

### 22.2 Захват аудио и потоковый STT (FR 2.1)
- Браузер (`/compliance`): `getUserMedia({audio: {channelCount: 1|2, echoCancellation, noiseSuppression}})` → `AudioWorklet` → ресемплинг в PCM16 16 кГц → бинарный WebSocket `/ws/audio/<session_id>` чанками по 100 мс. Требуется HTTPS или localhost (16.1).
- Сервер: `STTProvider` (5.3) — по умолчанию `vosk` с русской моделью; на сессию один распознаватель на канал; частичные результаты (`partial`) отправляются в UI сразу, финальные (`final`, с таймкодами слов) — в `utterances` и далее в детектор. Пользовательский словарь терминов повышает точность на ключевых словах («страховка», «ИСЖ», «НСЖ», «ПДС», «вклад», «гарантия», «формальность»).
- Источники сессии: `mic` (живой), `file` (предзаписанный WAV через тот же конвейер, 5.4), `transcript` (эталонный текст с таймкодами, если STT недоступен). Источник виден бейджем на экране.

### 22.3 Разделение спикеров (FR 2.2)
Анализу на мисселлинг подвергается только речь сотрудника (канал 1). Режимы `diarization_mode`:
- `stereo` — два канала аудио (две гарнитуры/USB-интерфейс или стерео-микрофон): левый — сотрудник, правый — клиент; самый надёжный, соответствует формулировке BRD «Канал 1 / Канал 2».
- `manual` (по умолчанию на демо с одним микрофоном) — демонстратор переключает активную роль пробелом/кнопкой; переключение фиксируется с таймкодом и применяется к следующим финальным репликам.
- `auto` — быстрая модель (Lightning) атрибутирует каждую финальную реплику роли по содержанию и контексту диалога (`{speaker, confidence}`); реплики с уверенностью < 0,7 помечаются «роль не определена» и не входят в анализ; режим служит подсказкой и страховкой при забытом переключении в `manual`.
Голосовая диаризация (pyannote и аналоги) не используется: требует GPU и моделей с ограниченным доступом (1.3).

### 22.4 Детектор мисселлинга (FR 2.3)
Таксономия `misselling_patterns` (включены по умолчанию первые три — по BRD; остальные выключены и доступны в настройках):

| Код | Паттерн | Примеры сотрудника | Что не является нарушением |
|---|---|---|---|
| `tie_in` | Жёсткая привязка услуги | «без страховки вам не одобрят», «кредит только со страховкой», «карту выдадим, если оформите подписку» | «страховка снизит ставку на 2 п. п., решение за вами» |
| `substitution` | Подмена понятий | «это как вклад, только лучше», «тот же депозит, но доходнее», «это не инвестиции, это накопления с гарантией» | «это инвестиционный продукт, доход не гарантирован, в отличие от вклада» |
| `concealment` | Утаивание информации | «подпишите, это формальность», «условия стандартные, читать не обязательно», «комиссий нет» (при наличии) | «обратите внимание на пункт о досрочном расторжении» |
| `pressure` (опц.) | Давление / искусственная срочность | «только сегодня», «решайте сейчас, потом не будет» | информирование о реальном сроке акции с датой |
| `guarantee` (опц.) | Гарантия доходности инвестиционного продукта | «гарантированно 20 % годовых» | «историческая доходность … не гарантирует будущую» |

Гибридная детекция в два этапа: (1) правила (`mock`-детектор: ключевые фразы и шаблоны с весами, ≤ 0,3 с) выставляют *предварительную* отметку (`status = preliminary`, серо-красная подсветка, в счётчик не входит); (2) быстрая модель (`GigaChat-3-Lightning` по умолчанию, structured output `{is_misselling, pattern_code, confidence, quote, explanation}`, контекст — последние 6 реплик и продукт сделки) подтверждает или снимает отметку в пределах 2 с; подтверждённые триггеры (`confirmed`, уверенность ≥ 0,6) входят в счётчик и подсвечиваются красным с чипом категории и процентом. Если LLM недоступна дольше 2 с, предварительная отметка правила с уверенностью ≥ 0,85 засчитывается с пометкой «по правилу» (failover), иначе ждёт. Для одной реплики — не более одного триггера. Выбор модели детектора подтверждается бенчмарком `misselling_v1` (14.3): F1 ≥ 0,8; при недостижении — Ultra с теми же бюджетами.

### 22.5 Машина состояний сессии (FR 2.4)
`audio_sessions.status`: `live` → (`trigger_count` растёт по подтверждённым триггерам) → при `trigger_count ≥ alert_threshold` (по умолчанию 3) → `alerted` (однократно за сессию; дальнейшие триггеры фиксируются, но повторный алерт не шлётся, если руководитель уже отреагировал) → `closed` (кнопкой «Стоп сессии», по тишине > 90 с или по предзаписанному файлу). Счётчик привязан к сессии: новая сессия (новый клиент/сделка) начинается с `0/3`; отклонённые руководителем триггеры (`dismissed`) уменьшают счётчик и попадают в обучающие примеры детектора. Сессии несут `run_id` (4.7); сброс к baseline очищает сессии сценария 9.

### 22.6 Алертинг и действия (FR 2.5)
При переходе в `alerted`: событие `compliance.alert` → WebSocket-топик `compliance` → `/manager` (экран 10) показывает всплывающее уведомление ≤ 1 с; при включённом боте и заданном `manager_chat_id` — сообщение в Telegram с теми же данными; создаётся инцидент `misselling` (8.1) в `team_compliance` с привязкой сессии, сотрудника, клиента, цитат и уверенностей; инцидент встаёт в очередь HITL руководителя отделения с вариантами «Иду» (инцидент `in_progress`, сделка помечена «приостановлена» в Клиент 360), «Ложное срабатывание» (триггеры `dismissed`, инцидент `rejected`, пример в обучающую выборку), «Открыть инцидент» (стандартная карточка). После решения человека агент готовит клиенту разъяснение (шаблон `misselling_clarification`) — отправляется только после подтверждения руководителя. На рабочем месте CX тот же инцидент виден «тихой» карточкой и учитывается в метриках и экономике (14.4).

### 22.7 Критерии показа
См. 19 п. 20–21 и бюджет 16.4: частичный транскрипт ≤ 0,5 с; отметка правила ≤ 0,3 с после финала реплики; подтверждение LLM ≤ 2 с; реакция счётчика ≤ 3 с; алерт на устройстве ≤ 1 с. На экране `/compliance` одновременно видны лента с красными фразами, счётчик, профиль менеджера, задержки STT/детектора и панель Log с процентами уверенности и JSON триггера.

### 22.8 Пакетный анализ транскрипта и «красные фразы» (ДТЗ FR-4.1–4.2) [ДТЗ]
Режим `pacing = batch`: транскрипт из `transcripts` (3.7) создаёт `audio_sessions` с `source = transcript`, `pacing = batch`, роли берутся из файла; все реплики сотрудника анализируются одним проходом: rule-детектор по всем семействам → один вызов LLM на транскрипт целиком (контекст — реплики клиента, продукт сделки, эталонный скрипт, факты о продуктах) со structured output `transcript_report` (находки с цитатами-подстроками, категорией, уверенностью, `fact_check` для `misinformation`, `recommendation_ru`; соблюдение этапов скрипта; общая оценка и план отработки). Бюджет — ≤ 10 с для 60 реплик. Для контакт-центра тот же режим включается флагом `employee_quality`.

Таксономия расширена семейством `conduct` (политика алерта указана в скобках):

| Код | Семейство | Паттерн | Примеры | Политика алерта |
|---|---|---|---|---|
| `rudeness` | conduct | Грубость, пренебрежение, обвинение клиента | «вы вообще читали условия?», «это не моя проблема», «я вам уже три раза сказала» | `immediate` при уверенности ≥ 0,8 |
| `script_violation` | conduct | Нарушение скрипта обслуживания: пропуск приветствия/идентификации/выявления потребности/резюме, запрещённые формулировки | начало с продажи без вопроса о потребности; «подпишите, потом почитаете» | `report` (в отчёт, без алерта) |
| `misinformation` | conduct | Неверная информация о продукте/тарифе/условиях | «ставка по вкладу 14 %» при табличной 9,5 %; «комиссия за СБП 1 %» при нулевой | `immediate` при уверенности ≥ 0,8 и подтверждённом `fact_check`; иначе — отчёт с пометкой «требует проверки» |
| `tie_in`, `substitution`, `concealment`, `pressure`, `guarantee` | misselling | см. 22.4 | — | `counter` (порог 3 за сессию) |

Эталонный скрипт обслуживания хранится в `service_scripts` (`retail_service_v1`: приветствие → идентификация → выявление потребности → предложение с раскрытием условий → резюме и следующий шаг → завершение; запрещённые формулировки). Проверка фактов: LLM извлекает утверждения о ставках/комиссиях/сроках, сервис сверяет с `products`, `tariffs`, `dcltv`/настройками и возвращает `truth`; LLM формирует формулировку расхождения. В живом режиме (22.4) семейство `conduct` работает по тем же правилам, но `misinformation` проверяется только по ключевым фактам (ставки и комиссии продукта сделки), чтобы уложиться в 2 с.

### 22.9 Уведомление руководителю с рекомендацией (ДТЗ FR-4.3) [ДТЗ]
Каждая находка получает `recommendation_ru` — что сказать сотруднику и какой учебный модуль назначить (шаблоны в `misselling_patterns.recommendation_ru`, уточняются LLM по цитате); алерт `immediate` и отчёт по транскрипту содержат цитату, категорию, уверенность и рекомендацию. Доставка: карточка на `/manager` (раздел «Отчёты по транскриптам»), запись в `notifications` (лог) и, при настройке, Telegram руководителя. Отчёт можно экспортировать (JSON/Markdown) и приложить к инциденту `misselling`/`service_quality` в команду `team_branch_network`.
