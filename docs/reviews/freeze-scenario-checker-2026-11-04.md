# Предфризовая проверка сценарного CLI и изоляции CI

Основа приложения — main `7fe3f85f2a2223ccdd016dfaf72f7de44aa55ecc`.
Проверки выполнялись на собственном Docker Compose с PostgreSQL 16 и Mock,
без ключей GigaChat/OpenRouter/Telegram, без внешних доставок и без изменения
рабочего банка. Этот документ не объявляет весь проект готовым к фризу.

## Найденные дефекты проверок

1. `scenario_check.py` отправлял `{}` даже для сценариев 1/4/7,
   требующих `reset_mode=baseline`. Реальный `all` останавливался на первом 409.
   Теперь без отдельного `--allow-baseline-reset` эти сценарии получают FAIL
   с инструкцией и **без HTTP-запроса**, а цикл продолжает остальные проверки.
   Только явный opt-in отправляет требуемый baseline. Обычный запрос остаётся `{}`.
   Makefile передаёт флаг только при `ALLOW_BASELINE_RESET=1`.
2. Ожидание графов/транскрипта возвращало одинаковый `None` при завершении и
   таймауте. После истечения `--wait` существующий сигнал мог давать ложный PASS.
   Теперь ожидание возвращает `bool`; таймаут добавляет сохранённый failed check
   `processing_completed` и делает результат FAIL. Увеличения timeout и retry нет.
3. Evaluator считал только legacy `outcome=error`, пропуская штатный `failed`;
   даже известный error не влиял на `passed` при пустых ожиданиях.
   Оба исхода теперь входят в `counts.errors` и запрещают PASS.
4. CI performance seed создавал `demo.dump`, но runtime оставался с default
   `PROFILE=lite`. Проверенный demo baseline отвергался как отсутствующий/legacy
   lite metadata. Теперь один выбранный профиль используется seed и обоими
   runtime origins. Schema fingerprint, metadata, restore guards не ослаблялись.

Регрессии: explicit baseline opt-in/default zero-POST — RED 7 failed;
таймаут — RED 2 failed; failed/error — RED 2 failed; profile — RED 2 failed.
Итоговый целевой набор: **67 passed**, Ruff check зелёный; форматирование
изменённых app/tests и CLI проверено. Формулы, ставки, политики, HITL, API/DDL
и рабочая история не менялись. Откат — revert файлов checker/helper;
исправления не запускают миграции, reset или внешние запросы сами по себе.

## Native HTTP-проверка каталога

Синтетический demo5000 создан за **30,058 с**. Один настоящий вход personal API
доставил `signal.received` через PostgreSQL NOTIFY в операторский WebSocket за
**3,076 мс**. Это один замер, не p95 и не доказательство задержек всех типов событий.

После исправления собственного PROFILE/DSN выполнены все 35 случаев штатным
`run_one` с явным разрешением reset только собственной БД. Приватная обвязка
сохраняла FAIL на HTTP-ошибках и продолжала каталог; сами assertions не менялись.
Полный неизменённый CLI также запускался отдельно и вернул exit1.

- 5 сценариев прошли все объявленные проверки: 3/4/6/9/10.
- 6 сценариев прошли реализованные проверки, оставив explicit unknown:
  1/2/5/7/8/11. Не проверены отдельные SLA/поведенческие/превентивные
  ожидания, переход в личный канал, live p50 и эскалация по молчанию.
- 18 случаев из demo20 прошли только smoke: у 14–33 пустой `expected`,
  поэтому присутствие сигнала и отсутствие failed не доказывают весь бизнес-сюжет.
- 17/26 получили HTTP409 `Simulator устарел: загрузите актуальные time/run/RNG
  перед управлением`. Ранее отдельный 17 проходил; это непостоянный control/tick
  конфликт, требующий самостоятельной диагностики и регрессии.
- 12/13 не получили необходимые записанные траектории/контексты read-model.
  Mock не подменялся replay; недостающие записи не изобретались.
- 34/35 прошли native Mock foundation, но остались FAIL/not_verified по
  самостоятельным UI/replay-критериям. Другие browser-доказательства оцениваются
  отдельно, эти placeholders автоматически не объявлялись PASS.

Итого 29 истинных результатов функции из 35, **6 FAIL**, но только 5 из 29
не имеют названных ограничений проверки. Весь каталог зелёным не объявляется.
Снимок EOF содержал 4 ещё активных AR; он не используется как доказательство
полного завершения массовой очереди. Банковские сбросы между 1/4/7 выполнялись
только на собственном стенде; результаты сохранялись до следующего reset.

Первоначальный green map в сценарии 6 оказался ошибкой приватной обвязки:
внутренний read-only producer читал default DSN вместо собственного. После
явного выбора DSN тот же native сценарий прошёл, включая красные зоны.
Первоначальный baseline409 также был воспроизведённым несоответствием PROFILE,
а не изменением DB schema после графа; demo metadata совпала с actual fingerprint.
Эти два первоначальных результата не выдаются за дефекты production producers.
