# ABS: сохранение входящего остатка при backfill

Финансовая граница кода и отдельные две корректировки согласованы пользователем 2026-11-05 с условием зелёных полного gate и CI. Рабочая БД этим PR автоматически не исправляется.

## Подтверждённый дефект

При штатном cold startup `main._abs_backfill()` вызывает `backfill_ledger()` для операций без проводок. Эти функции не менялись между предыдущей `main` и PR #222. На изолированной копии pre-rollout backup старый код воспроизвёл 17 891 историческую проводку и один недостающий счёт. Это не новые возвраты: только `credit`, `debit`, `fee`, `created_by=sim`; без refund/reversal, agent/rule/refund links и внешних отправок.

Однако два существующих счёта, 614 и 777, изменились с `-3400.00` на `0.00`. Старый opening credit использовал `greatest(balance,0)+spent`; наличие этой строки затем исключало создание отрицательного входящего остатка. Повтор старого и нового кода на уже дополненной истории ничего не добавлял: идемпотентность скрывала ошибочный первоначальный расчёт.

## Исправление

Только для счёта без opening marker (`operation_id IS NULL`) вычисляется:

```
existing_net = Σ credit + Σ refund − Σ debit − Σ fee − Σ reversal
initial = сохранённый accounts.balance − existing_net
```

Положительный `initial` сохраняется как opening credit, отрицательный — как opening debit с модулем суммы. При нулевом `initial` и существующих движениях создаётся допустимый схемой нулевой credit marker: следующие backfill не считают счёт неинициализированным. Пустой счёт с нулевым балансом лишней проводки не получает.

Сохранены сигнатура, selection операций по `run_id`, прежний выбор run для opening, создание недостающего счёта, отключённые historical events и смысл счётчика `credits` (все opening entries). Уже существующие opening entries не меняются. Формулы dCLTV, комиссии, ставки, правила возврата, HITL и лимиты провайдеров не затрагиваются.

## Проверки

Реальный PostgreSQL RED: отрицательный остаток с расходом терял исходное значение; существующий refund давал `100 → 120` вместо сохранения `100`. Ранее существовавший тест ошибочно требовал opening debit для любого отрицательного текущего баланса. Он заменён более строгими проверками сохранения каждого исходного баланса и знака/суммы opening согласно формуле.

GREEN: 13 native PG tests, включая отрицательный баланс без движения и с расходом меньше/равным/больше долга; положительный и нулевой остаток; нулевой marker; уже существующий refund без создания нового refund; повторный вызов без новых проводок; `run_id` scope и неизменность существующего opening. Ruff, format и strict mypy целевого service прошли. Полный immutable `make test` на runtime `dfeda7f3481dd2bb1042674d556c30fa962c0186`: **4141 passed / 20 skipped / 0 failed**, exit0. Backend: 2367 unit (19 skipped), 1015 integration, 44 scenarios (1 optional live skipped), 31 compliance; frontend634 и bot50. Архив Git не изменён, собственный PostgreSQL остановлен. Общие `make lint`, contracts и owners `--allow-cross` прошли. CI актуального PR head проверяется до merge.

## Отдельное восстановление уже изменённых двух счетов

Один source fix сохраняет существующие opening entries и поэтому автоматически не меняет уже обнулённые счета. Для них предлагается отдельная явно согласованная append-only операция: **две debit correction по 3400.00**, итоговые балансы `614: -3400.00`, `777: -3400.00`.

План не удаляет и не переписывает прежние проводки и не выполняет прямой `UPDATE accounts.balance`. Коррекции проходят через `abs.service.post_entry` в одной транзакции с блокировкой двух accounts. Для каждой фиксируются exact expected opening-entry hash/ID, исходный backup hash, current balance `0.00`, run и время исходного opening. Correlation детерминирована по backup hash и account ID; совпадение correlation допускает только точный повтор той же коррекции, иное содержимое вызывает отказ. `created_by=human`, `operation_id=NULL`, без refund, rule/agent links и внешних events.

Перед применением обязательны: неизменность approved opening fingerprints и всех предпосылок, отсутствие конкурентных банковских writers, проверенный backup; после — оба баланса `-3400.00`, бухгалтерский инвариант и неизменность всех остальных balances/старых ledger rows. Повтор должен быть no-op. Точный план проверен на собственной копии текущего backup без подмены ID/hash. Полный runner дополнительно прошёл 7 Docker-проверок, включая поздний отказ с rollback и committed repeat без изменений; сеть отключена, primary не подключалась. **Коррекции рабочей БД ещё не выполнялись; их финансовая граница отдельно согласована, применение — после зелёных gate/CI, нового backup и остановки writers.**

Откат source-кода не отменяет финансовые записи. Предложенная корректировка также требует отдельного решения для любого обратного действия; автоматического удаления истории нет.
