# Живая проверка LLM-нормализации — 29.10.2026

Причина расследования — normalize у SIG-080097 имел status=fallback и модель mock:mock-rules-v1. Нормализация уже вызывала выбранную роль fast (Lightning), но её ошибочный structured output приводил сразу к replay/mock. В контрольном вызове Lightning дважды вернул null в hidden_negativity.*.confidence, где контракт требует число; Ultra на том же тексте прошёл неизменённую схему. Исторические шаги не переписывались.

## Выборка и результат

`harness.py` выбирает текст исходного обращения, первые два кейса каждого sentiment из sentiment_v1 и первые уникальные группы markers из hidden_negativity_v1: всего 9 кейсов. Использованы активные профили стенда fast=GigaChat-3-Lightning и main=GigaChat-3-Ultra, temperature=0. Промпты и JSON Schema в обоих проходах одинаковы; mock/replay в baseline запрещены. Выбранные профили и каждый результат сохранены в `results.json`.

- Только fast: 7/9 валидных live-ответов, 2 bad_output; p50 1352 мс, максимум 3141 мс; 2841 учтённый токен, включая невалидные ответы.
- fast → main: 9/9 валидных live-ответов, mock=0; 5 Lightning и 4 Ultra; p50 1493 мс, максимум 5174 мс при общем бюджете живых попыток 8 секунд; 12858 учтённых токенов.
- Совпадение sentiment с gold: 7/8 в baseline (ошибка схемы входит в знаменатель), 8/8 после. Исходный текст без gold не входит в эту метрику.

Один проход не измеряет стабильность или общую точность. Некоторые кейсы получили разный результат в двух проходах при temperature=0; нельзя объяснять весь прирост исключительно кодом. Прямой переход от невалидного Lightning к валидному Ultra, включая исходное обращение, сохранён в attempts. Полная проверка precision/recall трёх видов скрытого негатива (T-211) здесь не заявляется: существующие markers в выбранном корпусе не покрывают эти три класса отдельно.

## Воспроизведение

Одноразовый Compose-контейнер использует зависимости образа backend, `backend/app` исследуемой ветки монтируется в `/app/app:ro`, этот harness и каталог результата — в `/reports`. Запуск `python /reports/harness.py`. Настройки и ключи читаются штатным Settings, в отчёт попадают только code/provider/model. Проверка TLS включена; LLM_RECORD выключен; lifespan и фоновые агенты не запускаются. БД читается в READ ONLY, новые обращения и кассеты не создаются.

Успешная нормализация не гарантируется при недоступности всех LLM: replay/mock остаются честно помеченным резервом. Auth/quota/429 не вызывают повтор другой моделью того же ресурса. Таймаут включает ожидание лимитера; остаток общего бюджета передаётся основной модели. Неудачные попытки и их расход сохраняются вместе с результатом.
