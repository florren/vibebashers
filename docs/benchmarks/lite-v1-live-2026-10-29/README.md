# Живой lite_v1: GigaChat Ultra / Lightning / Pro

Полные результаты от 29.10.2026: `baseline/` — исходная инструкция structured output; `global-instruction/` — эксперимент с общей новой инструкцией; `final/` — исправление только для Lightning, прежние инструкции Ultra и Pro сохранены. Каждый этап содержит 40 кейсов × 3 модели, один проход, temperature=0. Все ошибки сохранены; mock/replay в benchmark не используются.

Итог финального измерения (все ошибки входят в метрики):

- gigachat_ultra: тип 87.5%, продукт 100%, structured output 100%; p50/p95 2522/5472.5 мс; 143927 токенов; ошибки {}.
- gigachat_lightning: тип 70%, продукт 77.5%, structured output 90%; p50/p95 1147.5/2308.75 мс; 12274 токенов; ошибки {'bad_output': 4}.
- gigachat_pro: тип 77.5%, продукт 75%, structured output 97.5%; p50/p95 3452/4220.65 мс; 18501 токенов; ошибки {'bad_output': 1}.

Учтённые токены: baseline 194676, эксперимент общей инструкции 178373, final 174702; всего 547751 по 360 обработанным кейсам. Дополнительно отменённый запуск №1: один сохранённый кейс, 2968 токенов; незавершённый запрос может иметь неизвестный расход.

Общая новая инструкция улучшила schema success Lightning с 20% до 82,5%, но product accuracy Pro снизилась с 72,5% до 57,5%. Один проход не доказывает причинность; консервативно уточнение оставлено только Lightning, а Ultra/Pro возвращены прежние инструкции. Неудачный вариант и его метрики сохранены целиком. Результаты трёх этапов не смешиваются; финальная версия совпадает с измеренным кодом.

## Методика

Канонический набор — `data/bench/lite_v1.jsonl` (40 кейсов). Это НЕ `data/golden/lite_v1.jsonl` (36 кейсов). Содержимое БД проверено на точное совпадение канала, текста и gold с каноническим набором; исходные идентификаторы восстановлены в `results.jsonl` и CSV. Для типа и продукта N=40, для системы N=8. Контекст клиента и few-shot пустые, используется штатный `build_classify_prompt`, prompt v1.1. Полная схема классификации проверяется локальным валидатором.

Модели запускаются последовательно: Ultra → Lightning → Pro. Scope `GIGACHAT_API_PERS`, один поток генерации. Native `GigaChatProvider`, `ProviderChain(..., append_mock=False)`, строгая проверка TLS с пакетным CA bundle. Суточные/RPM лимиты и доступность ключей проверяет `BenchService`. Перед измерениями реальные остатки проверены через `/balance`; дополнительный консервативный резерв на все три этапа — 2 млн токенов. Остатки аккаунтов и ключи в репозиторий не включены. Проверка `/balance` во время baseline получила 429; автоматического повторения не было, повторная проверка после завершения генераций прошла по обоим ключам.

Backend стенда временно остановлен; `BenchService` работает в одноразовом Compose-контейнере с той же БД и настройками, без lifespan и фоновых agent/twin/ingest worker’ов. Простая остановка симуляции не выключает обработку старой очереди агента: первоначальный API-прогон №1 отменён и исключён из сравнения. Его сохранённые результаты находятся отдельно в `excluded-run-1.json`. После измерений штатный backend восстановлен.

В каждом каталоге: `summary.json` содержит параметры, метрики, версии моделей, SHA исходников/набора/образа и причины ошибок; `ultra.json`, `lightning.json`, `pro.json` — полные снимки `BenchService.detail`; `results.jsonl` и `results.csv` — все 120 результатов; `harness.py` — точный снимок исполнявшегося драйвера (ID набора/профилей относятся к этому стенду), `code-sha256.txt` — хеши модулей из измеренного образа.

## Значение метрик и ограничения

- `accuracy_type`/`accuracy_product`/`accuracy_system` — точное совпадение с размеченными полями; ошибки провайдера и невалидные ответы считаются неверными. Система оценивается только на восьми размеченных кейсах.
- `json_valid_rate` — полное соответствие JSON Schema с первой попытки; синтаксически корректного JSON недостаточно. `tool_success_rate` — соответствие после максимум одной попытки исправления. Банковские инструменты в benchmark не исполняются.
- p50/p95 — latency кейса, включая исправление ответа и OAuth при необходимости; процентиль с линейной интерполяцией. Первые два baseline-кейса Ultra завершились timeout, они включены в метрики. Ошибки инфраструктуры нельзя приписывать качеству классификации модели.
- Токены — сумма `usage.prompt_tokens + usage.completion_tokens` полученных ответов, включая исправления. Расход запроса, отменённого по timeout до получения usage, может быть неизвестен. `requests_total` — учтённые попытки, включая неуспешные логические вызовы; timeout мог произойти до фактической генерации. Это не независимый биллинговый счётчик.
- Для невалидного ответа сохраняется `_benchmark_error.kind=bad_output`, а не сырой текст; корректные parsed-объекты сохранены без ручных изменений.
- Истинные версии моделей — `reported_model_versions`; alias без суффикса в `metrics.model_versions` может относиться к ошибке без ответа провайдера.
- Рублёвые цены профилей не настроены: `cost_rub=null`; исходный `cost_estimate=0` API не означает бесплатное использование.
- Один проход не измеряет стабильность. `stability=null`. Gold не содержит criticality/team: recall критичных, accuracy criticality/route не вычисляются. Seed=42 — метаданные локального прогона, upstream seed не передаётся; temperature=0 не гарантирует детерминизм.
- Результаты — измерение данного набора и конфигурации, а не универсальный рейтинг моделей. Исходные ответы не исправлялись вручную; gold и classify prompt не подгонялись под результаты.

## Исправления

1. Единая temperature=0 только для benchmark; рабочий twin Pro остаётся на temperature=0.7.
2. Общий PERS-слот для генерации и сериализация benchmark разных GigaChat-профилей.
3. Учёт внутренних JSON-repair попыток, токенов и первого валидного ответа; исправлено удвоение расхода ключа при отсутствии `total_tokens`.
4. Невалидный JSON сохраняется как ошибка отдельного кейса, полный набор продолжается. Auth/quota/rate_limit завершают прогон; три последовательных транспортных сбоя останавливают расход. Частичные метрики помечаются `complete=false`.
5. Инструкция structured output только для Lightning различает описание JSON Schema и объект результата; служебные ключи не должны возвращаться как данные. Обязательные model/temperature/stream защищены от переопределения в `extra.request`.

## Воспроизведение

Соберите backend из merged main. Драйвер `final/harness.py` — точный снимок исполнения на этом стенде: dataset_id=3 и profile_id=1/3/2. Перед повтором проверьте соответствие ID в вашей БД и квоты. Укажите доступный для записи каталог как `/reports` при запуске драйвера через `docker compose run --rm --no-deps -T backend python ...`. На время измерений штатный backend должен быть остановлен, после измерений восстановлен через `docker compose up -d --no-deps --wait backend`. Драйвер использует тот же BenchService и параметры Compose, без lifespan приложения и без других вызовов генерации. Не запускайте API/lifespan параллельно: `BenchService.recover()` помечает чужие queued/running прогоны прерванными.
