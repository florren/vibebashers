# Нормализация Lightning → Pro → Ultra — 31.10.2026

По уточнению пользователя Pro становится первым резервом Lightning, Ultra — следующим.
Ролевые main/twin не изменены; используется выбранный ролевой профиль GigaChat-3-Pro.
Общий дедлайн сохранён: 10 с; при последовательных timeout бюджеты 4/3/3 с,
неиспользованное время достаётся следующей модели. Без профиля Pro сохраняются 5/5 с.

## Live-набор

Тот же [набор из 20 текстов](../gigachat-normalize-hitl-2026-10-31/cases.json),
точные normalization prompt/schema, настроенные тарифы/профили текущего стенда.
Команда внутри backend с модулем кандидата:

```sh
python scripts/bench_normalization_timeouts.py --dataset cases.json --output results.json --limits 10
```

[Все результаты](results.json): 19/20 валидных ответов, 11 Lightning и 8 Pro.
Максимум успешного ответа 6296 мс. Все восемь запросов, потребовавшие резерв после
bad_output Lightning, завершились на Pro без Ultra и без replay/mock.

Первый запрос из нового процесса не прошёл: Lightning timeout 4001 мс,
Pro timeout 2999 мс, Ultra timeout 3000 мс, итог 10004 мс с накладными расходами.
В этом процессе OAuth-токены изначально не кэшированы; логи также содержат 429
следующего запроса, обработанный существующим пулом ключей. Причину задержки
первого запроса однозначно не устанавливаем. 10 секунд не гарантируют live-ответ
при любой нагрузке; после дедлайна штатный runtime сохраняет честный replay/mock.
Исходные результаты не исключают первый отказ и не подменяют его прогревом.

## Детерминированные регрессии

Порядок всех трёх моделей, остановка на первом успехе, bad_output/unavailable/timeout,
дедупликация Pro, перенос свободного времени, auth/quota/rate_limit на Pro без повтора
Ultra и суммарный дедлайн. Unit-тесты не обращаются к внешним сервисам.
