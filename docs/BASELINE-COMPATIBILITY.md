# Старый baseline: pg_dump 18 → PostgreSQL 16 (#108)

`lite.dump` остаётся неизменным. Штатный backend использует pg_dump/pg_restore 16.
Старый custom archive 1.16, записанный pg_dump 18, нельзя чинить изменением заголовка.
Подготовка выполняется **в отдельной пустой PostgreSQL 16**, никогда в рабочей БД.

## Подготовка

Нужны окружение `backend/.venv`, pg_restore 18, psql 18 и pg_dump 16. Укажите реальные
пути установленных инструментов; пути ниже соответствуют пакетам PGDG. Передайте
`BASELINE_SCRATCH_URL` через локальное окружение (URI PostgreSQL) с реквизитами
одноразовой БД. Не сохраняйте реквизиты в репозитории или отчёте.

```bash
backend/.venv/bin/python scripts/seed/prepare_baseline.py \
  --source data/baseline/lite.dump \
  --output data/baseline/lite.compatible.dump \
  --pg-restore /usr/lib/postgresql/18/bin/pg_restore \
  --pg-dump /usr/lib/postgresql/16/bin/pg_dump \
  --psql /usr/lib/postgresql/18/bin/psql
```

Скрипт проверяет пустоту БД и major=16, восстанавливает pre-data/data/post-data с
`ON_ERROR_STOP`, применяет Alembic до head и штатный CSI-ремонт. Единственное
преобразование SQL — удаление `SET transaction_timeout = 0` вне COPY-данных:
PostgreSQL 16 такой настройки не имеет. Все остальные SQL-ошибки останавливают работу.
Исходный архив и его SHA256 не меняются; существующий выходной файл запрещено перезаписывать.

Старый baseline исключал `sim_runs`. Для проверки FK скрипт восстанавливает минимальную
метаинформацию из `seed_done` и run_id **самого архива**, без данных живого стенда.
Неизвестные исходные метаданные обозначены в `notes`; это не восстановление утраченных
названий, моделей и времён запусков. Подготовленный архив включает эти записи.

Рядом появляются `.dump.sha256` и `.dump.provenance.json` с хешами источника и результата.
Backend автоматически использует `lite.compatible.dump` только если оба хеша совпадают.
Несовпадение/отсутствие provenance блокирует restore до изменений БД. Новый штатный dump,
изменивший оригинал, требует заново подготовить или убрать прежний совместимый артефакт.
Архивы и их метаданные — локальные приватные данные, в Git их не добавлять.

## Восстановление и recovery

Перед намеренным сбросом рабочего стенда сохраните отдельный полный pg_dump **с sim_runs**
и каталог `data/runs` в приватном месте. Не используйте live dump вместо исторического baseline.
Проверьте prepared-архив в одноразовой БД, затем используйте обычную кнопку восстановления.

Restore сначала генерирует SQL без изменения БД, затем исполняет его одной транзакцией
psql с `ON_ERROR_STOP`. Исходящие FK и trigram-индекс сохранённой `sim_runs` снимаются и
возвращаются в этой же транзакции. FK возвращаются `NOT VALID`: старые записи запусков могут
ссылаться на уже отсутствующие сценарии/профили; новые записи проверяются. Любой ненулевой
exit code — ошибка; при SQL-ошибке вся транзакция отменяется. CSI-ремонт выполняется после
SQL-восстановления; его ошибка по-прежнему блокирует готовность и старт нового запуска.
При такой последующей ошибке восстановите приватный полный backup, если нужно вернуть
предыдущее рабочее состояние. Исходный baseline никогда не заменяется этим backup.

Чтобы отключить подготовленный артефакт, переместите `lite.compatible.dump` вместе с
provenance/sha в приватный архив. Исходный `lite.dump` сохраняется. Не удаляйте одноразовую
БД, пока не проверены результат и контрольные суммы; после проверки её можно убрать.

Проверка реального старого файла от 28.10.2026: source SHA256
`efd316e8b838d0e007f9120c488570c7da0dcc5641f9c8a3516b051d1f1b9193`.
Конвертация, два восстановления, Alembic `0010`, 200 клиентов, 800 сигналов,
CSI 480/480; повторный ремонт добавил 0 записей. Рабочая БД при проверке не использовалась.
