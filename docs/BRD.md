# Бизнес-требования (BRD) на разработку MVP AI-агента для демо-стенда

## 1. Цель и контекст проекта
**Цель:** Разработать демо-стенд ИИ-агента для демонстрации его возможностей по автономному решению клиентского негатива на внешних площадках и пресечению комплаенс-рисков (мисселлинга) в офлайн-отделениях в режиме реального времени (NRT).
**Аудитория демо:** Топ-менеджмент банка (C-level), руководители направлений (Retail, Compliance, Customer Experience).
**Ограничения MVP:** Для обеспечения стабильности показа на демо допускается использование мок-сервисов (mock) вместо реальных банковских АБС, биллинга и CRM. Аналитическая и логическая часть агента должна работать в реальности.

---

## 2. Сценарий 1: Проактивный парсинг внешних площадок и автономное решение
**Описание:** Агент находит негативный отзыв на внешней площадке (Банки.ру / Telegram), идентифицирует клиента, выявляет ошибку банка (списание комиссии) и самостоятельно проводит возврат с публикацией ответа.

### 2.1. Функциональные требования (FR)
*   **FR 1.1. Модуль мониторинга (Слушатель):** Система должна уметь забирать текст отзыва по API или из эмулятора внешней площадки (веб-форма, имитирующая пост).
*   **FR 1.2. NLP-анализатор (Извлечение сущностей):** Агент должен извлекать из неструктурированного текста:
    *   Тональность (Sentiment): Оценка уровня негатива (0-100%).
    *   Намерения (Intent): Угроза оттока ("закрою счет").
    *   Сущности (NER): Сумма (450 руб.), продукт (дебетовая карта), косвенные контакты (никнейм/маскированный номер).
*   **FR 1.3. Модуль идентификации (Матчинг):** Агент должен сопоставить извлеченные косвенные данные с базой клиентов (Mock CRM) и вернуть ID клиента.
*   **FR 1.4. Модуль принятия решений (Decision Engine):** 
    *   Проверка транзакций клиента по ID (Mock Processing).
    *   Поиск события, вызвавшего негатив (списание 450 руб.).
    *   Проверка бизнес-правила: "Если оборот выполнен по QR-коду, но комиссия списана -> Ошибка системы -> Инициировать возврат".
*   **FR 1.5. Модуль генерации ответа (NLG):** Агент должен сформировать персонализированный ответ для публикации, используя LLM, с указанием факта возврата и извинениями.

### 2.2. Требования к интеграциям (для демо)
*   **Эмулятор внешней площадки:** Простой UI, имитирующий ленту Банки.ру/TG.
*   **Mock CRM & АБС:** База данных с предзаполненным профилем "пострадавшего" клиента (история транзакций, статус выполнения оборота).

### 2.3. Критерии успеха на демо
Зритель видит, как публикация нового отзыва мгновенно (до 5-10 секунд) триггерит цепочку действий агента на экране логов, баланс клиента в "АБС" меняется, и под постом автоматически появляется релевантный ответ агента.

## 3. Сценарий 2: Аудиомониторинг (NRT) и пресечение мисселлинга
**Описание:** Агент слушает диалог менеджера и клиента в отделении, фиксирует нарушения скрипта (мисселлинг), и при достижении лимита нарушений (3+) отправляет пуш-уведомление руководителю.

### 3.1. Функциональные требования (FR)
*   **FR 2.1. Потоковое распознавание речи (STT):** Агент должен принимать аудиопоток (с микрофона ноутбука на демо) и переводить его в текст в режиме реального времени (Streaming Speech-to-Text).
*   **FR 2.2. Разделение спикеров (Diarization):** Система должна различать речь сотрудника банка (Канал 1) и клиента (Канал 2). Анализу на мисселлинг подвергается только речь сотрудника.
*   **FR 2.3. Детектор мисселлинга (NLP-классификатор):** Агент должен выявлять в тексте сотрудника заданные паттерны:
    *   Жесткая привязка услуги ("Без страховки не одобрят").
    *   Подмена понятий ("Это как вклад, только лучше").
    *   Утаивание информации ("Подпишите, это формальность").
*   **FR 2.4. Менеджер состояний (State Machine):** Система должна вести счетчик триггеров мисселлинга в рамках одной сессии (одного диалога). 
*   **FR 2.5. Модуль алертинга:** При достижении счетчика значения `X >= 3`, система должна немедленно сгенерировать алерт и отправить его по WebSocket/Push на интерфейс руководителя.

### 3.2. Требования к UI/UX для демо-стенда
*   **Экран мониторинга:** Разделенный экран (Split-screen). 
    *   *Левая часть:* Бегущая лента транскрибации диалога (чат), где красным цветом подсвечиваются выявленные фразы мисселлинга.
    *   *Правая часть:* Счетчик нарушений (0/3, 1/3, 2/3, 3/3 -> ALERT!) и профиль менеджера.
*   **Интерфейс руководителя:** Эмуляция экрана планшета/смарт-часов, на который падает всплывающее уведомление с номером стола, ФИО сотрудника и сутью нарушения.

### 3.3. Критерии успеха на демо
Зритель (демонстратор) разыгрывает диалог в микрофон. Текст мгновенно появляется на экране. При произнесении третьей запрещенной фразы интерфейс окрашивается в красный, и звучит/появляется NRT-уведомление на эмуляторе устройства руководителя. Задержка (latency) от произнесения слова до реакции счетчика не должна превышать 2-3 секунды.

## 4. Общие нефункциональные требования
*   **Визуализация работы ("Под капотом"):** Для демо-целей интерфейс агента должен иметь режим "Log/Debug", где зрители могут видеть, как именно "думает" ИИ (проценты уверенности модели, извлеченные JSON-сущности). Это повышает доверие к технологии.
*   **Отказоустойчивость демо:** На случай отсутствия интернета в помещении для демо или падения внешних STT/LLM API, в системе должны быть "зашиты" заранее записанные аудиофайлы и мок-ответы нейросетей, которые можно запустить нажатием скрытой кнопки.
