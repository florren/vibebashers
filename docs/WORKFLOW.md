# Рабочий цикл одной командой: `cx`

Вам не нужно помнить про worktree, ветки, `cd`, флаги Codex и `gh`. Всё это делает `scripts/cx.py` — один скрипт с несколькими командами. Запускается из папки основного клона (`vibebashers/`), откуда угодно внутри неё.

## Что такое worktree, в двух предложениях

Worktree — это вторая папка с тем же репозиторием, но переключённая на другую ветку. Благодаря этому агент для карточки T-213 работает в `../wt/T-213/`, агент для пакета B04 — в `../wt/B04/`, а ваша основная папка всегда остаётся на чистом `main`: они не мешают друг другу и не затирают файлы. `cx` создаёт эти папки, следит за ними и удаляет после слияния — вы в них не заходите.

Структура на диске:
```
~/dev/
├── vibebashers/     ← основной клон, всегда main; отсюда запускаете cx
└── wt/
    ├── B01/         ← создано cx start B01, удалится после cx done
    └── T-213/
```

## Пять команд, которые нужны каждый день

```bash
python scripts/cx.py next              # что брать: пакет из PLAN-14D на сегодня (или карточку без незакрытых зависимостей)
python scripts/cx.py start B01         # создать worktree, подготовить окружение, собрать промпт, запустить Codex без участия человека
python scripts/cx.py check B01         # прогнать проверки (contracts, owners, lint, test) и сохранить лог
python scripts/cx.py pr B01            # закоммитить остатки, перебазировать на main, запушить, открыть PR с отчётом агента
python scripts/cx.py done B01          # после слияния PR: удалить worktree и ветку
```

Вспомогательные: `status` (таблица всего, что в работе, с состоянием PR и CI), `fix <id>` (скачать лог упавших проверок и запустить агента «исправь»), `fix <id> --rebase` (конфликт с main), `clean` (done для всего слитого), `doctor` (проверка инструментов), `open <id>` (путь к worktree, если очень хочется зайти руками).

Чтобы не писать `python scripts/cx.py` каждый раз: `alias cx='python ~/dev/vibebashers/scripts/cx.py'` в `~/.bashrc`.

## День целиком

```
09:00  cx status                  # что висит с вечера: слитые → cx clean
       cx next --seat S1          # → «пакет B04 Агент-ядро»
       cx start B04               # Codex работает 1–4 часа; терминал можно свернуть
       cx next --seat S3          # параллельно второе место, если есть квота
       cx start B21 --agent cursor   # или cursor/manual для другого инструмента
13:00  cx check B04               # зелёное? → cx pr B04. Красное? → cx fix B04
       cx pr B04                  # ссылка на PR; CI запускается сам
17:00  cx status                  # проверки SUCCESS → нажать Merge в PR (или подождать владельца L1, если метка contract-change)
       cx done B04
```

Вы принимаете одно решение за цикл: нажать «Merge» в зелёном PR. Всё остальное — скрипт и CI.

## Что делает `cx start` на самом деле

1. `git fetch origin`, `git worktree add ../wt/<id> -b feat/<id> origin/main` (или подхватывает существующую ветку, если worktree уже был).
2. Копирует `.env` из основной папки, выполняет `uv sync --frozen` и `npm ci`, если код уже есть.
3. Собирает промпт из `scripts/prompts/task.md` + карточки/пакета (с урезаниями из PLAN-14D) и сохраняет в `../wt/<id>/.cx/prompt.md`.
4. Запускает `codex -a never -s workspace-write -C ../wt/<id> --add-dir <основной .git> exec -o .cx/report.md -` — неинтерактивно, с правом писать в рабочую папку и ходить в сеть за зависимостями. `--add-dir` на `.git` основного клона нужен потому, что worktree хранит свои метаданные там, иначе песочница Codex не даст закоммитить.
5. Записывает состояние в `.cx/state.json` (в `.gitignore`), печатает отчёт агента и подсказку, что делать дальше.

`--agent cursor` вместо Codex открывает папку worktree в Cursor и показывает, откуда взять промпт; `--agent manual` только готовит папку и промпт. `--interactive` запускает Codex в диалоговом режиме в той же папке, если хотите наблюдать и подсказывать.

## Если что-то пошло не так

| Симптом | Что сделать |
|---|---|
| `cx start` ругается, что worktree уже есть | это нормально: ветка продолжается; чтобы начать заново — `cx done <id> --force`, затем `cx start` |
| `cx check` красный по `owners` | агент тронул чужой слой; `cx fix <id>` с текстом «перенеси изменения в свой слой или опиши их в отчёте»; если изменение действительно нужно — PR получит метку `cross-layer`, его сливает владелец L1 |
| `cx pr` говорит «конфликт с main» | `cx fix <id> --rebase` — агент сам разрешит конфликты и повторит проверки |
| В PR висит «Expected — waiting for status» | ruleset включён раньше первого прогона CI — см. `docs/REPO-BOOTSTRAP.md` шаг 1 |
| Codex упёрся в лимит | `cx start <id> --agent cursor` — та же папка и тот же промпт, другой инструмент; состояние ветки сохраняется |
| Хочется посмотреть глазами | `cursor $(python scripts/cx.py open <id>)` |

## Требования

`git`, `gh` (GitHub CLI, один раз `gh auth login`), `codex` (`npm i -g @openai/codex`, вход через ChatGPT), опционально `uv`, `node`, `cursor` в PATH. Проверка: `cx doctor`. Основной клон должен указывать на GitHub (`origin`), зеркало в GitVerse делает CI сам.
