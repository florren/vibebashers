# Разделение разработки по слоям и людям (1–3 участника, разные инструменты)

Документ для команды без выделенного техлида-ревьюера. Цель: чтобы участники с разными harness (Codex, Cursor, Claude Code и т. п.) не мешали друг другу, а слияние веток не требовало человека, который «следит, кто что куда». Правила ниже обязательны для всех кодирующих агентов; AGENTS.md §5.1 ссылается сюда.

## 1. Пять слоёв и их границы

Слой = набор каталогов + набор субагентов из карточек. Карточка принадлежит ровно одному слою (поле «Слой» в карточке, колонка в `docs/tasks/README.md`). Агент, работающий над карточкой, имеет право менять файлы только внутри каталогов своего слоя плюс общие исключения из раздела 3.

| Код | Слой | Каталоги (владение) | Субагенты карточек | Карточек / в демо-минимуме | Пик |
|---|---|---|---|---|---|
| `L1` | Базис | `contracts/`, `backend/app/db/`, `backend/alembic/`, `backend/app/llm/`, `backend/app/replay/`, `backend/app/contracts/`, `backend/app/i18n/`, `frontend/src/shared/i18n/`, `scripts/` (кроме `seed/`), `install.sh`, `docker-compose.yml`, `Makefile`, `.github/`, `docs/`, `README.md`, `AGENTS.md`, `CLAUDE.md`, `.cursor/` | SA-Infra, SA-DB, SA-LLM, SA-Refs, SA-i18n, SA-Docs | 36 + 6 (v1.5) / 29 + 2 | волны 1–2, 7 |

Общие каталоги с совместным доступом (любой слой может добавлять, но не переписывать чужое): `backend/tests/unit/`, `backend/tests/integration/`, `frontend/src/shared/api/` (только сгенерированные файлы через `make sync-contracts`).

Почему именно так: в проекте два «бэкенда» разной природы — симулятор с данными (детерминизм, сид, экономика) и агент с LLM-контурами (промпты, инструменты, STT). Они конфликтуют друг с другом сильнее, чем фронт с бэком; разводим их по слоям L2/L3. Контракты (`contracts/`) — единственная точка, через которую слои договариваются, поэтому они в L1 и меняются одним человеком.

## 2. Раскладка по числу участников

Назначение слоёв фиксируется в `CODEOWNERS` (кто за что отвечает) — это единственное место, которое нужно править при смене состава.

**Один участник.** Все слои — у него; порядок строго по волнам из `docs/tasks/README.md`. Внутри дня: сначала карточки L1/L2 (фундамент и данные), затем L3, фронт (L4) — только когда бэк уже отдаёт реальные ответы, а не заглушки. Цель — демо-минимум (112 карточек), всё остальное помечено «можно отложить».

**Двое.**
- Участник A: `L1 → L2 → L5` («фундамент и правда данных»). Базис заканчивается к концу волны 2 — ровно когда симулятор набирает объём; в волнах 4–5 переключается на сценарии и тесты.
- Участник B: `L3 → L4` («мозг и витрина»). Тот, кто пишет агента, лучше всех знает, что показывать на экранах «Под капотом», `/feed`, `/compliance`.
- Граница — `contracts/` и события; никто не правит каталоги другого. Запросы на изменение контракта — через карточку с меткой `contract-change` участнику A.

**Трое.**
- Участник A: `L1 + L2`.
- Участник B: `L3`.
- Участник C: `L4 + L5`. Фронт стартует с волны 1 (T-002 каркас Vite) и живёт на 501-заглушках и примерах из `contracts/events/**/examples` до волны 3 — для этого в каждой JSON-схеме есть `examples`, а в OpenAPI — заглушки по тегам (T-200, T-221).

**Больше трёх.** Имеет смысл отделить только два дополнительных слоя: «Данные и промпты» (корпуса, наборы бенчмарков, промпты — текстовая работа без кода) и «Демо и подстраховка» (кассеты, аудио, демо-скрипт, меню демонстратора — критично в последнюю неделю). Другие деления создают больше стыков, чем экономят.

## 3. Режим без ревьюера: как сливать ветки, когда некому смотреть PR

Принцип: **проверяет машина, а не человек**. Человек нажимает «слить», если все проверки зелёные, и читает только отчёт агента в карточке.

Машина — это GitHub Actions (`.github/workflows/ci.yml`): на каждый PR и пуш в `main` поднимается чистая виртуальная машина и выполняются job'ы `contracts` (схемы, OpenAPI, карточки, парсинг DDL), `db` (PostgreSQL 16: `schema.sql` на чистой базе, идемпотентные миграции дважды, инварианты, позже alembic), `owners` (границы слоя по CODEOWNERS; только для PR) и `tests` (lint, pytest, vitest, build — после появления кода). Ruleset ветки `main` требует PR, зелёные `contracts`/`db`/`tests` и актуальность ветки; approvals — 0. Настройка — `docs/REPO-BOOTSTRAP.md`.

1. **Одна карточка — одна ветка — один PR** (AGENTS.md §5 п. 12). Имя ветки `feat/T-213-router-tools`; в описании PR — ссылка на карточку.
2. **Граница слоя проверяется автоматически.** `python scripts/check_owners.py --base main` сравнивает изменённые файлы с `CODEOWNERS` и слоем карточки (из имени ветки); чужие файлы → проверка красная. Исключение — метка `contract-change` или `cross-layer` в заголовке PR и явное перечисление чужих файлов в описании; такие PR сливает только владелец L1.
3. **Агент обязан перед PR выполнить и приложить вывод**: `make lint`, `make test`, `python scripts/contracts_check.py`, `python scripts/check_owners.py`, и заполнить блок «Отчёт» карточки (что сделано, что не сделано, что проверено руками, риски). PR без отчёта не сливается.
4. **Самопроверка по DoD** (AGENTS.md §8) — чек-лист в шаблоне PR; агент отмечает пункты сам, человек бегло смотрит.
5. **Что требует подтверждения человека (единственные три случая)**: изменение `contracts/` (L1), всё, что касается денег и HITL (`refund_fee`, политики, лимиты), и удаление/переименование существующих файлов других слоёв. Всё остальное сливается по зелёному CI.
6. **Конфликты слияния решает тот, чья ветка позже.** Перед PR — `git rebase main`; агенту так и формулируется: «подтяни main, разреши конфликты, прогони проверки заново».
7. **Контракт меняется только вперёд.** Новый эндпоинт/поле — да; переименование/удаление — только через миграцию и версию (AGENTS.md §7). Это снимает 90 % ситуаций, когда ветка одного ломает другого.
8. **Ежедневная синхронизация.** Каждый участник раз в день: `git pull`, `make sync-contracts`, `make test`. Расхождение контракта и кода ловит `scripts/check_openapi_drift.py` в CI.

## 4. Распорядок участника без опыта разработки

Весь цикл — через `scripts/cx.py` (подробно: `docs/WORKFLOW.md`). Ни `git checkout`, ни `cd` в worktree, ни флаги Codex руками не нужны.

```bash
python scripts/cx.py next --seat S1    # что брать сегодня (пакет из PLAN-14D или карточка без незакрытых зависимостей)
python scripts/cx.py start B04         # worktree + окружение + промпт + Codex без участия человека
python scripts/cx.py check B04         # проверки; красное → python scripts/cx.py fix B04
python scripts/cx.py pr B04            # PR с отчётом агента; CI запускается сам
python scripts/cx.py status            # проверки SUCCESS → нажать Merge в PR
python scripts/cx.py done B04          # убрать worktree после слияния
```

Единственное решение человека за цикл — нажать «Merge» в зелёном PR без меток `contract-change`/`cross-layer`. Промпт агенту собирается из `scripts/prompts/task.md` и карточки/пакета автоматически — один и тот же каждый раз.

Чего не делать: не просить агента «сделать сразу три пакета», не сливать красные PR «чтобы не терять время», не править чужие каталоги вручную, не заходить в `../wt/*` без нужды.

## 5. Сколько времени займёт разработка агентами

### Объём
После v1.5 добавлена 41 карточка (T-223…T-263, волны 7–9) — оценка пересчитывается индексом `docs/tasks/README.md`; ниже цифры по состоянию v1.4. Демо-минимум v1.5 — 15 карточек (E22, E23 без «Графа», T-257, T-261, T-263): примерно 3–4 человеко-недели агентной работы; остальные 26 карточек (кабинет, CSI/ВСП, дизайн v2) откладываются без потери показа цикла «сигнал → решение → сообщение клиенту» и поиска.

По оценкам карточек: все 150 карточек ≈ 248 человеко-дней; демо-минимум (112 карточек) ≈ 198; ядро без контуров BRD/ДТЗ (72 карточки волн 1–3 плюс замыкание) ≈ 132. Это оценки «как если бы писал человек»; агент тратит меньше календарного времени, но ограничен квотами.

### Пропускная способность одного рабочего места (ориентиры, не гарантии)
- **ChatGPT Plus (Codex)**: OpenAI оценивает 15–160 локальных сообщений за пятичасовое окно на GPT-6.1 Sol плюс недельный лимит, размер которого не публикуется; CLI, расширение, приложение и облако тратят одну квоту, облачные задачи — быстрее. Карточка M с правками и прогоном тестов — это 20–40 сообщений агентного режима, то есть 1–2 карточки на окно; в день при дисциплине — 2–3 окна. Недельный лимит по наблюдениям сообщества заканчивается раньше, чем сумма окон, поэтому реалистично **10–15 карточек в неделю** на одно место Plus; покупка кредитов снимает ограничение, но превращает квоту в деньги.
- **Cursor Pro**: пул 20 $ в месяц на сторонние модели по API-ценам плюс отдельный щедрый пул на собственные модели Cursor. На Claude/GPT — **5–8 карточек в неделю**, на Composer для фронтовых правок — заметно больше, но с большим числом итераций.
- **Человек без опыта разработки** как узкое место: чтение отчётов, нажатие «слить», прогон демо, ответы на вопросы агента — 1–2 часа в день на каждые 10 карточек в неделю. Больше трёх параллельных агентных сессий один человек не обслуживает.

### Календарная оценка

| Состав | Карточек в неделю | Ядро (72) | Демо-минимум (112) | Всё (150) |
|---|---|---|---|---|
| 1 человек, Plus + Cursor Pro | 15–20 | 4–5 нед. | 6–8 нед. | 8–10 нед. |
| 2 человека, у каждого Plus или Cursor | 25–35 | 2,5–3 нед. | 3,5–4,5 нед. | 4,5–6 нед. |
| 3 человека | 35–50 | 2 нед. | 2,5–3,5 нед. | 3,5–4,5 нед. |

К любому варианту прибавить **одну неделю** на интеграцию и репетиции: запись кассет replay, проверка Vosk на целевой машине, прогон демо-скрипта. Сроки сокращаются примерно на треть при переходе хотя бы одного места на Pro-тариф (нет пятичасового окна) или при докупке кредитов на пиковые недели 3–4 (узлы агента и экраны).

### Если дедлайн короче
Последовательность урезания без потери показа: сначала всё, что помечено «можно отложить» в карточках; затем контур ДТЗ сверх демо-минимума (T-209, T-211); затем аудиомониторинг с микрофона (оставить пакетный режим транскриптов — сценарий 10 и файл для сценария 9); затем внешние площадки (оставить сценарий 8 на кассете). Ядро (72 карточки) с кассетами — это нижняя граница, с которой демо всё ещё проходит.

## 6. Что проверить в первый день совместной работы
1. `CODEOWNERS` заполнен реальными логинами GitHub (владелец репозитория — `@florren`); `scripts/check_owners.py` проходит на пустом diff; ruleset `main` включён по `docs/REPO-BOOTSTRAP.md`.
2. У каждого участника свой harness читает инструкции: Codex — `AGENTS.md` (поднять `project_doc_max_bytes` в `~/.codex/config.toml`, файл больше 32 КиБ), Cursor — `.cursor/rules/` + `AGENTS.md`, Claude Code — `CLAUDE.md`.
3. Все трое открыли PR из тестовой карточки T-001-подобного размера и слили его по правилам раздела 3 — процесс отработан до того, как он понадобится под нагрузкой.
