# ADR-0026: сброс банка сохраняет рабочую конфигурацию

Статус: принято по требованию автоматического развёртывания, 09.11.2026.

## Проблема

Seed создаёт baseline до настройки моделей в мастере. Сравнение сохранённого
LLM fingerprint с текущим каталогом блокировало reset после настройки ключей,
ролей или лимитов. Возврат старой конфигурации вместо отказа был бы небезопасен.
Кроме того, оставшийся compatible-архив другого поколения перекрывал штатный
новый PG16 dump и приводил к отказу по provenance.

## Решение

Банковские данные и время восстанавливаются из baseline, рабочая конфигурация
сохраняется. В TOC restore исключены `llm_profiles`, `llm_api_keys`,
`llm_cassettes` и их identity sequences/объекты, а также целиком `llm_runtime` и
`channel_runtime`, включая архивы, созданные до этих правил.

Текущие `settings.llm`, canonical `settings.llm_keys` и `setup_payload.llm`
сохраняются через временные таблицы в той же psql-транзакции. Остальные банковские
настройки возвращаются из архива. Текущие профили, ciphertext ключей и sequences
проверяются на точное совпадение до COMMIT. Ошибка откатывает весь SQL restore.
Профили/ключи не дешифруются и не выводятся в SQL-скрипт или metadata.

Начальный архив, metadata и checksum автоматически создаёт существующий seed
установщика. Временные объекты создаёт сам restore; постоянная DDL/миграция и
ручная подготовка не нужны. Native dump, связанный собственным metadata digest,
имеет приоритет. Compatible-копия используется только как явно связанный
артефакт legacy-подготовки с прежними проверками source/output hashes.

Fingerprint LLM в metadata описывает создателя архива, но не предписывает откат
текущих моделей. Сохраняются проверка hash выбранного файла, DB contract,
canonical credential registry, текущие role/binding guards и maintenance boundary.
Неизвестный расход не становится известным, origin/counters не обнуляются,
повторные внешние отправки не разрешаются. SQL guard не является сверкой расхода.

## Проверка и эксплуатация

Регрессия: чистые миграции и автоматический seed; настройка LLM после seed;
оставшаяся compatible-копия; HTTP reset; банковские данные/время восстановлены,
настройки/ключи/кассеты/аудит/доставка сохранены. Дополнительно проверяются старый
полный архив и инъекция SQL, меняющего профиль: guard отменяет всю транзакцию.

Нельзя изготовлять новый «стартовый» архив из текущего изменённого банка для
снятия ошибки hash. Повреждённый или несовместимый DB contract по-прежнему
блокируется до эффектов. Импорт действительно старого PG18 формата остаётся
отдельным сценарием, а не необходимым действием после штатного развёртывания.

Rollback к прежнему image не меняет DDL или ciphertext, но возвращает прежний
отказ при отличающемся LLM fingerprint. Рабочая БД не сбрасывается при обновлении
кода; фактический reset выполняет пользователь отдельным подтверждённым действием.
