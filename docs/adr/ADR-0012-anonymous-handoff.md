# ADR-0012 — Приём анонимного обращения и ставка неизвестного продукта

Статус: принято по прямому запросу пользователя 29.10.2026. Разделы ТЗ: 9.2–9.3, 14.4, 27; сценарий 4.

Отсутствие установленного клиента не блокирует классификацию содержания, выбор продукта/команды и создание либо привязку тикета. Вопросы и жалобы передаются ответственной команде по существующим правилам; при отсутствии маршрута — `team_cx`. Благодарность без проблемы сохраняет прежний путь без инцидента. Клиент получает общее подтверждение приёма и сообщение о последующем решении в текущем канале. Обязательный запрос телефона, имени или номера карты для первичного приёма исключён. Идентификация по уже предоставленным сведениям по-прежнему выполняется.

Причины HITL, правила возвратов, лимиты и требования идентификации для денег не ослабляются. Если решение требует человека, до ожидания выполняется только безопасный приём: маршрут в команду, уведомление команды/клиента и обязательная эскалация. Возвраты, подарки и предложенные действия остаются за HITL. Инструменты записи и их идемпотентность сохраняются; checkpoint содержит уже выполненные действия, чтобы при продолжении не повторять приём.

Для инцидента без определённого продукта применяется `economics_settings.fallback_rate_code` (по умолчанию `bank_average`), даже если известны система или канал. Это явное изменение приоритета выбора ставки по запросу пользователя; обычный выбор для известного продукта и специальная стоимость мисселлинга сохраняются. Формула dCLTV, вероятности, коэффициенты удержания и суммы справочника не меняются. Средняя ставка — оценка потери при уходе, а потенциальный риск инцидента дополнительно учитывает множители формулы. У анонима эта оценка не называется персональным CLV. При отсутствии настройки средней ставки возвращается явная ошибка вместо выдуманной суммы.

Возврат прежнего поведения — revert PR; миграций БД и сброса данных не требуется. Ранее созданные запросы идентификации автоматически не удаляются и не переигрываются.

HTTP `/api/ingest/messages` после commit дополнительно вызывает `AgentService.submit`, сохраняя исходный `signal.received` для других потребителей. Это устраняет зависимость нового обращения от готовности LISTEN во время startup recovery. Повторные одновременные submit одного signal_id объединяются в одну задачу; завершённый проход защищён существующей проверкой process_signal. Внешние адаптеры по-прежнему используют события. Фоновое восстановление старых задач и их данные не удаляются.

После подтверждённого устранения (`verified=true`) финальное уведомление отправляется по исходным signal_id и каналу и для клиента без client_id, затем инцидент закрывается. Проверка verified не снимается; при отсутствии подтверждения ни закрытия, ни финального сообщения нет. В сообщение передаётся тело шаблона `resolved`, а не его тема.
