# ADR-0024 — Предложение отдельной demo-policy поведения клиентов

- Статус: **предложен для review, не принят**.
- Дата: 02.11.2026.
- Решение: пользователь запросил подготовку отдельной demo-policy. Согласия
  на значения, runtime, миграции и изменение действующих defaults **нет**.
- Основания: ТЗ §4.5, ADR-0006, T161; pure checkpoint `0d78205`.
- Предлагаемая конфигурация: [demo_policy.review.yaml](../../data/behavior/demo_policy.review.yaml).

## Контекст

Параметры психотипов заданы в data/psychotypes.yaml, но seg_mult, retained threshold,
компонентные наблюдения и интерпретация repeat/cadence/patience ранее не утверждены.
Демо должно показать разные реакции без выдачи синтетических коэффициентов за
калиброванную модель реального клиента. Нужен воспроизводимый конкретный вариант,
который человек может принять или отклонить перед реализацией.

## Предложение — все новые числа являются синтетическими допущениями

1. **Сегменты:** все семь явных seg_mult = 1.0. Это нейтральный контрольный вариант,
   не reuse priority_multiplier и не предположение о риске отдельных сегментов.
   Различия сервисных ожиданий уже присутствуют в существующем first_response_min;
   p_complain, веса, эластичности и base hazard из психотипов не меняются.
2. **Порог:** retained_threshold = 0.550 после округления полного weighted sum
   care до трёх знаков ROUND_HALF_UP. При реальном разрешении всех проблем и
   достижении порога — retained. Ниже порога — satisfied без утверждения retained
   или churned. Это не основание для денежного действия/новой формулы экономики.
3. **Care:** шесть компонент [0,1], исходные веса психотипа, без повторной
   нормировки/накопления бонуса за количество сообщений. Начальные значения 0
   означают отсутствие подтверждённой положительной заботы, не доказанный негатив.
   Для известного ещё не нарушенного SLA — provisional component=1; неизвестный
   SLA остаётся 0. Breach/пропущенный обязательный отчёт навсегда обнуляет эту
   компоненту текущей episode, даже после позднего решения.
4. **Коммуникация:** proactive засчитывается только фактически затронутому клиенту
   до первой жалобы и в причинной scope episode. Speed — первый содержательный
   доставленный ответ: 1 до текущего segment deadline, затем линейно до 0 при
   удвоенной задержке. Это care-оценка, не изменение SLA producer. Gift_offer,
   dm_invite и внутренний team_notice не объявляются содержательным ответом.
   Тон/объяснение — только видимый клиенту корректный текст, не внутренний reasoning.
   Неизвестный/некорректный шаблон не добавляет положительный credit; нарушение
   запрещённых фраз снижает tone. Список явных template scores есть в YAML.
5. **Подарок:** только уже состоявшийся existing gift task status=done,
   payload.issued и sent/delivered gift_offer. У бонусов fit равен текущей
   gift_elasticity, у партнёрской привилегии — privilege_elasticity; берётся max,
   не сумма нескольких выдач. Personal_call сам по себе не доказывает факт звонка.
   Никакой выдачи, refund, суммы, лимита или обхода HITL эта policy не инициирует.
6. **Repeat:** bool «была хотя бы одна фактическая повторная жалоба», не счётчик.
   p_repeat разыгрывается единожды для просроченного реально отправленного сигнала;
   отрицательный исход не превращается в draw на каждом следующем тике. Реальный
   внешний повтор потребляется как факт, а не запускает второй random draw.
7. **Hazard:** точная формула ТЗ. Один draw на логической 15-минутной UTC-границе,
   только waiting/churn_intent и симулируемые free/scenario. Хвостовые SLA batch
   ticks не дают дополнительных draw; pause не догоняется реальным временем.
   Профиль проверяется на экстремумах всех психотипов/сегментов: raw вне [0,1]
   отклоняет профиль до эффектов. Формула не clamp'ится и не делится на число
   тиков в сутках. Решение использует raw до четырёхзначного округления колонки
   hazard; округлённая колонка не становится новой вероятностью при restart.
8. **Complaint/silent decline:** p_complain и delay неизменны. silent_decline_prob
   трактуется условно после «не жаловаться». При отсутствии жалобы клиент всё
   равно ждёт решения, но не создаётся фиктивный signal/SLA. Для silent activity
   предложен multiplier=0.5; его применение требует отдельного T162 interface review.
   Вес outbound proactive исключается из inbound complaint channels, остаток явно
   нормируется (у silent_churner chat 2/3, email 1/3). При пустом остатке — отказ,
   а не fallback chat. Исходный каталог не переписывается.
9. **Patience:** единственный uniform draw из текущего patience_days при создании
   episode; дробные рабочие дни переводятся в 9-часовые интервалы существующим
   add_working_hours. Пн–пт 09–18 MSK, без заявления о производственном календаре.
   Restart/new failure не продлевает deadline. Истечение нерешённой episode
   фиксирует eligibility для отдельного review T164, не создаёт account_closure.
10. **Dedup:** одно current state на (run_id, client_id), множество причин внутри episode.
    Известные fault_id/op_id связываются по фактическим DB-связям, не fuzzy времени.
    Fault.started и его failed operations не дают повторных p_complain/delay draw.
    Новый regression fault — новая причина со ссылкой, а не дубликат старого fault.
    Receipt проверяется до RNG. Компоненты, таймеры, receipt, signals и RNG должны
    попасть в одну owned simulator transaction; никакой memory-only очереди.

## Числовые следствия, которые нужно рассмотреть человеку

[Воспроизводимый JSON](../reviews/T-161-demo-policy-sensitivity.json) строится
offline-скриптом scripts/reviews/behavior_demo_review.py через существующую pure
hazard-функцию. Это расчёт гипотез, не реальное наблюдение/калибровка.

- У loyal_pragmatic при неизменном waiting без repeat/breach raw за тик равен
  0.020/0.015/0.010 для care=0/0.5/1. За 96 независимых draw при неизменном состоянии
  вероятность хотя бы одного **churn intent** — 85.62%/76.56%/61.90%.
- У silent_churner соответствующие суточные числа — 99.97%/99.11%/78.74%.
  Высокий cumulative эффект текущего каталога не скрывается. Это **не** вероятность
  реального ухода/закрытия счёта/денежной потери; resolution, patience и T164 иные.
- Максимум raw текущего proposal: 0.216 (silent, care=0, repeat=true, breach=true).
  Большие будущие параметры могут нарушить domain; тогда требуется явный отказ
  и новая версия policy, не беззвучное ограничение результата.
- Своевременный понятный ответ+SLA+корректный тон без proactive/gift дают care:
  loyal 0.75, anxious 0.60, demanding 0.85, public 0.75, silent 0.30,
  bonus_hunter 0.35, novice 0.80, status 0.75. Порог 0.55 пропускает anxious,
  а 0.65 — нет. Silent с проактивностью получает 0.90; bonus_hunter с гипотетическим
  уже выданным уместным подарком 0.89. Это не рекомендация выдать подарок.
- После нарушения тона status_oriented в этом примере остаётся ровно 0.55.
  Proposal не вводит hard veto: ТЗ требует снижения, а не безусловного запрета
  retained. Этот граничный эффект порога должен быть явно принят/изменён при review.
- У silent вероятность activity decline для одной новой episode:
  (1−0.10)×0.70=0.63. Значение0.70 не выдаётся за безусловную вероятность.

## Последствия и обязательные границы реализации

Этот ADR и YAML **не активируют runtime**. Значения не production defaults и не
утверждение о поведении реальных клиентов. Действующие psychotypes, segments,
gifts, формулы денег/HITL и pure core не изменены. Файл .review не является
loader input ни для seed, ни для приложения; автоматической активации не будет.

После review нужны отдельные изменения внутреннего typed component snapshot и
возвращаемого результата: текущая score-only CareStrategy не должна скрыто хранить
компоненты в closure/памяти. Нужны durable timer/receipt schema 0017 после chain
review, снятие конкурирующей прямой записи care в TwinService, общий state writer
и process-crash proof. Satisfaction двойника остаётся наблюдением; оно не
подменяет care и не порождает вторую параметрическую реакцию на тот же notification.

Изменение T015/template catalog перед wire требует сверки eligibility и видимого
текста. Существующие статусы sent/delivered — факты доставки, не изменение API.
Live-контур этим вариантом не подключается к сим-часам. T164/T165 сохраняют свои
review boundaries; реальный GigaChat, счета клиентов и новые деньги не затрагивались.

Для принятия нужны отдельное человеческое решение по значениям/семантике и
проверки конкретной реализации. Запрос «подготовьте demo-policy» не равен такому
решению и не даёт разрешения включить её в runtime.

## Проверка этого proposal

Offline generator повторно создаёт sensitivity JSON с hash самого YAML и трёх
неизменённых каталогов. Проверены все 8 психотипов×7 явных сегментов; максимум raw
в domain. 60 pure tests passed (52 прежнего ядра +8 proposal), включая отказ от
activated/approved draft, пропущенного сегмента, bool threshold и invalid domain.
Ruff нового скрипта/тестов, mypy offline-скрипта и неизменённого pure core green. БД, runtime,
сетевые сервисы и внешние LLM для этой проверки не запускались.
