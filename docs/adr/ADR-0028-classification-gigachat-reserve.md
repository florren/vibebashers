# ADR-0028: резерв GigaChat Pro для live-классификации

Статус: принято.

## Причина

Наблюдение живого потока после PR #236 выявило некорректный JSON от Ultra на
classify. Штатная SDK-попытка исправления тоже не прошла schema validation,
после чего цепочка дошла до mock. Сеть и таймаут не были причиной. Уже
настроенный Pro использовался для normalize и decide, но не для classify.

## Решение

Default live classify v2 использует тот же frozen GigaChat Pro из role_profiles,
что и default live decide v3. Никакие профили, ключи и модели не создаются.
ProviderChain по-прежнему выбирает резерв только для допустимых ошибок формата
или доступности в оставшемся общем deadline. Auth/quota/rate-limit/network и
timeout не запускают лишний запрос другой моделью. Учёт расхода не меняется.

Явные версии промптов, offline/replay, другой provider/model и явный
fallback_profile сохраняют прежнее поведение. Промпты, схемы и replay hash не
меняются. Если обе модели не дают валидный ответ, остаётся явно обозначенный
последний резерв; его статус не скрывается и не считается успешным GigaChat.

Наблюдение также выявило decision с одной опцией HITL: Ultra и Pro повторяли
ошибку, поскольку сообщение jsonschema «too short» не указывало minItems=2.
SDK-repair теперь добавляет фактические ограничения длины/количества из схемы
и просит сохранить уже корректные обязательные поля. Первый запрос, схема,
число попыток, usage и deadline не меняются. Ответ по-прежнему создаёт LLM
и проверяет строгий validator; адаптер не дописывает опции или решения.
Обычный validate_schema сохраняет прежние сообщения ошибок по умолчанию.

## Проверка и откат

Тест с настоящим GigaChat SDK и synthetic HTTP transport проверяет валидный
Ultra, schema repair → Pro и ошибку обеих моделей для classify и decide.
Отдельно проверяются frozen bindings, pinned/offline режимы, исключённые виды
ошибок и общий deadline. Реальный поток проверяется после установки.

Rollback — прежний образ приложения. Миграций и изменений firewall нет.
