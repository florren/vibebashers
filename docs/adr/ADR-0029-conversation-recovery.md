# ADR-0029: продолжение диалога и восстановление неудачного кейса

Статус: принято по уточнению пользователя, 10.11.2026.

## Причина

Journey показывал входное сообщение родителя, но не все его клиентские ответы.
В `gather_context` история передавалась только personal, поэтому короткое дополнение
«Сколько ещё ждать?» теряло исходную проблему и могло создать другой инцидент.
Профиль `recovered` в форме воспринимался как продолжение, хотя профиль нового root
и последующие сообщения уже созданного кейса имеют разные границы.

## Решение

- Общая выборка диалога использует отдельный `journey_demo` run либо явную membership
  personal-сессии. Общий `client_id`, включая NULL, не является границей диалога.
  LLM получает только предыдущие сообщения и доставленные клиентские ответы.
- Для Journey контекст содержит инцидент исходного сообщения. Для personal — последнюю
  обсуждаемую проблему: новая явно указанная проблема остаётся отдельным инцидентом.
  Информационное дополнение без нового продукта использует известный продукт кейса;
  вопрос по открытому кейсу связывается с его инцидентом.
- Путь дополнения строится по исходному Journey-case, сохраняя выбранный SIG в заголовке.
  В клиентской ленте включены входы и доставки своего диалога; порядок определяется
  фактическими timestamp с учётом timezone и microseconds.
- Journey не принимает `recovered` как профиль нового root. Действие «Восстановление
  после эскалации» вызывает существующий `/api/demo/incidents/{id}/recover` после
  завершённой `failed`-попытки. Старый профиль и события не переписываются; создаётся
  продолжение плана того же инцидента. Глобальные часы, RNG и current-run не меняются.
- На `:9999` восстановление также следует за `failed`; `no_work` не выдаётся за
  завершённую попытку исправления. Повторный запрос восстановления идемпотентен.
- Итог `demo_unresolved` или `resolved` отправляется один раз на инцидент в диалоге,
  включая несколько дополнений. Другие сессии и обычные World-сигналы не объединяются.
  Положительный итог по-прежнему требует штатной проверки услуги.

## Проверки и откат

Регрессии проверяют полный Graph → failed → дополнение → recovery → verified close,
сохранение исходных действий, отсутствие нового инцидента и повторных итогов,
изоляцию кейсов одного клиента, передачу истории в оба LLM-этапа, порядок сообщений
при разных timezone, отрицательные входы и personal timer/repeat.

Миграций и новых постоянных объектов нет. Откат — прежний образ; записанные события
и исходные сообщения сохраняются. Прежние ошибочные ответы LLM не переписываются.
