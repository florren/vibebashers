# CX Pulse Control

Демо-стенд ИИ-агента банковского клиентского опыта (CX) для хакатона «Синапс»: эмулятор банка генерирует операции, сбои и обращения клиентов; агент классифицирует сигналы, собирает контекст, принимает решение, при сомнении спрашивает человека (HITL), заводит инциденты и уведомления; отдельный контур проверяет транскрипты встреч и звонков на мисселлинг, грубость и неверные факты. Всё работает без внешних ключей на встроенной mock-модели; с ключами GigaChat / OpenRouter / локальной модели — на настоящей LLM.

Что внутри одним взглядом: `/` — рабочее место (лента сигналов, очередь HITL, инциденты), `/engine` — «под капотом» (шаги агента, граф, цепочка решений, живые события, вкладка «Качество»), `/compliance` — транскрипты и отчёты комплаенса, `/manager` — алерты руководителю отделения, `/feed` — эмулятор внешней площадки (отзывы → ответ агента под постом) с виджетом Mock-АБС. Продуктовое описание — `docs/ONE-PAGER.md`, руководство пользователя — `docs/USER-GUIDE.md`.

### English (summary)

**CX Pulse Control** — hackathon demo of a bank CX AI agent: simulated bank, signal classification, HITL, incidents, compliance on branch transcripts, public review replies with Mock core banking. **Host:** Docker Desktop or Engine + Compose v2, Git; see [Part 3](#часть-3-технические-требования-к-устройству) for RAM/CPU. **Run:** `./install.sh` (app at http://localhost:8000); **offline / no LLM keys:** `./install.sh --offline` sets `LLM_CHAIN=replay,mock` (recorded model responses, then mock). **5‑minute demo script:** [docs/DEMO.md](docs/DEMO.md).

## Часть 1. Готовое приложение: скачать, настроить, запустить, показать

### 1.1. Что понадобится

Два пути запуска:

| Путь | Когда выбирать | Что ставить |
|---|---|---|
| **Docker (рекомендуется для демо)** | ноутбук для показа, минимум ручных действий | Docker Desktop (Windows/macOS) или Docker Engine + Compose v2 (Linux), Git |
| **Нативно (для разработки)** | нужен hot-reload, отладка, тесты | PostgreSQL 16, Python 3.12, [uv](https://docs.astral.sh/uv/), Node.js 22, Git |

Проверка перед стартом: `docker --version` и `docker compose version` (нужен Compose v2), `git --version`. Требования к железу — в [части 3](#часть-3-технические-требования-к-устройству).

### 1.2. Скачать

```bash
# вариант А: git (нужен доступ к репозиторию)
git clone https://github.com/florren/vibebashers.git
cd vibebashers

# вариант Б: без git — на странице репозитория Code → Download ZIP, распаковать, открыть терминал в папке
```

Зеркало в GitVerse обновляется автоматически после каждого слияния в `main` (`.github/workflows/mirror.yml`) — если GitHub недоступен, клонируйте оттуда.

### 1.3. Настроить `.env` (ключи — безопасно)

1. Скопируйте шаблон: `cp .env.example .env` (Windows PowerShell: `Copy-Item .env.example .env`).
2. Откройте `.env` в редакторе. Для демо без интернета **ничего менять не нужно** — приложение работает на mock-модели.
3. Если есть ключ GigaChat: вставьте в `GIGACHAT_AUTH_KEY_1=` значение **Authorization key** из личного кабинета (длинная base64-строка; это не access token), проверьте `GIGACHAT_SCOPE` (`GIGACHAT_API_PERS` для физлица, `GIGACHAT_API_CORP`/`B2B` для юрлица). Второй ключ в `GIGACHAT_AUTH_KEY_2` — ротация при лимитах.
4. Альтернатива — `OPENROUTER_API_KEY=` (OpenAI-совместимый API) или локальная модель `LOCAL_LLM_BASE_URL=http://host.docker.internal:11434/v1` (Ollama/vLLM/LM Studio).
5. Порядок отказоустойчивости задаёт `LLM_CHAIN=gigachat,openai_compat,replay,mock`: нет ключа или ошибка — переход к следующему. Для показа «гарантированно без сети» поставьте `LLM_CHAIN=replay,mock` или запускайте `./install.sh --offline`.

Правила безопасности: `.env` лежит в корне, в git не попадает (`.gitignore`), в Docker-образ не копируется (`.dockerignore`). Ключи никогда не вписываются в `docker-compose.yml`, README, карточки задач, чат с агентом или промпт. Все переменные, их варианты и конфликты — в [1.9. Справочник параметров](#19-справочник-параметров-env-installsh-make-скрипты); разбор по шагам — `docs/SETUP.md`.

Править `.env` руками не обязательно: мастер `http://<хост>:8000/setup` (9 шагов) записывает ключи моделей, `LLM_CHAIN`, токен бота, Mailpit и провайдер распознавания прямо в `.env` и применяет без перезапуска (в Docker файл смонтирован в контейнер); секреты наружу не возвращаются. Подробнее — [docs/SETUP.md](docs/SETUP.md), раздел 4а. Для распознавания речи с микрофона скачайте модель: `make stt-model`.

### 1.4. Запустить одной командой (Docker)

```bash
./install.sh                      # поднять PostgreSQL + backend (фронт собран внутрь), применить миграции, засеять данные (профиль lite)
./install.sh --profile demo       # 5 000 клиентов вместо 1 000 (для показа «живой» ленты)
./install.sh --offline            # принудительно mock, ни одного обращения в сеть
./install.sh --reset --seed 42    # снести данные и засеять заново воспроизводимо
./install.sh --with-mailpit       # просмотр писем клиентам на http://localhost:8025
```

Флаги `install.sh` (можно комбинировать, порядок не важен):

| Флаг | Варианты | Что делает | Чем отличается / с чем конфликтует |
|---|---|---|---|
| `--profile` | `lite` (по умолчанию) · `demo` · `stress` | объём данных сида: 1 000 / 5 000 / 20 000 клиентов (сигналов 800 / 2 500 / 10 000) | **перезаписывает** `PROFILE` в `.env`; `lite` — быстрый старт (~1 мин), `demo` — для показа «живой» ленты (~3 мин), `stress` — нагрузка (16 ГБ RAM, см. часть 3) |
| `--seed N` | целое | зерно генератора данных и эмуляции | перезаписывает `SIM_SEED` в `.env`; без флага остаётся значение из `.env` (42). Одинаковый seed + одинаковый профиль = одинаковые данные |
| `--offline` | — | автономный режим: `LLM_PROVIDER=mock`, `LLM_CHAIN=replay,mock`, `TELEGRAM_BOT_TOKEN=` пусто | **затирает** ваши `LLM_*`-настройки в `.env` — ключи GigaChat остаются в файле, но в цепочке не используются; чтобы вернуть, впишите `LLM_CHAIN=gigachat,openai_compat,replay,mock` обратно. Несовместим по смыслу с `--with-tgbot` |
| `--reset` | — | `docker compose down -v`: удалить тома БД и засеять заново | необратимо удаляет все данные стенда (решения HITL, инциденты, кассеты в БД); файлы `data/` и `.env` не трогает |
| `--with-mailpit` / `--no-mailpit` | по умолчанию выключен | поднять Mailpit (просмотр писем клиентам на :8025) | флаги взаимоисключающие, последний побеждает; `MAILPIT_ENABLED` в `.env` определяет, будет ли backend **отправлять** письма — без него Mailpit пустой |
| `--with-tgbot` | — | поднять контейнер Telegram-бота | требует `TELEGRAM_BOT_TOKEN` в `.env` и выход в интернет; бессмыслен с `--offline` |
| `--help` | — | подсказка | — |

Windows: запускайте из Git Bash или WSL2; либо руками: `docker compose up -d --build`, затем `docker compose exec backend alembic upgrade head` и `docker compose exec backend python /scripts/seed/run.py --profile lite`.

После старта: приложение — **http://localhost:8000**, API-документация — http://localhost:8000/docs, проверка — `curl -s localhost:8000/api/health` (ожидается `"status":"ok"`, `"db":true`; у LLM-профилей `ok` или `skip` без ключа — это штатно).

### 1.5. Запустить нативно (без Docker)

```bash
# PostgreSQL 16 запущен локально, пользователь/база cx:cx@localhost:5432/cx_pulse (и cx_pulse_test для тестов)
cp .env.example .env
make install-backend    # uv sync → backend/.venv
make install-front      # npm ci во frontend
make migrate            # alembic upgrade head
make seed PROFILE=lite  # данные
make dev                # backend :8000 с автоперезагрузкой
make dev-front          # в другом терминале: vite :5173 → proxy на :8000
make bench DATASET=lite_v1 PROFILE=mock  # локальный бенчмарк без сети и записи в БД
```

Фоновые бенчмарки запускаются из вкладки на `/engine` через `POST /api/bench/runs`: API возвращает `202` и отдельный `run_id` для каждого профиля. Наборы и профили берутся из БД, результаты сохраняются, прогресс поступает по WS-теме `bench`; доступны отмена и экспорт CSV/JSON. `dry_run=true` считает прогноз без вызова LLM и создания прогона. Ошибка выбранного провайдера завершает его прогон со статусом `failed`; автоматической подмены на mock в бенчмарке нет. CLI-команда `make bench` для профиля, отличного от mock, выводит только прогноз.

Основные цели Makefile: `lint`, `test`, `test-scenarios`, `sync-contracts`, `scenario`, `report`, `e2e`, `import-transcripts`.

`make lint` проверяет backend и frontend; `make test` запускает unit, integration, scenarios, compliance и frontend-тесты. Нужны оба установленных окружения; для integration/scenarios/compliance задайте `DATABASE_URL_TEST` на отдельную тестовую БД (её схема пересоздаётся). Отдельные цели: `make test-front`, `make test-compliance`. В локальном Node 26 запускайте frontend-тесты с `NODE_OPTIONS=--no-experimental-webstorage`, чтобы Vitest использовал Web Storage из jsdom; CI использует Node 22.

`make import-transcripts CX_BASE_URL=http://localhost:8000` импортирует серверный каталог `data/import/transcripts/` через API. Повторный импорт возвращает число дубликатов; отклонённые файлы дают код 1, ошибка HTTP/ответа — код 2. Успешный приём не означает завершение фонового анализа.

`make stt-bench` распознаёт встроенный WAV локальной моделью Vosk и выводит JSON с WER, временем вычисления первого partial/final, общей длительностью обработки и real-time factor. Для своего WAV: `make stt-bench FILE=/path/voice.wav REF=/path/reference.txt` (PCM16 mono 16 kHz, эталон UTF-8). Эталон сравнивается без учёта регистра, пунктуации и различия ё/е; в результат попадает только распознанный текст. Это ускоренный файловый прогон: время загрузки модели и задержки доставки микрофона в метрики не входят. Нужна установленная Vosk-модель (`STT_MODEL_PATH` или `make stt-model`); отсутствие модели даёт код 2, пустое распознавание — код 1. CLI не пишет в БД и не реализует весь набор/UI T-191.

`make demo-offline` вызывает `./install.sh --offline` без `--reset`, сохраняя существующие данные. Установщик выбирает replay/mock и Vosk; для первого запуска нужны Docker-образы и локальная модель (без кэша установщик может обращаться к сети).

### 1.6. Провести демо

Пятиминутный показ с таймингом и планом Б — [docs/DEMO.md](docs/DEMO.md). Расширенный конспект с репликами (12–15 мин) — [docs/DEMO-SCRIPT.md](docs/DEMO-SCRIPT.md). Короткая последовательность:

1. Открыть http://localhost:8000, нажать **Старт** в шапке. Эмуляция идёт в сим-времени; переключатель скорости ×1 / ×10 / ×60 / ×120 / ×300 — сколько сим-секунд проходит за одну реальную (×60 = сим-час за минуту, ×120 = рабочий день примерно за 5 минут; ×300 — быстро «прокрутить сутки», сигналов становится много и live-модель может не успевать). Ночью по сим-времени поток падает — это нормально. Через 20–40 секунд в ленте появляются сигналы, агент разбирает их; часть уходит в очередь **HITL**.
2. В очереди HITL принять одно решение (одобрить / изменить / отклонить) — показать, что человек правит агента и это сохраняется.
3. Карточка инцидента: маршрутизация в команду, SLA, уведомления, цепочка решений.
4. `/engine`: шаги агента с промптами и ответами модели, граф, живые события по WebSocket.
5. Комплаенс: в терминале `make scenario ID=9` и `make scenario ID=10` (или кнопка «Импорт корпуса» на `/compliance`). На `/manager` появятся алерты «порог срабатываний» и «немедленный»; по ссылке «Транскрипт» — отчёт с факт-чеком ставки по тарифам и пропущенными этапами скрипта.
6. Публичный отзыв и возврат комиссии: `/feed` → «Опубликовать отзыв» с 4 цифрами карты клиента (или `make scenario ID=8`). Через несколько секунд под постом — ответ агента, в виджете «АБС (эмуляция)» — зелёная проводка «возврат»; сверху — «Возвращено» и «Авто / HITL».
7. Вкладки **Карта** (тепло / зоны, клик по региону → города) и **Дашборд** (KPI ТЗ 14.1, экономика dCLTV с группировкой, «Факт по симуляции»): показать, где болит и сколько это стоит.
8. Вкладки **Тикеты** (действия сотрудника по FSM, режим «Эскалации» — принять / закрыть с резолюцией) и **Команды** (нагрузка и SLA): показать, как человек управляет исключениями.
9. Вкладка **Качество** на `/engine` — индекс здоровья и список «что доработать»: показать, что система сама говорит, где она на заглушках и где человек поправлял агента.
10. **Настройки** (`/setup`): мастер из 9 шагов — показать, что пороги, SLA, маршрутизация и экономика настраиваются без кода.
11. **Живая встреча** («Комплаенс» → «Микрофон»): речь менеджера распознаётся офлайн (Vosk), срабатывания мисселлинга подсвечиваются на лету; «Задачи» — выдать или заменить подарок клиенту.
12. Режим жюри (кнопка в шапке; «Надиктовать» — ввод голосом): ввести свой текст обращения — агент разберёт его на глазах.

Полезно перед показом: `make scenario ID=all` — прогон всех сценариев ТЗ с результатом OK/FAIL; `make report` — отчёт о качестве в `data/reports/latest.md`.

### 1.8. Если что-то не так

| Симптом | Что сделать |
|---|---|
| `install.sh` падает на `docker compose` | Нужен Compose v2 (`docker compose`, не `docker-compose`); на Linux добавьте пользователя в группу `docker` |
| Порт 8000/5432 занят | В `.env` поменяйте `APP_PORT`/`DATABASE_URL`, либо остановите локальный PostgreSQL |
| `/api/health` → `"db": false` | PostgreSQL ещё стартует (подождите 10–20 с) или неверный `DATABASE_URL` (внутри compose хост `postgres`, нативно — `localhost`) |
| В логах `llm_chain_skip … нет GIGACHAT_AUTH_KEY_*` | Штатно: ключа нет, работает mock. Проверьте `.env`, если ключ должен быть |
| Ответы агента шаблонные, без «живого» текста | Работает mock; вкладка «Качество» покажет «% LLM-шагов на fallback». Добавьте ключ или `LOCAL_LLM_BASE_URL` |
| Лента пустая после «Старт» | Эмуляция на паузе или ночь по сим-времени (видно в шапке); увеличьте скорость или нажмите «Старт» ещё раз |
| GigaChat: ошибка SSL | оставьте `GIGACHAT_VERIFY_SSL=true`; используется встроенный CA bundle. Для своей цепочки задайте `GIGACHAT_CA_BUNDLE_FILE` |

### 1.9. Справочник параметров (.env, install.sh, make, скрипты)

Правило приоритета: переменные окружения процесса > `.env` > значения по умолчанию в `backend/app/config.py`. `install.sh` **пишет** в `.env` (`PROFILE`, `SIM_SEED`, при `--offline` — `LLM_*`), поэтому после него проверьте файл.

#### `.env` — приложение

| Переменная | Варианты | По умолчанию | Что делает | Отличия и конфликты |
|---|---|---|---|---|
| `APP_ENV` | `dev` · `test` · `prod` | `dev` | режим приложения | `dev`: читаемые логи в консоль, `/docs` открыт, уровень DEBUG. `test`: без JSONL-журнала и без моста LISTEN/NOTIFY (для pytest). `prod`: логи JSON, `/docs` **выключен**, ожидается `GIGACHAT_VERIFY_SSL=true` с сертификатом. Для демо оставляйте `dev` |
| `APP_SECRET` | строка | генерирует `install.sh` | подпись служебных токенов | `change-me` допустимо только локально |
| `APP_LANG` | `ru` · `en` | `ru` | язык текстов API/уведомлений | UI переведён только на `ru`; `en` даст смешанный интерфейс |
| `APP_PORT` | число | `8000` | порт backend (и SPA) | при смене обновите `ports` в `docker-compose.yml` и `CX_BASE_URL` для скриптов |
| `PROFILE` | `lite` · `demo` · `stress` | `lite` | профиль данных, который видит приложение (подписи, лимиты) | сам по себе данные **не** создаёт — их создаёт сид (`install.sh --profile` или `make seed PROFILE=`); держите одинаковыми |
| `SIM_SEED` | целое | `42` | зерно эмуляции и сида | меняйте вместе с `--reset`, иначе новые данные лягут поверх старых |
| `DATABASE_URL` | `postgresql+psycopg://user:pass@host:5432/db` | `…@localhost:5432/cx_pulse` | основная БД | внутри compose хост **`postgres`**, нативно — `localhost`; `install.sh` не переписывает — compose передаёт свой через `environment` |
| `DATABASE_URL_TEST` | то же | — | БД для pytest (пересоздаётся) | **не** указывайте ту же базу, что в `DATABASE_URL`: тесты применяют миграции с нуля и чистят данные |
| `LLM_PROVIDER` | `mock` · `gigachat` · `openai_compat` · `replay` | `mock` | **какой профиль считается основным**: модель и лимиты, под которыми подписываются шаги агента (`agent_steps.model`) и считается `fallback` | порядок fallback задаёт `LLM_CHAIN`; явные mock/replay исключают живые вызовы даже при заданных ключах. ## Часть 2. Руководство для тех, кто ведёт разработку ИИ-агентами

Репозиторий спроектирован так, чтобы задачи выполняли ИИ-агенты (Codex, Cursor, Claude Code, Perplexity Computer, DeepSeek и локальные модели), а человек ставил задачи, проверял результат и сливал PR. Ниже — как это устроено и что делать по шагам.

### 2.1. Как устроен репозиторий для агентов

| Что | Где | Зачем |

### 2.2. Подготовка рабочего места (общая для любого агента)

1. Установите Git, Python 3.12, uv (`curl -LsSf https://astral.sh/uv/install.sh | sh`), Node.js 22, Docker (для тестов хватит локальной PostgreSQL 16), GitHub CLI `gh`.
2. Авторизуйте `gh auth login` под учёткой с правом писать в репозиторий (владелец даёт доступ: Settings → Collaborators → Add people; роль Write).
3. Клонируйте в структуру, которую ждёт `cx`:
   ```bash
   mkdir -p ~/dev && cd ~/dev
   git clone https://github.com/florren/vibebashers.git
   cd vibebashers && python scripts/cx.py doctor     # проверит git, gh, codex, uv, node
   alias cx='python ~/dev/vibebashers/scripts/cx.py'  # добавьте в ~/.bashrc
   ```
4. Поднимите БД для тестов: `docker compose up -d postgres`, в `.env` укажите `DATABASE_URL_TEST`. Проверьте `make lint && make test` на `main` — должны быть зелёные.
5. Настройте git-автора агента (`git config user.name/user.email`) — так в истории видно, кто из агентов что делал.

Параметры `cx` (`python scripts/cx.py <команда> …`):

| Команда | Параметр | Варианты | Отличия и конфликты |
|---|---|---|---|
| `next` | `--seat` | `S1` · `S2` · `S3` | рабочее место из `docs/PLAN-14D.md` §2: S1 backend, S2 frontend, S3 данные/промпты/тесты/доки; без флага — ближайшая карточка без незакрытых зависимостей |
| `start`, `fix` | `id` | `B01…B21` (пакет) или `T-001…T-222` (карточка) | пакет = несколько карточек в одной ветке и одном PR; карточка = одна. Не смешивайте: карточку из уже начатого пакета вторым worktree брать нельзя — будет конфликт при слиянии |
| | `--agent` | `codex` (по умолчанию) · `cursor` · `manual` | `codex`: запуск `codex exec` без участия человека, итог в `.cx/report.md`. `cursor`: открыть worktree в Cursor, промпт показать — дальше вручную. `manual`: только worktree и `.cx/prompt.md` — для Claude Code, aider, Perplexity Computer и любого другого агента |
| | `--interactive` | — | только с `--agent codex`: диалоговый режим вместо автономного; с `cursor`/`manual` игнорируется |
| `fix` | `--rebase` | — | вместо «почини по логу проверок» — «разреши конфликты с main и повтори проверки» |
| `done` | `--force` | — | удалить worktree и ветку, даже если PR не слит (по умолчанию отказ) |
| `check`, `pr`, `open` | `id` | — | без доп. флагов |

Worktree создаются в `../wt/<id>` рядом с клоном (константа `WT_DIR` в `scripts/cx.py`); состояние — `<repo>/.cx/state.json` (в `.gitignore`).

### 2.3. Codex (OpenAI Codex CLI)

1. `npm i -g @openai/codex`, затем `codex login` (ChatGPT-аккаунт или `OPENAI_API_KEY`).
2. В `~/.codex/config.toml` поднимите лимит чтения инструкций — `AGENTS.md` больше 32 КиБ:
   ```toml
   project_doc_max_bytes = 200000
   model = "gpt-5-codex"          # или другая доступная модель
   approval_policy = "never"      # cx start сам передаёт -a never -s workspace-write
   ```
3. Запуск задачи без участия человека: `cx start B06 --agent codex` (или `cx start T-171`). Скрипт создаёт worktree `../wt/B06`, собирает промпт из карточки и запускает `codex exec`. Для диалогового режима — `--interactive`.
4. Codex читает `AGENTS.md` сам; итог работы агент записывает в `../wt/B06/.cx/report.md` — этот текст `cx pr` подставит в описание PR.

### 2.4. Cursor

1. Установите Cursor, войдите в аккаунт; в настройках включите «Rules for AI» — проект уже содержит `.cursor/rules/`.
2. `cx start B06 --agent cursor` — создаст worktree и откроет папку в Cursor (если команда `cursor` в PATH), промпт задачи сохранится в `../wt/B06/.cx/prompt.md`.
3. В Cursor откройте Agent (Composer), вставьте содержимое `prompt.md`, режим Agent с автозапуском команд. Cursor подхватывает `AGENTS.md` и `.cursor/rules/` автоматически.
4. Дальше как обычно: `cx check B06`, `cx pr B06`.

### 2.5. Claude Code

1. `npm i -g @anthropic-ai/claude-code`, `claude` → вход в аккаунт Anthropic (или `ANTHROPIC_API_KEY`).
2. Claude Code читает `CLAUDE.md` в корне, который отсылает к `AGENTS.md`. Если хотите, добавьте в `~/.claude/settings.json` разрешения на `make`, `uv`, `npm`, `gh`, чтобы не подтверждать каждую команду.
3. Запуск: `cx start B06 --agent manual` (создаст worktree и промпт, агента не запустит), затем
   ```bash
   cd ../wt/B06 && claude -p "$(cat .cx/prompt.md)" --permission-mode acceptEdits
   ```
   или интерактивно: `claude`, затем вставить промпт.

### 2.6. DeepSeek, другие API-модели и локальные модели

Любая OpenAI-совместимая модель подключается через те же CLI-агенты:

- **Codex CLI с другим провайдером** — в `~/.codex/config.toml`:
  ```toml
  model_provider = "deepseek"
  model = "deepseek-chat"
  [model_providers.deepseek]
  name = "DeepSeek"
  base_url = "https://api.deepseek.com/v1"
  env_key = "DEEPSEEK_API_KEY"
  ```
  Для локальной модели: `base_url = "http://localhost:11434/v1"` (Ollama), `env_key` любой непустой. Дальше `cx start … --agent codex` работает без изменений.
- **Другие агентные CLI** (aider, opencode, Cline в VS Code) — укажите им модель и базовый URL по их документации и запускайте в worktree с промптом из `.cx/prompt.md` (`cx start … --agent manual`).
- **Локальные модели (Ollama / vLLM / LM Studio)** — честное ограничение: для этого репозитория (150+ файлов, строгие контракты, mypy strict) модели до ~30B часто не доводят задачу до зелёных проверок. Практика, которая работает: локальная модель — для маленьких карточек (S) и правок по логу `cx fix`, облачная — для пакетов B-уровня. Ограничьте контекст одной карточкой и запускайте `cx check` чаще.
- Модель **самого приложения** (не агента-разработчика) настраивается отдельно, в `.env` (`LLM_CHAIN`, `LOCAL_LLM_BASE_URL`) — см. часть 1.

### 2.7. Как подключить агента к репозиторию

1. **Доступ.** Владелец репозитория добавляет учётку агента (или человека, под чьим `gh` он работает) с ролью Write. Для API-токенов — fine-grained PAT с правами Contents: Read/Write, Pull requests: Read/Write, Actions: Read на один репозиторий; срок — не больше спринта.
2. **Ветки.** Агент никогда не пишет в `main` напрямую: ruleset требует PR и зелёные `contracts`, `db`, `tests`. Ветки `feat/<id>-…` создаёт `cx start`.
3. **Слои.** Карточка привязана к слою; `python scripts/check_owners.py --base main` (его вызывает `cx check`) падает, если агент тронул чужие файлы. Если это осознанно — PR получает метку `cross-layer` (и `contract-change`, если менялись контракты), сливает владелец L1.
4. **Секреты.** В промпт и в репозиторий ключи не попадают: `.env` в `.gitignore`, в карточках — только имена переменных. CI-секреты (`GITVERSE_TOKEN`) — в Settings → Secrets.
5. **Что агент должен прочитать перед задачей** (это уже зашито в `scripts/prompts/task.md`): `AGENTS.md` целиком, карточку, разделы ТЗ из карточки, контракты из карточки, `docs/REPORTS.md` при починках.

Чтобы результат не зависел от того, кто ставит задачу, каждый промпт человека агенту строится из пяти блоков. Пропускать блоки нельзя — лучше написать «нет».

### 2.10. Как сделать задачу (пошагово)

1. `cx next` — подскажет карточку без незакрытых зависимостей. Либо выберите сами в `docs/tasks/README.md`. `PLAN-14D` срез уже закрыт.
2. `cx start <B06|T-171> --agent codex|cursor|manual` — worktree, окружение, промпт, запуск агента.
3. Дождитесь завершения (Codex пишет итоговый отчёт в `../wt/<id>/.cx/report.md`; промпт — там же в `prompt.md`). Агент обязан заполнить «Отчёт субагента» в карточке и поставить статус.
4. `cx check <id>` — contracts, owners, lint, test; лог в `.cx/check.log`. Красное → `cx fix <id>` (агент получает лог и чинит), конфликт с `main` → `cx fix <id> --rebase`.
5. `cx pr <id>` — коммит остатков, rebase, push, PR с отчётом агента в описании. CI запускается сам.
6. Проверьте PR глазами: описание, скриншоты/логи из отчёта, нет ли секретов и лишних файлов; при `contract-change` — что обновлены `schema.sql` + alembic + OpenAPI + JSON-схемы + TS-типы.
7. Слияние: Squash and merge (ruleset требует зелёные `contracts`, `db`, `tests`; `owners` и `mirror` для PR с меткой `cross-layer` могут быть красными — это информационно). После слияния `cx done <id>`.
8. При желании — `make report` до и после: индекс здоровья и рекомендации должны измениться в лучшую сторону.

Промпт для ручного запуска агента (Cursor, Claude Code, другой CLI) — он совпадает с тем, что `cx start` кладёт в `.cx/prompt.md`, и его можно скопировать как есть:

```text
РОЛЬ И КОНТЕКСТ: ты работаешь в репозитории CX Pulse Control в worktree <../wt/T-171> на ветке <feat/T-171-…>; другие папки не трогать. Сначала прочитай целиком AGENTS.md, затем docs/TEAM-SPLIT.md §3, карточку docs/tasks/<T-171-…>.md, разделы ТЗ и контракты, на которые она ссылается.
ЗАДАЧА: выполни карточку <T-171> полностью по разделу «Шаги» так, чтобы выполнились все пункты «Критерии приёмки». Если карточка — часть пакета <B06>, выполни все карточки пакета в этой же ветке в порядке зависимостей: <T-171, T-175, T-176, T-177>.
ГРАНИЦЫ: слой <L3>; меняй файлы только внутри каталогов слоя по CODEOWNERS, в общие тесты — только добавлять. Контракты и чужие слои не менять: опиши нужное изменение в «Отчёте субагента» и продолжай с заглушкой. Не ослабляй тесты, не отключай проверки, не добавляй внешние CDN, не клади секреты и ПДн. ПРОВЕРКИ: make lint && make test; python scripts/contracts_check.py; python scripts/check_owners.py --base origin/main; <make scenario ID=8 на поднятом стенде>. Падает — чини, пока не зелёное.
ФОРМАТ ОТВЕТА: 1) заполни «Отчёт субагента» в карточке (ветка, что сделано, отклонения, затронутые контракты, как проверено, время) и поставь статус done или in_progress; 2) закоммить осмысленными коммитами с префиксом «<T-171>:», не пушь и не открывай PR (это сделает cx pr); 3) последним сообщением — сделано / не сделано / проверки / риски, 10–20 строк, на русском.
```

### 2.11. Как доделать задачу, которую начал другой и не закончил

1. Найдите следы: `cx status` (worktree/ветки на этой машине), `gh pr list --state open` и `git branch -r | grep <id>` (ветки на GitHub), карточка со статусом `in_progress` и частично заполненным «Отчётом субагента».
2. Прочитайте отчёт субагента и диффы: `gh pr diff <номер>` или `git log origin/main..origin/feat/<id>-… --stat`. Поймите, какие пункты «Шаги» карточки закрыты, какие нет.
3. Если ветка существует удалённо: `cx start <id>` на той же машине продолжит существующий worktree; на другой машине — `git fetch && git worktree add ../wt/<id> feat/<id>-…` и затем `cx start <id> --agent …` (скрипт увидит worktree и не будет создавать заново).
4. Дополните промпт: в `../wt/<id>/.cx/prompt.md` допишите блок «Что уже сделано предыдущим исполнителем … Что осталось …» (возьмите из отчёта и диффа) и запустите агента (`--interactive` для Codex или вручную для Cursor/Claude).
5. Если чужая ветка безнадёжно устарела или сломана: `cx done <id> --force` (удалит worktree и локальную ветку), удалите удалённую ветку, закройте PR с комментарием, перенесите полезные куски руками через `git cherry-pick` и начните `cx start <id>` заново.
6. Дальше по общему циклу: `cx check` → `cx pr` → слияние → `cx done`. В «Отчёте субагента» укажите обоих исполнителей и что изменилось.

Промпт «доделай чужую незавершённую задачу» (добавляется к базовому промпту карточки из 2.10 или вставляется в `.cx/prompt.md` блоком):

```text
РОЛЬ И КОНТЕКСТ: ты продолжаешь карточку <T-213> в worktree <../wt/T-213> на существующей ветке <feat/T-213-…>, которую начал другой исполнитель (<Codex, 20.10> / PR #<n>, не слит). Прочитай AGENTS.md целиком, карточку, её «Отчёт субагента», `git log origin/main..HEAD --stat` и `git diff origin/main...HEAD`.
ЗАДАЧА: сначала составь список «сделано / не сделано / сделано неправильно» по пунктам «Шаги» и «Критерии приёмки» карточки и покажи его мне одним сообщением. Затем доведи карточку до полного выполнения критериев приёмки: <что известно о причине остановки: «упали тесты db», «не хватило контракта», «конфликт с main»>.
ГРАНИЦЫ: не переписывай работающие части предшественника без причины — правь точечно; историю коммитов не переписывай (без rebase -i, без force push); слой <L3>; контракты не менять. Если предыдущая реализация противоречит карточке или AGENTS.md — исправь и перечисли это в отчёте отдельным списком.
ПРОВЕРКИ: make lint && make test; python scripts/contracts_check.py; python scripts/check_owners.py --base origin/main; при конфликте с main — git rebase origin/main и повторить проверки.
ФОРМАТ ОТВЕТА: обновлённый «Отчёт субагента» в карточке с подзаголовками «Сделано предшественником», «Доделано», «Исправлено», «Не сделано и почему»; коммиты с префиксом «<T-213>:»; итоговое сообщение 10–20 строк на русском.
```

### 2.12. Как запросить новый функционал

1. Сформулируйте требование на языке ТЗ: пользователь, путь, ожидаемый результат, что видно на экране/в API. Если это изменение требований — допишите раздел в `docs/TZ-additional.md` (PR в L1).
2. Заведите карточку: карточки генерируются скриптом — добавьте запись `dict(id=264, title=…, epic=…, agent=…, size=…, wave=…, goal=…, tz=[…], contracts=[…], deps=[…], steps=[…], accept=[…], check=[…])` в список в `scripts/gen_tasks.py` и выполните `python scripts/gen_tasks.py` — появится `docs/tasks/T-264-*.md` и обновится индекс. ### 2.13. Как это проверяет CI и когда просить человека

- `contracts`: `scripts/contracts_check.py` (JSON-схемы и OpenAPI валидны, примеры проходят), дрейф OpenAPI ↔ код (`scripts/check_openapi_drift.py`), i18n (`scripts/i18n_check.py`).
- `db`: `alembic upgrade head`, `alembic check`, схема совпадает с `contracts/db/schema.sql`.
- `tests`: ruff, ruff format, mypy strict, pytest (unit, integration, scenarios) на PostgreSQL в сервисе CI; фронт: eslint, tsc, vitest, build, проверка сгенерированных TS-типов.
- `owners`: границы слоя (информационный для `cross-layer`).
- Человек нужен для: слияния PR с метками `contract-change`/`cross-layer`, изменений ТЗ, ключей и доступа. Урезания `docs/PLAN-14D.md` больше не требуют отдельного решения, чтобы взять карточку из бэклога.

Промпт «почини красный CI» (его же формирует `cx fix <id>`, вставляя лог):

```text
РОЛЬ И КОНТЕКСТ: ты в worktree <../wt/T-171>, ветка <feat/T-171-…>, PR #<n>. Прочитай AGENTS.md §4–§5, карточку и лог упавших проверок ниже.
ЗАДАЧА: сделай проверки зелёными, не меняя смысла задачи. Упало: <contracts | db | tests | owners>. Лог: <последние 100–200 строк из cx check / gh run view --log-failed>.
```

## Часть 5. Собственные решения: что, почему, что делает

| Решение | Почему так | Что делает |
|---|---|---|
| **Контракты первичны, код генерируется** (`contracts/` → `make sync-contracts`; `scripts/gen_enums.py`, `gen_models.py`, `gen_schemas.py`, `gen_api_stubs.py`, `check_openapi_drift.py`) | несколько агентов параллельно меняют слои; без единого источника истины фронт и бэк расходятся за день | enums, Pydantic-модели, SQLAlchemy-модели, TS-типы и роутеры создаются из DDL/OpenAPI/JSON-схем; CI падает при расхождении спецификации и кода (сейчас 159 операций = 159) |
| **Заглушки 501 с номером карточки** (`app/errors.py::NotImplementedYet`) | весь API виден с первого дня; фронт пишется против контракта, не дожидаясь бэка | каждый нереализованный эндпоинт отвечает `application/problem+json` с полем `card: T-xxx`; отчёт о качестве считает вызовы 501 как «спрос на нереализованное» |
| **Карточки задач как код** (`scripts/gen_tasks.py` → `docs/tasks/*.md` + индекс по волнам и слоям) | у агента должен быть законченный, самодостаточный вход; статусы и зависимости нужно считать скриптом | 151 карточка с целью, разделами ТЗ, контрактами, шагами, критериями приёмки, командами проверки, зависимостями и «Отчётом субагента»; статусы сохраняются при регенерации |
| **`cx.py` — рабочий цикл одной командой** (`docs/WORKFLOW.md`) | руководитель без опыта разработки не должен помнить worktree, флаги Codex и `gh` | `next / start / check / fix / pr / done / status / clean / doctor`: worktree на карточку, промпт из шаблона, запуск Codex/Cursor, проверки с логом, PR с отчётом агента, уборка после слияния |
| **Слои и `check_owners.py`** (`CODEOWNERS`, `docs/TEAM-SPLIT.md`) | параллельные агенты не должны переписывать чужие файлы | PR проверяется на выход за слой карточки; осознанные исключения — метки `cross-layer` / `contract-change`, сливает владелец L1 |
| **Единый интерфейс LLM + цепочка отказоустойчивости** (`app/llm/base.py`, `failover.py`, `keys.py`, `ratelimit.py`) | демо не должно зависеть от доступности и квот одного провайдера | `ProviderChain`: таймауты по контексту (`fast_path` 8 с, `detector` 5 с, `batch` 12 с, `default` 30 с), любая ошибка → следующий провайдер; пул ключей GigaChat с ротацией, rate limiter, учёт токенов в `agent_steps` |
| **Mock-модель на правилах, заполняющая любую схему** (`app/llm/mock.py`) | стенд обязан работать без ключей и сети, детерминированно для тестов | эвристики по ключевым словам (тип сигнала, тональность, флаги), генерация валидного объекта под любую JSON-схему; блок-подсказка `<<mock_verdict>>` позволяет узлам передать правило-вердикт, чтобы mock повторял логику правил |
| **Replay-кассеты** (`app/replay/store.py`, `data/cassettes/*.jsonl`, таблица `llm_cassettes`) | воспроизводимое демо и тесты «как с настоящей моделью», но без сети | ответы модели кэшируются по `sha256(provider, model, messages, schema)`; провайдер `replay` в цепочке отдаёт записанное |
| **Собственный раннер графа агента вместо LangGraph** (`app/agent/graph.py`, `nodes.py`, `runner.py`) | меньше зависимостей, чекпоинт и трассировка должны лежать в нашей БД и быть видны в UI | узлы `ingest → normalize → identify_client → gather_context → classify → check_rules → decide → wait_human → act → close`; каждый шаг — строка `agent_steps` с промптом, ответом, латентностью, токенами и статусом `ok/retry/fallback/error`; пауза на HITL и возобновление по `thread_id` |
| **Политики HITL и правила как данные** (`app/agent/policies.py`, `data/*.yaml`, таблицы `hitl_policies`, `routing_rules`) | человек должен править поведение без кода; правки должны учиться | четыре ветки HITL (одобрить/изменить/отклонить/делегировать), `human_decisions` с `agent_proposal` и `modified_proposal`, флаг `use_as_fewshot`; маршрутизация и SLA — матрица из YAML |
| **Нормализатор входов** (`app/ingest/`) | сигналы приходят из эмулятора, REST, транскриптов, ленты — агент должен видеть один формат | все источники приводятся к `ingest/signal`-схеме с `origin`, `channel`, `tracking_token` |
| **Эмулятор банка в сим-времени с детерминированным RNG** (`app/sim/clock.py`, `rng.py`, `engine.py`, `generators.py`, `events.py`, `runs.py`) | 14 дней «жизни банка» за минуты, воспроизводимо по сиду, с изолированными запусками | `SimClock` с ускорением ×1…×300 и фазами дня, `random.Random` с сериализацией состояния в `sim_state`, шина событий, валидирующая каждое событие по JSON-схеме, запуски `sim_runs` (сравнение «до/после», сброс к сиду) |
| **Шина на `LISTEN/NOTIFY` → WebSocket-хаб** (`app/realtime/`) | без Redis/Kafka; одна БД — один источник правды для UI | `NotifyBridge` слушает каналы PostgreSQL, маршрутизирует в темы (`signals`, `hitl`, `incidents`, `compliance`, …), фронт инвалидирует кэш TanStack Query по теме |
| **Сид с профилями и матрицей покрытия** (`scripts/seed/`, `data/corpus/`, `data/bench/`) | данные должны покрывать все типы сигналов, психотипы, регионы и сценарии ТЗ | профили lite/demo/stress (1 000 / 5 000 / 20 000 клиентов), идемпотентный сид, корпуса текстов и золотые наборы бенчмарков |
| **Сценарии ТЗ как исполняемые проверки** (`data/scenarios/*.yaml`, `app/sim/scenarios.py`, `scripts/scenario_check.py`, `tests/scenarios/`) | «демо-сценарий» должен быть и автотестом, и кнопкой на стенде | один YAML описывает инъекцию (операция, сбой, пост, транскрипт) и ожидания (тип сигнала, команда, HITL, паттерны, алерты); результат хранится в `scenarios.last_result` и виден в отчёте о качестве |
| **Комплаенс: правила-гейт + LLM-подтверждение + факт-чек** (`app/compliance/`) | модель дорогая и ошибается; правила — дешёвые, но шумные; соединение даёт объяснимость | правила (ключевые фразы с нечётким совпадением, факт-чек ставок/комиссий по `products.tariffs` с числами словами, этапы скрипта с отрицаниями) дают предварительную находку → LLM подтверждает и объясняет (`misselling_detect`), счётчик → алерт `threshold`/`immediate` → инцидент и уведомление руководителю; отчёт `transcript_report` с цитатами, «сказано/по тарифам», планом действий |
| **Mock-АБС как книга проводок, а не поле «баланс»** (`app/abs/`) | возврат денег — единственное действие агента с реальными последствиями; его нужно уметь доказать, повторить без дублей и показать на экране | счёт на клиента, проводки двойной записи (`debit/credit/fee/refund`), инвариант `balance = Σ проводок` (`check_invariant`), идемпотентность по `correlation_id` (повторный вызов → `duplicate`, денег не двигает), возврат только при подтверждённом правилом нарушении и не больше комиссии; догоняющие проводки для сида и сценариев при старте; политика автономии читает из книги факты «уже возвращали», «возвратов за 30 дней» |

| **Экономика как формула, а не оценка** (`app/economics/`) | бизнесу нужно доверять цифре «предотвращено N ₽» — значит, каждый множитель должен быть виден и воспроизводим | единственная реализация формулы ТЗ 14.4 (`compute`), `formula_ru` в каждом расчёте («12 × 10 % × 50 % × (961 + 91,53) = 631,52 ₽»), ставка по приоритету продукт → система → канал → средняя по банку, класс исхода из фактов (SLA, подарок, регрессия, уход), «факт по симуляции» показывает допущения рядом с реальным поведением двойников и позволяет подставить факт в калькулятор |
| **Наблюдаемость и отчёт о качестве** (`app/observability/`, `docs/REPORTS.md`) | команда из агентов и людей должна понимать, где сломалось, где работает не так и что доработать, не читая stdout | JSONL-журнал с `request_id`, HTTP-счётчики по маршрутам, кольцевой буфер ошибок; отчёт по `agent_runs/agent_steps/human_decisions/incidents/scenarios/compliance` с правилами рекомендаций («где смотреть») и индексом здоровья; `make report`, `GET /api/reports/quality`, вкладка «Качество» |

| **Все тексты UI через i18n с проверкой enum-ов** (`scripts/i18n_check.py`) | русский — язык продукта; коды из контрактов должны иметь перевод | CI падает, если для значения enum из `common.schema.json` нет строки в `ru.json` |

### Финансовый эффект запуска

Откройте `/finance` из шапки или дашборда. Основная модель dCLTV и два сценария (вероятность оттока, вероятность с условным штрафом) показаны раздельно; допущения можно менять. Live относится к выбранному запуску, периоды — к симуляционному времени UTC. Без текущего запуска итог нулевой; возвраты и отрицательный чистый эффект видны отдельно. Методика и ограничения — [ADR-0013](docs/adr/ADR-0013-financial-impact.md), [сопоставление требований](docs/FINANCIAL-IMPACT-ANALYSIS.md).

В блоке «Оценка по данным» рядом показаны демо-калибровка и рабочий контур. Реальные данные и согласования не подменяются демо: без них рабочий итог неизвестен. В детализации мисселлинга можно записать новую версию доказательства вмешательства и посмотреть историю. Перед запуском обновлённого стенда выполните штатную миграцию (`make migrate`, Alembic 0008; Docker применяет её при старте). Формат входного набора и политика — [data/economics](data/economics/README.md), методика — [ADR-0014](docs/adr/ADR-0014-finance-calibration-evidence.md).

Фильтр «Продукты» на `/finance` позволяет выбрать отдельные позиции, выделить все кнопкой «Все продукты» и переключиться в «Все, кроме выбранных». Фильтр общий для всех сумм, графика, реестра и обоих контуров. «Снять выделение» в обычном режиме даёт пустой срез, в режиме исключения — все продукты.

### Поиск сигналов и информация оператора

Во вкладках «Сигналы» и «Требует решения» поиск принимает SIG/INC/HD/ESC и остальные коды реестра. По умолчанию область — все запуски; можно выбрать текущий. Историю можно догрузить, статусы сигнала не скрывают его из поиска. В HITL показаны исходный SIG и связанные INC/HD/ESC/SR. Из карточек SIG/INC доступна ссылка «Решения и информация оператора».

Если граф уже продолжается, добавляйте сведения в «Информация оператора»: они сохраняются в истории связанного запроса без повторения действий и денежных операций. Кнопка «Запрос обработан» подтверждает обработку non-blocking эскалации; активный wait_human сохраняет обычные варианты решения. Автоматический timeout отмечен отдельно. Перед запуском обновления нужна штатная миграция до 0009 (`make migrate`; Docker выполняет upgrade при старте). Методика — [ADR-0015](docs/adr/ADR-0015-signal-hitl-continuity.md).

### Анонимный пользовательский чат :9999

`./install.sh` запускает отдельный сервис `personal` на `http://localhost:9999`: форма продукта/региона/города, свободный текст, диктовка Vosk и чат с ответами общего агента. Операторских ссылок и API на этом порту нет. Входы проходят normalizer как анонимные; в «Сигналах» есть фильтр `ui_pers_demo`. Сессия хранится в HttpOnly cookie, каждый запрос идемпотентен. CAPTCHA решать не нужно; при слишком быстрой отправке страница сама ждёт, сохраняя текст.

Малая русская модель Vosk готовится автоматически; `--no-stt` пропускает её загрузку. Для `--offline` модель нужно заранее подготовить через `make stt-model`, иначе доступен текстовый ввод. Новый UI собирается обычным `npm run build` во второй каталог `frontend/dist-personal`.

Для публичного HTTPS впишите **локально** в `.env` `TUNA_API_KEY` (право `tunnels:connect`); старый `TUNA_TOKEN` также поддержан. Ключ не отправляется пользователям и не передаётся в командной строке. Установленный `tuna` запускается installer командой:

```sh
tuna http 9999 --subdomain=royal-penguin-6552 --rate-limit=10 --https-redirect --inspect=false
```

Фактический адрес берётся из ответа `Forwarding` Tuna, а не вычисляется: зона зависит от плана (в текущем Free — `https://royal-penguin-6552.a.tuna.free`). Installer подтверждает доступность именно этой страницы по HTTPS. `TUNA_ENABLED=0` или `--offline` отключают управляемый туннель. Отдельный повторный запуск/остановка: `python3 scripts/tuna_tunnel.py start|stop --env-file .env`. Приватные PID/лог находятся в `.cx/personal-tunnel`; чужие процессы скрипт не завершает.

### Поздние сведения оператора

После миграции `0010` дополнения HITL не только сохраняются: агент отдельно разбирает их и учитывает в следующем контексте инцидента. В истории видны статус и ссылка на AR разбора. Старый граф/денежные действия не повторяются; формальное решение человека не заменяется. Закрытые кейсы получают задачу повторного ручного разбора. Детали: [ADR-0016](docs/adr/ADR-0016-operator-feedback-processing.md), [ADR-0017](docs/adr/ADR-0017-public-personal-chat.md).

В текущем Free-плане Tuna браузер при первом посещении видит собственное предупреждение с кнопкой «Посетить». Это происходит до загрузки приложения и не является нашей CAPTCHA. Ограничения формы не добавляют таких заданий. Проверка туннеля обычным API-клиентом подтверждает транспорт/страницу, но не отсутствие этого внешнего предупреждения: [официальное описание](https://tuna.am/en/docs/abuse/).

### Повторная установка без изменения данных

`install.sh` вызывает seed в режиме `--if-needed`: при существующих данных выводит coverage и наличие baseline, сохраняя справочники, настройки, seed_done, текущий запуск, время и файлы снимков. Недостаточное покрытие старой истории отмечается предупреждением; история автоматически не пересоздаётся. При незавершённом seed, отсутствии/несовместимости pg-tools или ошибке первичной генерации установка прекращается с понятной причиной. Docker содержит pg_dump/pg_restore 16, соответствующие PostgreSQL 16. Подробнее: [ADR-0018](docs/adr/ADR-0018-safe-install-seed.md). Отсутствующий старый baseline не создаётся из живого стенда; резервную копию следует хранить отдельно.

Служебная строка `sim_state`, созданная backend до seed, не считается заполненным
банком: если клиентов и запусков ещё нет, первичный `--if-needed` выполняет seed.
При наличии клиентов или запусков без корректного `seed_done` установка по-прежнему
останавливается для диагностики, сохраняя данные. Ошибка такого старта может проявляться
как `Cannot choose from an empty sequence` после Start при нуле клиентов; повторять
`--reset` для диагностики не следует. Исправление и регрессия: issue #135.

В чате :9999 добавлено «Как к вам обращаться?» — необязательное имя, псевдоним или произвольная подпись до 120 символов. Подпись сохраняется после отправки сообщения и восстанавливается в своей сессии. Её можно убрать для следующих сообщений; старые сообщения сохраняют своё обращение. Это контекст диалога для агента, без проверки личности или банковской идентификации.

Встроенные `mock_social_polling`/`review_portal_feed` не создают сообщения по реальному
таймеру. Автоматическая синтетика идёт через часы симуляции; отдельный mock-пакет —
явное «Опросить сейчас» при активной небазовой симуляции. При паузе команда отклоняется.
URL-адаптер пока не реализован и сообщает ошибку вместо выдуманного сетевого ответа.
Настоящие `/feed`, `/compliance`, чат и голосовой вход работают при остановленных часах.
При пустом `current_run_id` первый явный запрос создаёт один `live` без старта генераторов.
Обоснование: [ADR-0019](docs/adr/ADR-0019-explicit-synthetic-ingest.md).

Для старой истории без CSI можно сначала посмотреть план, затем добавить только
недостающие CSI (без reset, через обычный normalizer, транзакционно):

```bash
docker compose exec -T backend python /scripts/seed/repair_csi.py
docker compose exec -T backend python /scripts/seed/repair_csi.py --apply
```

Перед записью сохраните приватный backup БД. Повторный `--apply` не меняет данные.
Пробелы вне CSI/SLA требуют отдельного решения. Старый `baseline.dump` не переписывается:
после восстановления **совместимого** старого архива приложение само выполняет CSI-ремонт
до уведомления о готовности и старта нового сценария. Ручная команда после restore не нужна.
Повторный restore не накапливает CSI; полный архив остаётся без добавлений. Ошибка ремонта
останавливает завершение restore и старт нового запуска, а не скрывается за HTTP 202.
Dump/restore и ремонт используют БД переданного соединения, включая аутентификацию,
независимо от глобального `DATABASE_URL`.

Совместимость конкретного старого `lite.dump` (формат pg_dump 18 и старая схема) с
текущим стендом вынесена по согласованию в [#108](https://github.com/florren/vibebashers/issues/108).
Авто-CSI не конвертирует формат архивов и не заменяет миграции схемы.
См. [ADR-0020](docs/adr/ADR-0020-automatic-baseline-csi.md).

### Фильтры сущностей и экономика инцидента

На `/finance`, `/engine`, `/compliance`, `/manager` доступен поиск по SIG/INC и связанным
кодам (AR/TR/AS/CL/HD/ESC и другие коды реестра). Запрос применяется до пагинации и вместе
с выбранными фильтрами запуска/продуктов. На `/finance` он ограничивает также суммы,
график и оба контура оценки. `/journey` позволяет найти сигнал по коду/тексту или коду
связанной сущности и закрепить выбранный граф.

В карточке инцидента вкладка «Экономика» показывает расчёт backend, исход, ставку,
множители, возврат и чистый эффект с копейками. `/economics` — калькулятор допущений,
редактирование ставок через существующие настройки и факт по симуляции. Ставки
сохраняются только кнопкой; изменение параметров предпросмотра не меняет настройки.
Штрафы и подтверждённый эффект вмешательства остаются отдельными оценками (ADR-0013/0014).

Для старого `lite.dump` доступна безопасная подготовка совместимого архива в изолированной
PostgreSQL 16: [инструкция и recovery](docs/BASELINE-COMPATIBILITY.md). Оригинал сохраняется;
backend выбирает подготовленный файл только после проверки SHA256 источника и результата.

Нормализация имеет отдельный общий бюджет 10 секунд: порядок моделей
`GigaChat-3-Lightning → GigaChat-3-Pro → GigaChat-3-Ultra`. При последовательных timeout
бюджеты — 4/3/3 секунды; свободное время переходит следующей модели. Pro берётся из
настроенных активных ролевых профилей; без него сохраняется Lightning → Ultra (5/5). Обычный fast_path
сохраняет 8 секунд. После HITL/follow-up статистика AR продолжает всю историю шагов,
включая токены, latency и известный cost. Решение и live-замеры: [ADR-0021](docs/adr/ADR-0021-normalization-reserve-and-resume-usage.md).

Холодный GigaChat использует connect timeout 2 с для TCP/TLS и ротацию ключей
после transport timeout/network, включая отмену активного HTTP внешним дедлайном.
Валидные OAuth-токены кэшируются; транспортный сбой не деактивирует ключ.
Если все ключи испытали транспортный сбой, пробуется наиболее давно отказавший;
429/auth/quota остаются обязательными ограничениями. Все попытки и исправления JSON
делят исходный бюджет модели. Подробности: [ADR-0022](docs/adr/ADR-0022-gigachat-cold-start-rotation.md).

Перед готовностью backend GigaChat получает OAuth-токены резервных ключей и проверяет
`GET /models` (без генерации). Подготовка ограничена 12 с и явно логирует неготовность;
при недоступном провайдере сохраняется штатный replay/mock. HTTP keep-alive — 60 с.
Для проверки холодных запусков: `scripts/bench_normalization_timeouts.py --cold-each --prepare`;
`initialization_ms` и `cold_total_ms` показывают стоимость запуска отдельно от 10-секундной нормализации.

### Полный цикл демо на `/journey`

Панель «Эмуляция команд и сотрудников» запускает отдельный сценарий с одним из пяти исходов: успех в срок, поздний успех, бездействие, неуспешная попытка, восстановление после эскалации. Агент может отвечать за demo-оператора и руководителя; ручной ввод сохраняется. Источник LLM и demo-авторство записываются в историю. Успешное закрытие связано с отчётом проверки и конечными уведомлениями клиентам. Каталог включает 20 тематических входов из ТЗ заказчика. Границы синтетических интеграций, критерии приёмки и порядок показа: [docs/DEMO-EXECUTION.md](docs/DEMO-EXECUTION.md).
